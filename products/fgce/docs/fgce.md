## Обзор

FGCE — ядро двумерной композиции. Оно принимает кадр запросами и возвращает буфер пикселей, который хост кладёт на экран один к одному. Растр и вектор рисуются в одной целочисленной координате **sPx**. Квант чертежа остаётся 5/15; дробной координаты у вызывающего нет. Число клеток окна выводится из его размера в sPx. Координаты записаны на эталоне; живой кадр только читает их.

Ядро не открывает окно, не читает файлы и не знает кодеки. Хост говорит с ним через `submit`; веб и мобайл используют адаптер хоста, который в крейт не входит (§10).

Этот документ нормативен для крейта `fgce`.

## Цели и не-цели

**Цели:**

- Один переносимый крейт без зависимостей: растр, вектор, клип, заливка.
- Адрес пикселя только целым sPx. Клетка 5/15 при любом допустимом масштабе попадает на целые пиксели.
- Скорость равна объёму памяти: запись в итоговый буфер, без промежуточного полнокадрового битмапа и без повторной конвертации на горячем пути.
- Детерминизм: один и тот же ряд запросов даёт те же байты.
- Сборка `wasm32-unknown-unknown` и обычного хоста из одного крейта.
- Живая решётка окна и дерево боксов: живые прямоугольники одним спуском от эталона, `Show` вторым спуском по уже посчитанным прямоугольникам, растр за `End` один раз.

**Не-цели:**

- Поверхность GPU, CSS, виджеты, таймер внутри ядра.
- Жест, фокус, порядок обхода, клавиатура и захват указателя. Это слой над крейтом. Он читает снимок поставленных боксов, попадание точки считает по этому снимку и шлёт сдвиг или новый прямоугольник в sPx. Pin, отступ, эталон и дерево он не читает.
- Кривая на изменение размера окна. Окно двигает боксы формулой привязки сразу.
- Шейпинг и разбор шрифтов. Глиф входит как уже построенная маска. Каретка, выделение, строка, индекс и метод ввода в крейт не входят: каретка — бокс шириной 1 sPx, выделение — заливка под глифами, оба ставит слой над ядром.
- Поворот, градиент, размытие, фильтр, клип по произвольному пути.
- Частичная перерисовка без очистки кадра.
- Цветовые профили. Буфер — 8-bit sRGB; смешение частичного покрытия идёт в линейном свете (§6).
- Разбор битстримов и любых других кодеков.
- JS/wasm-адаптер в составе крейта ядра. Ядро остаётся без экспортов; generic-адаптер — отдельный host-crate [`crates/fgce-wasm`](../crates/fgce-wasm) (C ABI `3`, [`wasm-abi.md`](./wasm-abi.md)), в поставку `fgce` не входит.
- Любые внешние зависимости: `[dependencies]` ядра пуст.

## Место в архитектуре

FGCE — ядро композиции без собственного app-shell: хост владеет окном, вводом и текстом.

Публичная поставка — один крейт `crates/fgce`. Внутренние модули — файлы этого крейта, не отдельные crates: второй публичный крейт стал бы второй дверью. Снаружи видны типы запросов и `Engine::submit`. Модули `pub(crate)`.

```
Хост (нативное приложение, wasm-хост, тест, чужой проект)
  └─ fgce::Engine::submit          ← единственная дверь
       └─ dispatch                 ← один match по Request
            ├─ place               ← align и pin, канонический проход и живой проход; frame не вызывает
            │    ├─ tree           ← эталон, окно, группы, сущности
            │    ├─ lattice        ← покрытие окна клетками
            │    └─ spx            ← квант, длина, край в пикселях
            ├─ round               ← резолв радиуса и контур скругления
            ├─ debug               ← дебаг-слой: обводки, подписи, стрелки
            │    ├─ debug_font     ← таблица 5×7 и метрики подписи
            │    ├─ tree           ← видимые узлы и цепочки предков
            │    └─ fill           ← линии обводки 1 sPx
            └─ frame               ← буфер, клип, порядок вызовов
                 ├─ store          ← загрузка изображений
                 ├─ fill           ← прямоугольник
                 ├─ blit           ← растр
                 ├─ vector         ← заливка и обводка пути
                 ├─ round          ← скруглённая заливка, маска, контур
                 └─ span           ← единственный писатель байтов; его зовут fill, blit и vector
```

Направление внутрь: `dispatch` зовёт `place`, `round`, `debug` и `frame` раздельно. `frame → {fill, blit, vector, round, store}`. `debug → {fill, frame, tree, debug_font}`. `round → {fill, spx}`. `{fill, blit, vector, round} → span`. `{store, blit, span} → color` — чистые формулы §6; `fill` и `vector` получают их через `span`. `place` читает `tree`, `lattice`, `spx` и `frame` не вызывает; `tree` читает `spx` для разбора края. `lattice`, `spx` и `color` никого не импортируют. `fill`, `blit` и `vector` не импортируют друг друга и не знают про эталон. `contract` не импортирует модули композиции. `lib.rs` вызывает `dispatch` и не содержит формул.

`frame` держит состояние и вызывает модули. Цикл по пикселям в `frame` запрещён. Очистка кадра — функция `span`.

Внешние зависимости запрещены: список `[dependencies]` ядра пуст.

Мост к декодеру — данные у хоста, не код. FGCE не импортирует кодеки. Хост, если ему нужен декодированный кадр, передаёт в `Upload` байты раскладки из §9.

## 1. Поставка и semver

Версия продукта — semver крейта, `major.minor.patch[-pre]`. Источник номера — поле `version` в `crates/fgce/Cargo.toml`; `fgce-wasm` и `package.json` несут тот же номер.

Текущая версия реализации: **`0.2.0`**. Пока major равен 0, смена minor может изменить запросы (правило Cargo для `0.y`). Патч этого не делает.

Источник номера — поле `version` в `Cargo.toml` крейта. Константа ядра:

```rust
pub const VERSION: &str = env!("CARGO_PKG_VERSION");
```

`Request::Info` возвращает ту же строку. Второго номера формата нет: форма запроса и есть публичный API этой версии.

Крейт можно скопировать в чужой проект, поэтому его `Cargo.toml` не наследует поля workspace: все значения записаны явно, без `*.workspace = true`:

| Поле | Значение |
|------|----------|
| `version` | `0.2.0` |
| `edition` | `2024` |
| `rust-version` | `1.97` |
| `license` | `AGPL-3.0-only` |
| `publish` | `false` |
| `[dependencies]` | пусто |
| `unsafe_code` | `forbid` |

`unsafe` запрещён в ядре; адаптер — единственный крейт с разрешёнными сырыми указателями (§10). Широкая запись в ядре делается безопасными кусками `u32`/`u128` (§7), не блоками `unsafe`.

Каноническое место — `crates/fgce` в корне продукта. В чужой проект копируется **каталог крейта** целиком, в любое место. Точка входа — этот каталог: в нём `Cargo.toml` и `src/lib.rs`. Подключение — path и точный semver:

```toml
[dependencies]
fgce = { path = "third_party/fgce", version = "=0.2.0" }
```

Точное `=` обязательно. Новый каталог с другим номером не соберётся, пока потребитель не сменит версию в своём `Cargo.toml`. Обновление = заменить каталог и поправить эту строку. Других включений нет: внутренние модули в зависимости не перечисляются.

Собранный `.rlib` точкой поставки не является. ABI rlib привязан к конкретному rustc, поэтому «подложить бинарник» ломается на следующем компиляторе. Модуль, который переносится, — каталог исходников; компилирует его Cargo потребителя.

Продукт собирается в собственном workspace: корневой `Cargo.toml` каталога FGCE перечисляет `crates/fgce`, `crates/fgce-wasm` и `tests/conformance`. Крейт ядра остаётся переносимым: `version.workspace = true` запрещён, при копировании снаружи используется точный `version = "=0.2.0"`.

Вызов снаружи:

```rust
let mut engine = fgce::Engine::new();
let response = engine.submit(request)?;
```

`Engine::new` только создаёт пустое состояние, без буфера. `submit` — единственный метод работы. Других публичных функций нет. Типы, без которых нельзя собрать запрос, экспортируются из корня крейта: `Request`, `Response`, `Error`, `Rect`, `Color`, `Verb`, `ImageId`, `NodeId`, `ReferenceId`, `PixelFormat`, `AlphaMode`, `Edge`, `Edges`, `Inset`, `Align`, `Pin`, `Blend`, `FillRule`, `Fill`, `Stroke`, `Peak`, `Sample`, `StrokeAlign`, `Join`, `Cap`, `Radius`, `EntityKind`, `DebugGridStyle`, `DebugPoint`, `Node`, `Frame`, `Pixels`, `Snapshot`, `Info`, `Grid`, `Lattice`.

## 2. Философия

1. **Целый пиксель.** Вызывающий задаёт геометрию целыми sPx. Покрытие пикселя — `0..=256` (§8.3). У непрозрачной заливки частичная альфа `1..=254` бывает только у наклонной или кривой кромки внутри пикселя. Кромка сетки 5/15 бинарная.
2. **Память — это и есть работа.** Пиксель меняется в итоговом буфере. Промежуточный кадр, повторный premul и копия «на всякий случай» запрещены. Единственная обязательная копия — загрузка изображения. Premul на ней выполняется у `Rgb8` и `Rgba8`. `Alpha8` остаётся покрытием до `Blit`.
3. **Один писатель.** Байты пикселя пишет модуль `span`. Остальные готовят прямоугольник, покрытие или индекс текселя.
4. **Порядок вызовов.** Непосредственное рисование идёт в порядке `submit` и ради батча не переставляется. Дерево рисует `End` обходом §5.5, поверх команд этого кадра.
5. **Ошибка не двигает состояние.** `Err` оставляет движок как до вызова.
6. **Один поток.** У `Engine` нет мьютекса. Хост держит по экземпляру на поток.
7. **Эталон — источник координат.** Размер окна не переписывает записанные клетки. Живой пиксель выводится из эталона и привязки.
8. **Окно на пиксель.** Пока `0 ≤ a ≤ R`, изменение окна на 1 sPx сдвигает пропорциональный бокс на 0 или 1 sPx. Скачок на клетку 15 — отдельный режим `snap`.

## 3. sPx и чертёж 5/15

### 3.1. Что сохраняется от чертежа

Квант тот же: fine и primary, `primary = 3 × fine`. Масштаб — целое `k ≥ 1`, то же отношение `s = k / 5`, что держало шаги целыми. Движок не принимает `s` числом с плавающей точкой.

| `k` | `s = k/5` | fine, sPx | primary, sPx |
|-----|-----------|-----------|--------------|
| 3 | 0.6 | 3 | 9 |
| 4 | 0.8 | 4 | 12 |
| 5 | 1 | 5 | 15 |
| 6 | 1.2 | 6 | 18 |
| 10 | 2 | 10 | 30 |

Допустимый диапазон ядра: `k = 1..=40`. Лестница конкретных `s` для окна остаётся политикой хоста. Ядро обещает целые шаги на всём диапазоне.

```
fine(k)    = k
primary(k) = 3 * k
```

Один **sPx** — один пиксель буфера FGCE. `+x` вправо, `+y` вниз. Левый верхний пиксель окна — начало только при привязке окна по умолчанию (§3.4).

`devicePixelRatio` в ядро не входит. Одно и то же логическое окно на 2K и на 4K задаётся целым `d ≥ 1`: сколько пикселей устройства приходится на один sPx. Хост делит сторону устройства на `d` нацело и передаёт уже sPx. Остаток пикселей устройства хост отрезает до вызова, дробного sPx из него не получается. При равном логическом окне `d = 1` и `d = 2` дают одно и то же число клеток и ту же картинку. На показе каждый sPx повторяется блоком `d×d` без фильтра (§10).

### 3.2. Клетка

Индекс primary и fine — целый, диапазон включительный. Шаг primary равен `3 * k`, шаг fine равен `k`.

```
x = primary * 3 * k + fine * k + spx
```

`fine` — только `0`, `1` или `2`. `spx` — только `-(k - 1)..=(k - 1)`. Три fine — это уже следующий primary, `|spx| = k` — уже следующий fine; так и записываются, отдельные величины за эти пределы — `BadNudge`. При `k = 5` диапазон `spx` равен `−4..=4`. При включённой сетке `spx` без заданного `fine` — только `BadNudge`. Голый sPx — одно целое и законен только при выключенной сетке; к этому целому `BadNudge` не применяется.

Любой целый пиксель при включённой сетке записывается этой тройкой. Внутри своего primary остаток `rem` (`0..3k`) даёт `fine = rem / k` и `spx = rem % k`, и такой `spx` лежит в `0..=k - 1`. Отрицательный `spx` нужен, чтобы сдвинуть уже названную линию назад, и может попасть в предыдущую клетку.

Подпись чертежа `A.B – C.D`, если она нумеруется с 1, хост переводит один раз: `primary = A - 1`. Ширина включительного диапазона `(C − A + 1) × step` от этого не меняется. При `k = 5` primary-клетка занимает 15 sPx.

Координаты вида `(H + 0.5) × step` не существуют. Линия между рядами `H` и `H+1` (0-based) — край `y = (H + 1) * step`.

Стороны бокса включительны: размер `far - near + 1`. Крайний пиксель принадлежит боксу. `Inside` ширины 1 рисуется по этому пикселю (§8.4). `Outside` красит полосу за этим краем.

### 3.3. Длина вне клетки

Иконка, кегль и радиус, заданные целым размером `n` при `s = 1`, переводятся так:

```
length(n, k) = (n * k + 2) / 5
```

Деление целочисленное. У частного `m / 5` дробная часть бывает только `.0 .2 .4 .6 .8`, поэтому отдельного правила для «ровно .5» нет. Произведение `n * k` должно помещаться в `u32`, иначе `Overflow`.

Проверка преемственности округления, которое раньше делали через `round(n × s)`:

| `n` | `k` | результат |
|-----|-----|-----------|
| 2 | 3 | 1 |
| 22 | 3 | 13 |
| 15 | 6 | 18 |

`length(1, k)` hairline не является. При `k = 1` формула даёт 0. Hairline — константа **1 sPx** на любом `k`. Ширина обводки 0 — `BadStroke`.

### 3.4. Живая решётка окна

Число клеток выводится из окна. Фиксированный лист 128×63 в ядре не хранится: такой размер может быть только каноном конкретного эталона (§4).

Принцип снят с локальной ветки `web-lattice-anchor` и записан без её развилки. В той ветке шаг оставался 15, высота кадра была равна окну, а центр листа считался через `floor` лишних пикселей: окно на 1 px сдвигало лист на 0 или 1 px, не на 15. Число рядов было `ceil` от высоты, поэтому последняя клетка торчала за край, а полностью внешняя в счёт не входила. Колонки при этом были заперты на 128, потому что лист держали сразу за левый и правый край. Заметка той же ветки про предыдущий счётчик оси в код не вошла. В этом законе счётчика нет: обе оси окна живые, клетка есть ровно пока она пересекает окно.

Пусть `step = primary(k)`, сторона окна `span` в sPx, `span ≥ 1`. `Lattice` с `span < 1` или `step < 1` — `BadCell`: деления нет.

```
count = (span + step - 1) / step
sheet = count * step
slack = span - sheet
```

`slack ≤ 0`. Клетка с индексом `0..count` пересекает окно. Клетка, которая с окном не пересекается, не существует. При `span`, кратном `step`, `slack = 0`: последняя линия лежит на краю окна, запасной клетки за краем нет. При ненулевом остатке лист длиннее окна и пересекает край. Пустого зазора между краем окна и последней клеткой нет: `sheet ≥ span`.

Привязка окна задаёт, с какого края растёт этот запас. Знак оси — не направление `+x/+y`:

| Ось | −1 | 0 | 1 |
|-----|----|---|---|
| x | левый край, origin = 0 | центр листа | правый край |
| y | нижний край | центр листа | верхний край, origin = 0 |

```
origin_x(−1) = 0
origin_x(1)  = slack
origin_x(0)  = slack.div_euclid(2)

origin_y(1)  = 0
origin_y(−1) = slack
origin_y(0)  = slack.div_euclid(2)
```

По умолчанию окно привязано к верху и к левому краю: pin `(x = −1, y = 1)`, origin `(0, 0)`. Иной pin окна задаётся отдельно.

Делёж выступа пополам — только pin `0`. Тогда лишний пиксель отрицательного `slack` остаётся на стороне lead, слева или сверху: `lead = slack.div_euclid(2)`, `trail = slack - lead`. Половинного origin нет. При `slack = −5` лист выступает на 3 sPx в lead и на 2 sPx в trail. Pin к ближнему краю держит origin `0`: lead `0`, весь slack на trail. Pin к дальнему краю держит origin `= slack`: trail `0`, весь slack на lead.

| pin | surface | span листа | slack | lead | trail |
|-----|---------|------------|-------|------|-------|
| 0 | 100 | 105 | −5 | −3 | −2 |
| 0 | 90 | 90 | 0 | 0 | 0 |
| 0 | 91 | 105 | −14 | −7 | −7 |
| ближний `(−1, 1)` | 100 | 105 | −5 | 0 | −5 |
| дальний | 100 | 105 | −5 | −5 | 0 |

Пример покрытия при `step = 15`: окно 91 даёт 7 клеток и лист 105; окно 90 даёт 6 клеток и лист 90. Рост окна на 1 px добавляет клетку только когда новая сторона впервые пересекает её. Координата, привязанная к левому или верхнему краю, от этой новой клетки не прыгает.

### 3.5. Что у прежней раскладки снято

Прежняя CSS-поверхность больше не закон размещения. У неё сняты: `sPx(N, s) = round(N × s)` как определение единицы, неокруглённый origin `(surface − span) / 2`, координата полуклетки, hairline `0.5`, умножение шага на DPR, `transform: scale` холста, запертый лист 128×63 как единственный кадр. Квант 5/15 и `s = k / 5` живут в §3.1. Живое окно — в §3.4. Дерево боксов — в §4.

## 4. Дерево боксов

Слои снизу вверх. Нижний слой не знает, где он лежит на окне. Каждый следующий только размещает уже собранный прямоугольник.

```
Сущность          размер в sPx, места на окне нет
Координатный бокс x1,y1–x2,y2 в сетке родителя
Групповой бокс    объединение координатных боксов, ровно два ребёнка
Произвольный бокс ручные края, минимум один ребёнок, своя сетка по окну; может лежать в произвольном боксе
Оконный бокс      живая решётка §3.4
Эталон            канон координат; у среды свой эталон, у эталона своё окно
```

Родитель сущности — окно, пока её id нет ни в одном `children`. Группа и произвольный бокс — законные родители: края разбираются в локальных координатах того, кто держит id. Родитель группы — окно, группа более высокого слоя или произвольный бокс. Родитель произвольного бокса — окно или произвольный бокс. Выше группы лежат другие группы без предела по глубине, произвольные боксы или окно. Выше окна — только эталон.

### 4.1. Эталон

Координаты записываются на эталоне и при смене окна не переписываются. У эталона есть канонический размер окна `canon_w × canon_h` в sPx, целое `k`, целое `d` и pin окна по умолчанию. Живой размер приходит в `Begin` и живёт только до следующего `Begin`.

У сервиса несколько эталонов. Каждый держит своё окно: один канон для компьютера, другой для мобильного. Активен один. Переключение — один кадр, без класса движения. Порог на эталоне — минимум клеток, с которого этот эталон имеет право стать активным. Число колонок и рядов считается шагом **его** `k`, не шагом того, кто был активен. Эталон подходит при `count_x ≥ enter_cols` и `count_y ≥ enter_rows`. Ноль на оси эту ось не держит. Среди подходящих берётся больший `enter_cols`, затем больший `enter_rows`. Полное равенство оставляет текущий, если он в этой ничьей. Текущий вне победившей пары — активен меньший `ReferenceId`. Не подошёл никто — текущий остаётся. От этого счёта кадры не качаются туда-обратно, когда у эталонов разные `k`. Обратный порог — числа другого эталона, отдельного поля нет.

`UseReference` с ненулевым id удерживает эталон, пока не придёт другой такой запрос или `UseReference { id: 0 }`. Ноль снимает удержание и возвращает выбор порогу. Если в одном кадре сошлись порог и запрос, выполняется запрос. Между `Begin` и `End` переход один. Второй `UseReference` после уже прошедшего перехода — `ReferenceBusy`: эталон и дерево не меняются. Вызов, который сам вернул `Err`, переход не занимает. До первого `Begin` и после `End` переключений может быть несколько: так записываются деревья двух эталонов.

Встроенный эталон в этот выбор не входит, как только хотя бы один эталон сервиса подходит под окно. Базовый эталон сервиса записывает порог 0, чтобы маленькое окно не осталось на пустом встроенном.

У каждого эталона своё дерево. Узел, созданный запросом, попадает в активное. Снимок и кадр читают только его. `NodeId` уникален на весь движок: один id не лежит в двух деревьях. `Show`, `Place` и `Remove` ищут id только в активном дереве. Id другого эталона для них — `UnknownNode`, то дерево не меняется. Новый узел с id, который уже есть в другом дереве, — `BadParent`. Повтор того же класса в активном дереве заменяет поля (§5.5). Другой класс — тоже `BadParent`.

### 4.2. Сущность

У сущности нет положения. Положение появляется только у её координатного бокса. Поля запроса `Entity` разложены по задаче: имя, место, краска. Четвёртая таблица — размер бокса, который ядро выводит само и в запрос не принимает.

Клетка говорит одно из трёх: **обязателен**, **по умолчанию**, **поля нет**. Столбец читается сверху вниз: это полный набор одного типа.

**Имя.** Кто эта сущность.

| Поле | Photo | Glyph | Vector | Flat | Box |
|------|-------|-------|--------|------|-----|
| `id` | обязателен, `NodeId` ≥ 1 | обязателен, `NodeId` ≥ 1 | обязателен, `NodeId` ≥ 1 | обязателен, `NodeId` ≥ 1 | обязателен, `NodeId` ≥ 1 |
| `kind` | `Photo` | `Glyph` | `Vector` | `Flat` | `Box` |

**Место.** Куда встать на окне. Одинаково у всех пяти.

| Поле | Photo | Glyph | Vector | Flat | Box |
|------|-------|-------|--------|------|-----|
| `on_grid` | по умолчанию включена | по умолчанию включена | по умолчанию включена | по умолчанию включена | по умолчанию включена |
| `edges` | обязателен, §4.3 | обязателен, §4.3 | обязателен, §4.3 | обязателен, §4.3 | обязателен, §4.3 |
| `align` | по умолчанию `(0, 0)` | по умолчанию `(0, 0)` | только `(0, 0)`, иное — `BadAnchor`; вершины в `zero + local` | только `(0, 0)`, иное — `BadAnchor`; `free = 0` | только `(0, 0)`, иное — `BadAnchor` |

**Краска.** Чем рисовать. У картинки, пути и заливки разные поля.

| Поле | Photo | Glyph | Vector | Flat | Box |
|------|-------|-------|--------|------|-----|
| `image` | обязателен, ненулевой `ImageId` | обязателен, ненулевой `ImageId` | поля нет | поля нет | поля нет |
| `format` | обязателен, `Rgb8` или `Rgba8` | обязателен, `Alpha8` | поля нет | поля нет | поля нет |
| `tint` | по умолчанию непрозрачный белый | по умолчанию непрозрачный чёрный | поля нет | поля нет | поля нет |
| `color` | поля нет | поля нет | обязателен | обязателен | обязателен |
| `blend` | по умолчанию `SrcOver` | по умолчанию `SrcOver` | по умолчанию `SrcOver` | по умолчанию `SrcOver` | по умолчанию `SrcOver` |
| `verbs` | поля нет | поля нет | обязателен | поля нет | поля нет |
| `fill`, `stroke` | поля нет | поля нет | ровно одно; `fill` несёт `rule`, `stroke` — `width_q8`, `StrokeAlign`, `join`, `cap`, `peak` | поля нет | хотя бы одно; `fill` и `stroke` вместе разрешены, порядок — `fill`, затем `stroke` |
| `radius` | по умолчанию нет | по умолчанию нет | `BadRadius` при любом значении | по умолчанию нет | по умолчанию нет |

Клетка «поля нет» значит: поле в запрос не передано. Переданные `verbs`, `fill` или `stroke` там, где их клетка говорит «поля нет», — `BadPath`. Переданные `format`, `image`, `color` или `tint` не своего типа — `BufferLayout`. Пропущенный `format` у `Photo` или `Glyph` и пропущенный `color` у `Vector`, `Flat` или `Box` — `BufferLayout`. Пропущенный обязательный `image` — `UnknownImage`. Пропущенные обязательные `verbs` — `BadPath`. Пропущенные обязательные `edges` — `BadCell`. `Photo` и `Glyph` с `ImageId` 0 или с id, которого нет в store, — `UnknownImage`. `format` сущности и `format` изображения в store совпадают; иное — `BufferLayout`, состояние прежнее. Оба рисуются 1:1. `Glyph` — только `Crisp`. `Area` остаётся у непосредственного `Blit`, когда `dest` и `src` разного размера. У `Vector` оба поля `fill` и `stroke` сразу или ни одного — `BadPath`. У `Box` пустые оба — `BadPath`; оба вместе разрешены и рисуются в порядке `fill`, затем `stroke`. `fill` несёт `rule`. `stroke` несёт `width_q8` в 1/256 sPx (`width_q8 ≥ 1`), `StrokeAlign`, `join`, `cap` и `peak` (§8.4). Пропущенный параметр выбранной ветки — `BadPath`. Поле `align` сущности остаётся прижатием бокса и вершины не двигает. У `Vector`, `Flat` и `Box` допустимо только `(0,0)`; иное — `BadAnchor`. Поле `radius` — скругление бокса §8.5; у `Vector` оно всегда `BadRadius`, у остальных типов допустимо и по умолчанию отсутствует. Отсутствующий радиус и радиус 0 — одно и то же поведение без скругления.

**Бокс сущности.** Его считает ядро. Запроса с размером бокса нет.

| | Photo | Glyph | Vector | Flat | Box |
|--|-------|-------|--------|------|-----|
| Размер | `width × height` изображения | `width × height` изображения | включительные границы результата, включая наружную обводку | равен координатному боксу | равен координатному боксу |

`Empty` — шестой вариант: пикселей не кладёт, но занимает координатный бокс в дереве и в `Snapshot`. `align` у него только `(0, 0)`, иное — `BadAnchor`; `radius` — `BadRadius`; `blend` принимается и игнорируется. Размер бокса равен координатному.

Крайний пиксель бокса `Photo` и `Glyph` — пиксель картинки 1:1 и лежит внутри бокса. Отдельной обводки у этих типов нет. Изображение крупнее координатного бокса — `BoxOverflow`. `Upload`, который создаёт такую пару у уже стоящей сущности, оставляет состояние прежним (§5.3). Уменьшение делает хост до `Upload`. `Vector` приносит вершины в локальных sPx своего координатного бокса, в пикселе `zero + local`; `align` их не двигает (§4.5).

Сущность, включённая в сетку, задаёт положение в таком порядке: сначала линия 15, затем линия 5, и только после обеих — sPx. Флаг выключения сетки снимает этот порядок: край — одно целое sPx, не тройка. Клеточная тройка при выключенной сетке и голое целое при включённой — `OffGrid`. При включённой сетке `spx` без `fine` — только `BadNudge` (§3.2).

### 4.3. Координатный бокс

При включённой сетке край — три целых, уже ограниченных в §3.2. При выключенной край — одно целое sPx, и `BadNudge` к нему не применяется:

```
edge = primary * 3 * k + fine * k + spx
```

Прямоугольник задают две точки углов. `(x1, y1)` — ближний угол, левый верхний. `(x2, y2)` — дальний угол, правый нижний. Оба числа каждой точки — координаты sPx, не ширина и не высота. Ширина `x2 − x1 + 1`, высота `y2 − y1 + 1`. Края включительны: пиксель угла принадлежит боксу. `x2 < x1` или `y2 < y1` — `BadCell`.

Ненулевой `fine` или ненулевой `spx` — это отступ края. Такой отступ разрешён у одной или у двух сторон, у каждой свой. Третья сторона с отступом — `BadNudge`. Две сетки, не три: 15 и 5. sPx только подправляет уже заданную линию 5 на `1..=(k − 1)` пикселей в любую сторону.

Бокс сущности лежит внутри этого прямоугольника. Если по ширине или по высоте он больше координатного хотя бы на 1 sPx, это `BoxOverflow`, ещё до привязки: вдвинуть его некуда.

### 4.4. Ноль внутри бокса

Сетка внутри любого бокса совпадает с решёткой окна, а не с левым верхним пикселем самого бокса. Точка `0,0` локальных координат — ближайшее пересечение линий 15, которое лежит внутри бокса: первая линия primary на краю или сразу внутрь от левого и верхнего краёв.

```
r = (edge - origin).rem_euclid(step)
zero = edge            если r = 0
zero = edge + step - r если r ≠ 0
```

`origin` — каноническое начало решётки окна §3.4, от канонического размера эталона. Живая решётка от текущего окна двигает snap-линии, но `zero` не пересчитывает. При origin `0` остаток совпадает с `edge.rem_euclid(step)`. Окно `100`, `step = 15`, pin `x = 1`, origin `−5`, край `10`: край уже на линии, `zero = 10`.

Бокс, сдвинутый левее линии 15 на 3 sPx, получает локальный левый край `−3`. Та же формула по вертикали. Внутренний элемент или группа могут стоять на отрицательной локальной координате, но не дальше линии своего бокса. Координата за этой линией — `BoxOverflow`. Если внутри бокса нет ни одной линии 15, ноль всё равно считается по формуле и может оказаться за дальним краем; дети при этом по-прежнему не выходят за линию бокса.

Ноль считается по каноническому краю и при живом сдвиге заново не ищется. Пиксель локальной координаты `local`: `pixel = zero + local`. После разбора хранятся не тройки, а целые от ближнего канонического края родителя:

```
a = zero + local - parent_near
size = far - near + 1
```

`zero` и `parent_near` здесь канонические. Дальше pin и `Show` двигают уже `a` и `size`. Сдвиг родителя на 1 sPx сдвигает ребёнка на 1 sPx.

Внешние линии группового бокса совпадают с крайними линиями координатных боксов детей. Его сетка при этом остаётся оконной.

### 4.5. Привязка сущности

Пара `(x, y)`, каждое значение только `−1`, `0` или `1`. Иное — `BadAnchor`. По умолчанию `(0, 0)`: центр координатного бокса.

Это прижатие бокса сущности к координатному боксу, не закон движения при смене окна. Поле называется `align`. На группу, произвольный бокс и окно оно не ставится.

| x | y | Куда встаёт бокс сущности |
|---|---|---------------------------|
| 0 | 0 | центр |
| 1 | 0 | центр правой стороны |
| −1 | 0 | центр левой стороны |
| 0 | 1 | центр верхней стороны |
| 0 | −1 | центр нижней стороны |
| 1 | 1 | правый верхний угол |
| 1 | −1 | правый нижний угол |
| −1 | 1 | левый верхний угол |
| −1 | −1 | левый нижний угол |

`y = 1` — верх, `y = −1` — низ. Пусть `S` — включительный размер координатного бокса, `C` — размер бокса сущности, `free = S - C` (`free ≥ 0`, иначе бокс уже отвергнут как `BoxOverflow`). Начало сущности от левого или верхнего края координат:

```
x −1 → 0
x  1 → free
x  0 → free.div_euclid(2)

y  1 → 0
y −1 → free
y  0 → free.div_euclid(2)
```

На оси `0` лишний пиксель остаётся справа или снизу. `x = −1` прижимает к левому краю, `y = −1` — к нижнему, дальнему. `x = 1` прижимает к правому, `y = 1` — к верхнему, ближнему. У `Flat` размеры равны, `free = 0`; у `Vector` вершины стоят в `zero + local` координатного бокса. Поэтому у этих двух типов допустимо только `align = (0,0)`; иное — `BadAnchor`.

### 4.6. Группа, произвольный бокс, движение окна

Группа нижнего слоя собирает детей. Группа — бинарный union: детей ровно два, и набор из сущностей и групп сходится в «две сущности», «две группы» или «одна сущность и одна группа». Иное — `BadGroup`. Набор из трёх и более сущностей и групп — тоже `BadGroup`; контейнер списка — `Arbitrary`, а не группа. Ребёнок, который является произвольным боксом, этим кодом не пользуется: группа его не держит, и это только `BadParent`. Прямоугольник группы в каноне эталона — включительное объединение координатных боксов детей. Поля `x1,y1,x2,y2` группы наружу не задаются. `Place` группы — `BadParent`: объединение не становится входом; группа — производный union, для контейнера, который двигают, есть `Arbitrary`. Канон пишут узлы, которые хранят собственное `a`.

Произвольный бокс занимает прямоугольник, края которого заданы вручную той же грамматикой §4.3. Поле `on_grid` то же, что у сущности: по умолчанию включено. Выключенное разрешает голое целое; тройка при выключенной сетке и голое целое при включённой — `OffGrid`. Это не объединение детей: дети лежат внутри уже нарисованных координат. Детей не меньше одного, и каждый ребёнок — сущность, группа или произвольный бокс. Пустой произвольный бокс — `BadArbitrary`. Верхней границы числа детей нет. Родитель произвольного бокса — окно или произвольный бокс; иной родитель — `BadParent`. Группа не держит произвольный бокс. Произвольный бокс может держать другой произвольный бокс. Края дочернего произвольного бокса лежат внутри координатного бокса родителя; иное — `BoxOverflow`.

Внутри него своя система координат. Её ноль — пересечение линий 15 окна по §4.4, не левый верхний пиксель нарисованного прямоугольника. Ребёнок отсчитывается от этого нуля и не выходит за нарисованную линию. Отступ §4.8 на детях не считается: его носит сам произвольный бокс, если он лежит прямо под окном.

Привязка группы, произвольного бокса и окна — отдельное поле `pin`, та же тройка `−1/0/1`. Оно не прижимает содержимое и не называется `align`. Значение вне тройки у `Group`, `Arbitrary`, `DefineReference` и `Lattice` — `BadAnchor`. `pin` задаёт, как прямоугольник едет, когда меняется размер родителя. Размер самого прямоугольника от этого не меняется. Растягивание во время движения делает слой над ядром запросом `Show` (§4.7).

Канонический начало `a` и размер `size` записаны на эталоне. Канон родителя по этой оси — `R`, живой размер родителя — `L`. Зазор до дальнего края: `gap = R - (a + size)`.

| Pin | Живое начало |
|-----|----------------|
| x = −1 или y = 1 | `a` — левый или верхний край, координата не едет |
| x = 1 или y = −1 | `L - size - gap` — тот же зазор в пикселях канона справа или снизу |
| 0 | `(a * L) / R` — доля родителя |

Деление pin `0` — `(a * L).div_euclid(R)`, в том числе при отрицательном `a`. При `R = 0` — `Overflow`. Пока `0 ≤ a ≤ R`, рост `L` на 1 меняет результат pin `0` на 0 или на 1, не на клетку. Pin к дальнему краю (`x = 1` или `y = −1`) сдвигает начало на ту же прибавку, что получило `L`, и сохраняет зазор: шаг клетки от размера окна не зависит, поэтому неизменный зазор в sPx — это те же клетки. Pin к ближнему краю (`x = −1` или `y = 1`) оставляет начало равным `a`. Pin `0` двигает начало не со скоростью края, а по доле.

Проверка: `R = 1000`, `a = 400`, `size = 50`. Pin `0` при `L = 1100` даёт начало `440` — окно выросло на 100, начало на 40. Pin `x = 1` держит `gap = 550` и даёт начало `500` — начало сдвинулось на те же 100, что и окно. Pin `y = 1` при любом `L` оставляет вертикаль `400`.

По умолчанию движение плавное в этом смысле: пиксель за пикселем. `snap` выключен. Включённый `snap` после формулы квантует абсолютный край в sPx окна: `parent.live_near + pin_result`. Линии лежат в `origin + i * step` при любом целом `i`. В канон возвращается положение относительно родителя: `line − parent.live_near`.

- pin к левому или верхнему краю — наибольшая линия, которая не больше абсолютного края;
- pin к правому или нижнему — наименьшая линия, которая не меньше абсолютного края;
- pin `0` — ближайшая линия, при равном расстоянии та, что справа или снизу.

Уже стоящий на линии абсолютный край не двигается. Это единственный режим прыжка. `snap` применяется после pin и до отступа §4.8.

Окно само является корнем, поэтому его pin читается как §3.4, а не как сдвиг внутри ещё одного родителя.

Живой пересчёт запускают `Snapshot`, `Place` перед обратным pin и `End`, и только если изменились живой размер, активный эталон, pin, канон, предок, отступ или `Show`. Эталон к этому моменту уже выбран (§4.1); проход его не меняет.

1. Посчитать `count` и `origin` живой решётки окна для `snap`. Канонический `origin` для `zero` уже учтён в `a`; список клеток не хранится.
2. Каноническое объединение группы пересчитать, если изменился канон ребёнка или состав детей. Смена окна его не трогает.
3. Живые прямоугольники pin и отступа записать одним спуском от окна к листьям.
4. `Show` наложить вторым спуском по уже посчитанным прямоугольникам (§4.7). Клетки заново не разбираются.

Любое изменение канона ребёнка — `Place`, повтор `Entity` с новыми `edges`, включение или удаление из `children` — запускает один канонический проход. Снизу вверх пересчитывается union каждой затронутой группы: абсолютный канонический пиксель ребёнка — `parent.near + a`, union — минимум и максимум по детям. Затем сверху вниз каждому ребёнку пишется `a = absolute − parent.near`; `a` группы у её родителя берётся из нового near. Изменение near поднимается по цепочке групп до корня, и соседи на каждом уровне переписываются в том же проходе. Без этого `Place` ребёнка сдвигает near группы, а соседи остаются со старыми `a` и едут. Канонический проход — часть `place`; `tree` хранит узлы и `a` не пересчитывает. Запускает его обработчик `Entity`, `Group`, `Arbitrary`, `Remove` и `Place` сразу после разбора запроса, до ответа; `Snapshot` и `End` запускают только живой проход, если канон не менялся.

Растр за один `End` обходится один раз. Узел хранит живой прямоугольник; список хранит одно поколение. Совпавшее поколение списка пропускает пересчёт прямоугольников. `Begin` обнуляет буфер и при том же размере, поэтому `End` после него снова пишет пиксели уже посчитанных прямоугольников. Растровые модули получают целые прямоугольники и эталона не видят.

### 4.7. Положение на экране во время движения

Кривую, длительность и отмену считает слой над ядром. В этом крейте нет модуля `motion`, типа `MotionClass` и запроса `Advance`.

Пока движение играет, слой шлёт `Show { id, rect }`. `rect` — включительный прямоугольник в sPx окна, от левого верхнего пикселя. Запрос не меняет края эталона. В этом кадре ядро ставит бокс по `rect` вместо результата pin и отступа. Потомок без своего `Show` pin заново не считает и сдвигается на дельту ближайшего показанного предка. Дельта — начало `Show` минус абсолютное начало предка после отступа, оба в sPx окна, как `rect.x1 − parent.live_x1` у `Place`. `pin_result` сам по себе в эту разность не входит: абсолютный край pin — `parent.live_near + pin_result`. Потомок со своим `Show` стоит по своему `rect` и эту дельту не получает. Размер потомка без своего `Show` прежний. Вылезшее за предка режет пересечение §5.5. Растянуть потомка может только его собственный `Show`. `Show` у `Photo` и `Glyph` тексели не пересчитывает: картинка остаётся 1:1 и режется пересечением показанного `rect` с предками и кадром. `rect` крупнее картинки её не растягивает: бокс сущности остаётся `width × height` и садится прежним `align`. `BoxOverflow` у этого `Show` не возникает.

`Place { id, rect }` записывает новый канон из этого же прямоугольника и снимает `Show` этого id. Перед формулой `Place` запускает проход §4.6, если входы с прошлого прохода изменились. `parent.live` и `L` ниже — результат этого прохода, не прошлого кадра. Грамматика краёв в `Place` не входит. `align` эта запись не использует. По оси x `p = rect.x1 − parent.live_x1`, по оси y `p = rect.y1 − parent.live_y1`. `size` равен стороне `rect`. Пустой `rect` у `Show` и `Place` — `BadCell`.

У сущности `a = p` по обеим осям, `size` берётся из `rect`, `align` остаётся прежним. Если после записи бокс сущности больше нового координатного бокса, `Place` — `BoxOverflow`, состояние прежнее. `Place` группы и `Place` окна — `BadParent` (§4.6, §5.5).

У произвольного бокса та же `size` и ветки pin. `Place` дочернего `Arbitrary` проверяет, что новый прямоугольник лежит внутри координатного бокса родителя; иное — `BoxOverflow`, состояние прежнее. При pin к ближнему краю `a = p`. При pin к дальнему `a = p − L + R`. При pin `0` `a = (p * R).div_euclid(L)`, а `L = 0` — `Overflow`. На pin `0` следующий кадр — `(a * L).div_euclid(R)`. Он может не совпасть с `p`: `p = 50`, `R = 3`, `L = 100` даёт `a = 1` и следующий кадр `33`. Пока `Place` не пришёл, эталон прежний. Отмена — это отсутствие следующих `Show` и отсутствие `Place`.

`Begin`, изменивший размер окна, снимает `Show`, пришедшие до этого `Begin`. На экране остаётся положение по §4.6. Смена эталона тоже снимает такие `Show` и происходит одним кадром. `Show`, присланный уже после этого `Begin`, этим `Begin` не снимается и действует в том кадре, где пришёл. Кадр, который этот `Show` не повторил, снимает его до прохода §4.6. Отмена так и остаётся отсутствием следующего `Show` и отсутствием `Place`.

Нецелый sPx запросом не выражается.

### 4.8. Отступ верхнего бокса от окна

Группа или произвольный бокс, чей родитель — окно, может задать отступ по сторонам. Вложенный бокс с отступом — `BadInset`. Отступ не сдвигает записанные края эталона и не меняет размер бокса.

Сторона задаётся так же, как край §3.2, но все три числа неотрицательны: `primary ≥ 0`, `fine` в `0..=2`, `spx` в `0..=(k - 1)`. Незаданная сторона — ноль. Это минимум зазора между этой стороной бокса и тем же краем окна. `gap0` — левый или верхний зазор, `gap1` — правый или нижний.

Принцип тот же, что у листа в `web-lattice-anchor`: пока в окне хватает места, каждая заданная сторона держит свой минимум; когда места не хватает, бокс не сжимается, а оба зазора одной оси уступают вместе. Там минимум был одной клеткой 15 на оси, прижатой к двум противоположным краям сразу, и начало в обеих фазах оставалось `floor((окно − бокс) / 2)`. Здесь у каждой стороны свой зазор, а формула pin считается до него.

По одной оси, зазоры `gap0` и `gap1` в sPx, размер бокса `size`, живое окно `L`, начало после pin — `pin_origin`:

```
lo = gap0
hi = L - size - gap1
```

Пока `lo ≤ hi`, место есть. Начало — `pin_origin`, зажатое в `[lo, hi]`. Зазор стороны не падает ниже её отступа, лишнее место остаётся там, куда его положил pin.

Когда `lo > hi`, места на оба отступа и размер уже нет. Бокс не меняет `size`. Нехватка `short = lo - hi` делится пополам, лишний пиксель уходит в дальний зазор:

```
origin = gap0 - short.div_euclid(2)
```

Оба зазора становятся меньше своего минимума на одну и ту же пару `div_euclid`. Начало может уйти в минус: бокс пересекает окно. При нечётном `short` начала двух формул расходятся: окно `119`, бокс `100`, зазоры `15+15` дают `short = 11` и начало `10`.

`snap` квантует `pin_origin` до зажатия. Пока место есть, последнее слово за отступом, и прыжок на клетку минимум не пробивает. В фазе нехватки результат на клетку больше не ставится.

Проверка при `size = 100`, `gap0 = gap1 = 15`. Окно `160`: диапазон начала `[15, 45]`. Pin, давший `0`, становится `15`, справа остаётся `45`. Окно `120`: `lo = 15`, `hi = 5`, начало `10`, оба зазора по `10`.

## 5. Запросы

`submit` принимает один `Request` и возвращает `Result<Response, Error>`.

`Rect` — две точки углов в sPx, те же, что в §4.3. `(x1, y1)` — ближний угол, `(x2, y2)` — дальний. Сторона по x — `x2 − x1 + 1`, по y — `y2 − y1 + 1`. Ни одно из четырёх чисел не является шириной или высотой. `x2 < x1` или `y2 < y1` — пустой прямоугольник. `NodeId` и `ImageId` — разные пространства: оба `u32`, ноль у `NodeId` только у окна, у `ImageId` ноль запрещён. `ReferenceId` — третье пространство, ненулевой `u32`; ноль в `UseReference` означает не эталон, а возврат к выбору по порогу.

Геометрию и запись дерева можно слать до `Begin`, если у активного эталона уже есть канон: живое окно для этого не нужно. Канон эталона из `DefineReference` есть сразу. У встроенного эталона канон появляется с первым успешным `Begin` и равен этому окну. `Entity`, `Group` и `Arbitrary` на встроенном эталоне до этой записи — `NotBegun`, состояние прежнее. `Snapshot`, `Show`, `Place`, `ReadPixels`, `ClipPush`, `ClipPop` и рисование до успешного `Begin` — `NotBegun`. `Upload` до `Begin` остаётся законным.

### 5.0. Состояние движка и форма запросов

`Engine` проходит три состояния: `Empty` — до первого успешного `Begin`; `Begun` — между `Begin` и `End`; `Ended` — после `End` до следующего `Begin`. `Begin` в `Begun` начинает новый кадр и зануляет буфер.

| Запрос | `Empty` | `Begun` | `Ended` |
|--------|---------|---------|---------|
| `Info`, `Grid`, `Length`, `Lattice`, `EdgePx`, `Measure`, `Upload`, `Drop`, `DefineReference`, `UseReference` | ok | ok | ok |
| `Begin` | ok | ok, новый кадр | ok |
| `End` | `NotBegun` | ok | `NotBegun` |
| `DrawTree` | `NotBegun` | ok, идемпотентен | `NotBegun` |
| `FillRect`, `Blit`, `FillPath`, `StrokePath`, `StrokeRoundRect`, `FillLattice`, `ClipPush`, `ClipPop`, `Show` | `NotBegun` | ok | `NotBegun` |
| `ReadPixels`, `Snapshot` | `NotBegun` | ok | ok |
| `Place` | `NotBegun` | ok | ok |
| `Entity`, `Group`, `Arbitrary` | ok, если у активного эталона есть канон; иначе `NotBegun` | ok | ok |
| `Remove` | ok | ok | ok |
| `DebugGrid`, `DebugHover`, `DebugLabel` | ok (состояние) | ok | ok |

`DrawTree` рисует активное дерево один раз и ставит флаг кадра; повторный `DrawTree` — no-op, `End` после него дерево не рисует второй раз, но дебаг-слой рисует. `DebugGrid`, `DebugHover` и `DebugLabel` меняют только состояние и пишут байты не раньше ближайшего `End`, поэтому разрешены вне кадра. Дебаг-hover ищет самый глубокий узел и при равенстве берёт нарисованный последним; это порядок REQ-5, он может расходиться с хостовым hit-test §14 (обратный порядок `Snapshot`). Расхождение относится только к дебаг-слою.

`End` дважды без нового `Begin` — `NotBegun`. `End` не сбрасывает буфер: `ReadPixels` и `Snapshot` после `End` читают последний кадр. `DefineReference` в `Begun` разрешён: дерево активного эталона меняется сразу, переход `UseReference` не занимает; `Show` удалённых узлов исчезают.

Типы запроса и ответа — Rust enums, не плоские C-структуры. `submit`:

```rust
pub fn submit<'a>(&mut self, request: Request<'a>) -> Result<Response<'_>, Error>;
```

`Request<'a>` несёт заимствованные `bytes` и `verbs`; они копируются или читаются до возврата. `Response` — `Info`, `Grid`, `Length`, `Lattice`, `EdgePx`, `Measure(Rect)`, `Frame(Frame<'_>)`, `Snapshot(Snapshot)`, `Pixels(Pixels)`, `None`. `Frame { width, height, stride, pixels: &[u8] }`. `Pixels { x, y, width, height, stride, bytes: Vec<u8> }`, `stride = width * 4`; `x, y` — начало пересечения с клипом и кадром. `Snapshot { generation: u64, nodes: Vec<Node> }`, `Node { id, parent, rect }`; `generation` — одно число на снимок.

`Entity` — общая структура плюс enum:

```rust
pub struct Entity<'a> {
    pub id: NodeId,
    pub kind: EntityKind<'a>,
    pub on_grid: Option<bool>,
    pub edges: Edges,
    pub align: Option<Align>,
    pub blend: Option<Blend>,
}

pub enum EntityKind<'a> {
    Photo { format: PixelFormat, image: ImageId, tint: Option<Color> },
    Glyph { format: PixelFormat, image: ImageId, tint: Option<Color> },
    Vector { verbs: &'a [Verb], fill: Option<Fill>, stroke: Option<Stroke> },
    Flat { color: Color },
}
```

`None` в `on_grid` — включено, в `align` — `(0,0)`, в `blend` — `SrcOver`, в `tint` — умолчание типа (§4.2). Поля, которых у варианта нет, в нём отсутствуют; отдельной проверки «поле не передано» не нужно. `Fill` несёт `rule`, `Stroke` — `width_q8`, `align`, `join`, `cap`, `peak`. `Group`, `Arbitrary`, `Show`, `Place`, `Remove`, `DefineReference`, `UseReference`, `ClipPush`, `ReadPixels` — варианты `Request` с полями §5.5; остальные варианты — §5.1–§5.3.

### 5.1. Геометрия и справка

| Запрос | Ответ |
|--------|--------|
| `Info` | `version`, `max_side = 8192`, `max_k = 40`, `max_clip = 32`, `max_vertices = 65536`, `max_coord = 1048576`, формат пикселей premul RGBA8 |
| `Grid { k }` | `fine`, `primary` |
| `Length { n, k }` | sPx |
| `Lattice { span_x, span_y, step, pin_x, pin_y }` | `count_x`, `count_y`, `origin_x`, `origin_y` по §3.4 |
| `EdgePx { edge, k }` | пиксель края по §4.3 |
| `Measure { verbs, fill, stroke }` | минимальный включительный `Rect` нарисованной области в локальных sPx, включая наружную обводку |

`Measure` — чистая справка, разрешена в любом состоянии. Ровно одно из `fill`/`stroke`: `fill` — `FillRule`, `stroke` — параметры §8.4. Границы по оси — `floor(min)` и `ceil(max) − 1`; для обводки берётся наружная граница с учётом `Join` и `Cap`. Область без пикселей — пустой `Rect`. Пустой путь — `BadPath`, параметры обводки — `BadStroke`. `Measure` и размер бокса `Vector` (§4.2) считает одна функция `vector`; `tree` и `place` читают результат и границы не повторяют.

### 5.2. Кадр

`Begin { width, height }` проверяет границы, выделяет буфер (§7) или сохраняет прежний, если `width`, `height` и выравнивание совпали, и заливает его нулём. Сторона вне `1..=8192` — `SurfaceOutOfRange`. `width` и `height` — живое окно в sPx (§3.1). `k` и `d` берутся из активного эталона. Пока эталон сервиса не задан и не удерживается, действует встроенный: `k = 5`, `d = 1`, pin `(−1, 1)`, канон равен окну первого успешного `Begin`, порог `0, 0`. Изображения в store и деревья эталонов переживают `Begin`. Стек клипа сбрасывается. `Begin` снимает `Show`, которые пришли до него, если изменился размер окна или активный эталон. Кривую это не играет. `d < 1` — `ScaleOutOfRange`. Верхней границы `d` нет: в размер буфера `d` не входит.

Живые прямоугольники считаются при `Snapshot`, при `Place` перед обратным pin и перед рисованием дерева в `End`, одним проходом §4.6, и только если с прошлого прохода изменились размер, эталон, pin, канон, предок, отступ или `Show`. Канонический проход — в обработчике изменения дерева (§4.6), до ответа на `Entity`, `Group`, `Arbitrary`, `Remove` и `Place`.

`DrawTree` рисует сущности активного дерева сразу и ставит флаг кадра. `End` рисует дерево, только если флаг не стоит, затем всегда рисует дебаг-слой (§5.3), если он включён, и возвращает `Frame`: `width`, `height`, `stride`, `pixels: &[u8]` — заимствование буфера движка. Следующий `&mut` на `Engine` возможен только после того, как ответ отпущен. Это и есть выход без копии.

`ReadPixels { rect, alpha }` возвращает **владеющую** копию в `Pixels`. `alpha: Premul` копирует как лежит. `alpha: Straight` делает обратный premul в эту копию (§6). Прямоугольник обрезается текущим клипом и кадром. `Pixels` несёт `x`, `y`, `width`, `height` пересечения, `stride = width * 4` и `bytes`. Пустое пересечение — `width = 0`, `height = 0`, пустой `bytes`, не ошибка.

### 5.3. Ресурсы и рисование

`Upload { id, width, height, stride, format, alpha, bytes }` копирует тексели в store. `Rgb8` и `Rgba8` приводятся к premul (§6). `Alpha8` остаётся покрытием. `id` выбирает хост (`ImageId`, ненулевой `u32`). Ноль в `Upload`, `Drop` и `Blit` — `UnknownImage`. Сторона изображения вне `1..=8192` — `ImageTooLarge`. Повторный `Upload` того же `id` заменяет изображение, если ни одна ссылающаяся сущность не становится больше своего координатного бокса и `format` каждой такой сущности совпадает с `format` загрузки. Иначе большая картинка — `BoxOverflow`, чужой `format` — `BufferLayout`; состояние прежнее: байты и бокс сущности не меняются. `Drop { id }` удаляет, если ни одна живая сущность на этот id не ссылается. Иначе `UnknownImage`, байты остаются. Неизвестный `id` в `Drop` и `Blit` — `UnknownImage`. Размер бокса сущности, которая ссылается на этот `id`, берётся из `width` и `height` сам (§4.2), когда `Upload` принят.

`FillRect { rect, radius, color, blend }` — сплошной прямоугольник или скруглённая форма §8.5. `radius: None` и `radius: Some(0)` идут путём прямого прямоугольника; иной радиус — заливка формы (`fill_shape`), а не маска углов. Поэтому `FillRect` с `Blend::DstOut` и радиусом стирает саму форму, а не её углы.

`Blit { id, dest, src, sample, tint, blend, radius }` — растр. `src` в пикселях изображения, `dest` в sPx кадра. `blend` по умолчанию `SrcOver`. Оба прямоугольника включительны по расположению. Неположительный `dest` или `src` — no-op до проверки границ, в том числе когда координаты вне изображения. У положительного `src` прямоугольник целиком внутри изображения: `x1 ≥ 0`, `y1 ≥ 0`, `x2 < width`, `y2 < height`. Иначе `BufferLayout`, состояние прежнее. Неизвестный `id` — `UnknownImage`. `radius` — скругление `dest` §8.5: растр пишется, затем углы вне скруглённой формы стираются через `DstOut`. Радиус резолвится от `dest` и ограничен половиной меньшей стороны.

`FillPath { verbs, rule, color, blend }` и `StrokePath { verbs, stroke, color, blend }` — вектор. `stroke` несёт `width_q8` в 1/256 sPx (`width_q8 ≥ 1`), `align`, `join`, `cap` и `peak` (§8.4).

`StrokeRoundRect { rect, radius, stroke, color, blend }` — обводка скруглённого прямоугольника. `radius: None` и `Some(0)` — прямой контур; реализация та же, что у `Box { stroke }`, и при `align: Inside` байты совпадают. `Box` дополнительно режет краску пересечением своего координатного бокса, предков и кадра (§5.5), а `StrokeRoundRect` — только клипом кадра и стека `ClipPush`/`ClipPop`; при `Center` и `Outside` внешняя половина штриха у `Box` срезается, поэтому байты расходятся. Рекомендуемое значение — `align: Center` (D2).

`FillLattice { rect, step, primary_step, fine_color, primary_color, blend }` — решётка линий шириной 1 sPx внутри `rect`: вертикали на `rect.x1 + i·step`, затем горизонтали на `rect.y1 + j·step`, `i, j ≥ 0`. `primary_step: None` — без primary; `Some(0)` или `Some(ps)`, не кратный `step`, — `BadCell`. Линия, кратная `ps`, красится `primary_color` и рисуется один раз; пересечение красит горизонталь. `blend` применяется к каждой линии, клип режет линии.

`DebugGrid { style: Option<DebugGridStyle> }` включает или выключает дебаг-слой; `None` сохраняет имена узлов. `DebugGridStyle { base, tip, label_base, label_tip, label_alpha, label_scale }`: цвет обводки уровня интерполируется от `base` к `tip` по `depth / max_depth`; подписи интерполируются по той же формуле от `label_base` к `label_tip`, а если эти поля не заданы — от `base` к `tip`. Поэтому стиль без явных цветов подписей даёт прежний кадр байт-в-байт. После интерполяции подписи и стрелки получают `label_alpha`; `0` выключает подписи. `label_scale` — целое `1..=4`. `DebugHover(Option<DebugPoint>)` задаёт точку наведения в sPx окна; `None` снимает подписи. `DebugLabel { id, text: Option<&str> }` задаёт имя узла; `NodeId(0)` — имя окна, `text: None` снимает имя, текст длиннее 64 байт или `label_scale` вне `1..=4` — `BufferLayout`. Имена и стиль — постоянное состояние движка: `Begin` их не сбрасывает; `Remove` забывает имена поддерева, повтор `DefineReference` — имена этого эталона. Кадровая аллокация — только список видимых узлов; подписи аллоцируются на `DebugLabel` (§7).

Дебаг-проход выполняется в конце `End` после дерева и после любого immediate-слоя, включая команды после `DrawTree`. Обводка идёт по видимым узлам: окно — корень глубины 0, дети рисуются раньше родителя, линии 1 sPx по `x2 + 1`/`y2 + 1` внутри кадра. Подписывается наведённый узел и его предки; окно участвует как корень цепочки подписей, но не как hover-кандидат. Стрелка узла красится цветом его подписи. Смешение обводки и подписи при `color.a < 255` — по §6 в линейном свете.

`ClipPush { rect }` пересекает rect с текущим клипом и кладёт результат. Глубина больше 32 — `ClipOverflow`. `ClipPop` при пустом стеке — `ClipUnderflow`. Начальный клип после `Begin` — весь кадр.

Прямоугольник нулевого или отрицательного размера на рисовании — no-op. Координаты вне кадра обрезаются клипом.

### 5.4. Ошибки

`ScaleOutOfRange`, `SurfaceOutOfRange`, `NotBegun`, `UnknownImage`, `UnknownNode`, `ImageTooLarge`, `BufferLayout`, `ClipUnderflow`, `ClipOverflow`, `BadCell`, `Overflow`, `BadStroke`, `BadPath`, `BadNudge`, `BadAnchor`, `BadGroup`, `BadArbitrary`, `BadInset`, `BoxOverflow`, `OffGrid`, `BadParent`, `ReferenceMissing`, `ReferenceBusy`, `BadRadius`.

Текста в ошибке нет.

Пределы: сторона кадра, канона эталона и изображения `1..=8192`; `k = 1..=40`; `d ≥ 1`; клип ≤ 32; вершин в одном пути ≤ 65_536; абсолютная координата вершины, края и `a` ≤ 1_048_576; порог эталона ≥ 0. `a * L`, `p * R` и `(a * L) / R` считаются в `i64`: при `a, p ≤ 1_048_576` и `R, L ≤ 8192` произведение не выходит за `i64`. `Measure` с пустым путём — `BadPath`; параметры обводки — `BadStroke`. Сторона кадра или канона вне `1..=8192` — `SurfaceOutOfRange`. Сторона изображения вне `1..=8192` — `ImageTooLarge`. Вершин в одном пути больше 65_536 — `BadPath`. Модуль координаты вершины, края или `a` больше 1_048_576 — `Overflow`. Отрицательный порог — `BadCell`. `stride` байт меньше `width * bpp` — `BufferLayout`. Срез `bytes` короче `(height - 1) * stride + width * bpp` — тот же `BufferLayout`, store прежний. `d < 1` и `k` вне диапазона — `ScaleOutOfRange`. Ноль в `DefineReference` — `ReferenceMissing`. `ImageId` 0 и ссылка `Photo` или `Glyph` на изображение, которого нет в store, — `UnknownImage`. `Drop` id, на который ссылается живая сущность, — `UnknownImage`, байты остаются. Второй `UseReference` между `Begin` и `End`, когда один переход уже прошёл, — `ReferenceBusy`.

### 5.5. Дерево

`DefineReference { id, canon_w, canon_h, k, d, pin, enter_cols, enter_rows }` записывает канон и пустое дерево эталона (§4.1). Повтор того же id делает это снова: канон заменяется, узлы этого эталона исчезают, их `NodeId` снова свободны, остальные эталоны не меняются. Ошибочный повтор оставляет прежний канон и прежние узлы. Активный id от повтора не меняется, и переход `UseReference` не занимается. `UseReference { id }` удерживает его. Неизвестный ненулевой `id` — `ReferenceMissing`, переход не занимается. `UseReference { id: 0 }` снимает удержание. Повтор в открытом кадре после уже прошедшего перехода — `ReferenceBusy` (§4.1).

`Entity { id, kind, on_grid, edges, align, blend, radius }` создаёт сущность и её координатный бокс в активном дереве. `radius` — скругление §8.5, по умолчанию отсутствует. `kind` — `EntityKind`: `Photo { format, image, tint }`, `Glyph { format, image, tint }`, `Vector { verbs, fill, stroke, color }`, `Flat { color }`, `Box { fill, stroke, color }`, `Empty` (§4.2). Размер бокса в запросе не передаётся. Поля краски — поля варианта; полей, которых у варианта нет, в запросе нет. Пропущенное обязательное поле варианта — тот же код §4.2. `fill` и `stroke` несут параметры непосредственного пути (§8.3, §8.4). `Photo` и `Glyph` с `ImageId` 0, с id, которого нет в store, или с пропущенным `image` — `UnknownImage`. `format`, не совпавший с store, — `BufferLayout`, состояние прежнее. `Group { id, parent, children, pin, snap, inset }` и `Arbitrary { id, parent, on_grid, edges, children, pin, snap, inset }` создают боксы §4.6. `on_grid` произвольного бокса по умолчанию включён. `parent` группы — окно (`0`), группа или произвольный бокс. `parent` произвольного бокса — окно (`0`) или произвольный бокс; иной родитель — `BadParent` (§4.6). `inset` допустим только когда `parent` — окно (§4.8).

Узел принадлежит одному родителю. Пока id не в чьём `children`, родитель — окно, и края разбираются в его локальных координатах. Поле `parent` группы и произвольного бокса равно этому родителю: у id вне списков в запросе только `0`. Другое значение на создании и на повторе — `BadParent`, узел в список не вставляется, состояние прежнее. Включение в `children` переносит узел из прежнего списка, записывает ему этого родителя и сохраняет абсолютный пиксель: `near` старого родителя плюс `a`. В старом списке id после переноса нет, поддерево из-за переноса не удаляется. Если новый родитель — группа, сначала запоминается абсолютный пиксель каждого id из нового `children`: `near` его текущего родителя плюс `a`. Затем пересчитывается объединение, и `a` группы у её родителя берётся из нового ближнего края. Каждому id из нового списка `a` равен сохранённому абсолютному пикселю минус новый `near`. Это тот же канонический проход, что и для `Place` ребёнка (§4.6); отдельного алгоритма нет. У окна и произвольного бокса ближний край от включения не меняется; абсолютный пиксель перенесённого ребёнка сохраняется той же разностью. Повтор того же `NodeId` тем же классом заменяет поля и не меняет порядок среди соседей. Другой класс, цикл, повтор id в списках, неизвестный ребёнок — `BadParent`. Исключённый из нового списка и не перенесённый в другой ребёнок удаляется вместе с потомками; если родитель от этого становится незаконным, весь запрос — `Err`.

`Show { id, rect }` ставит бокс на этот кадр, не меняя эталон (§4.7). `Place { id, rect }` у сущности пишет `a = p` и `size` из `rect` и снимает `Show`; `align` не меняется. Если бокс сущности больше нового координатного бокса — `BoxOverflow`, состояние прежнее. `Place` произвольного бокса пишет канон по pin (§4.7). `Place` группы и окна — `BadParent`. `Remove { id }` удаляет узел и потомков. Если родитель был группой или произвольным боксом и после удаления стал незаконным, запрос целиком — `Err`, состояние прежнее. Окно после удаления ребёнка остаётся законным. `Show`, `Place` и `Remove` по окну — `BadParent`, по id, которого нет в активном дереве, — `UnknownNode`. `Resize` отдельно нет: новый размер окна — это `Begin`.

`Snapshot` возвращает поколение и узлы активного дерева сзади вперёд, без окна. Поля узла: `id`, `parent`, видимый `Rect`; `generation` — одно число на снимок, в узле не дублируется. Видимый прямоугольник — layout box: координатный бокс после pin, `Show` и отступа, пересечённый с предками и кадром. Это не painted bounds: `Photo` с `align` может занимать меньше; hit-test идёт по layout box. Пустое пересечение остаётся в списке. Дети окна идут в порядке создания, дети группы и произвольного бокса — в порядке `children`. Поздний рисуется выше. `End` рисует только сущности, в том же порядке: сначала узел, потом его дети. Группа и произвольный бокс в этот проход пикселей не кладут. Краска режется пересечением координатного бокса, предков и кадра. Стек `ClipPush`/`ClipPop` действует на непосредственное рисование и `ReadPixels`; дерево в `End` его не читает.

Поколение — одно `u64` на список. Оно растёт, когда проход §4.6 пишет новые прямоугольники, и не растёт, если входы те же. Отдельного счётчика у узла нет; частичный пересчёт по узлам спецификацией не обещается.

## 6. Цвет

В запросе `Color` — прямой sRGB, каналы `u8` `r, g, b, a`.

В буфере кадра — **premul**: `rgb` уже умножены на альфу, альфа хранится отдельно. В store premul у `Rgb8` и `Rgba8`. `Alpha8` — покрытие до `Blit` (§7). Хранение и альфа считаются байтовыми формулами без деления на альфу:

```
pm(c, a) = (c * a + 127) / 255

over(src, dst, src_a) = src + (dst * (255 - src_a) + 127) / 255
```

Арифметика в `u16` на канал, затем насыщение до 255. При корректном premul (`канал ≤ альфа`) насыщение не срабатывает. `a = 255` даёт `pm(c, 255) = c`. `a = 0` даёт 0.

`over` для альфы использует ту же формулу, где `src` — альфа источника.

**Смешение `SrcOver` при `src.a < 255` идёт в линейном свете.** Кадр остаётся premul sRGB, но каналы источника и приёмника перед смешением переводятся в линейный свет, смешиваются там и кодируются обратно один раз. Таблицы — sRGB EOTF и обратное преобразование (IEC 61966-2-1):

```
L(v)     = v / 12.92                                если v ≤ 0.04045
L(v)     = ((v + 0.055) / 1.055)^2.4                иначе
decode[v]= round(65535 * L(v / 255))                v = 0..=255
E(l)     = 12.92 * l                                если l ≤ 0.0031308
E(l)     = 1.055 * l^(1/2.4) − 0.055                иначе
encode[l]= round(255 * E(l / 65535))                 l = 0..=65535

mix_straight(src, src_a, dst, dst_a, out_a) =
    encode[(decode[src] * src_a * 255
          + decode[dst] * dst_a * (255 − src_a)
          + (255 * out_a) / 2) / (255 * out_a)]
```

`out_a = over(src_a, dst_a, src_a)` — альфа остаётся байтовой; при `out_a = 0` результат 0. Деления на 8 бит до конца формулы нет. `src.a = 255` при полном покрытии — плотная запись источника без таблиц; `src.a = 0` не читает и не пишет приёмник; `dst.a = 0` даёт источник без обратного преобразования. Полностью покрытый непрозрачный пиксель равен цвету байт-в-байт.

`Blend::Src` записывает premul-источник. `Blend::Clear` записывает нули; на частичном покрытии кромка бинарная — пиксель либо обнулён, либо нет. `Blend::DstOut` — destination-out с покрытием: каждый канал premul, включая альфу, умножается на `1 − cover_alpha`. В линейный свет `DstOut` не переводится:

```
dst = (dst * (255 - cover_alpha) + 127) / 255
```

`cover_alpha` — из §8.3, поэтому `DstOut` даёт антиалиасную кромку. `cover = 256` даёт нули, `cover = 0` оставляет пиксель нетронутым. `Blend::SrcOver` смешивает каналы через `mix_straight`. Если у источника альфа 255, `SrcOver` обязан совпасть с записью источника.

Обратный перевод в прямой альфа-канал, только для `ReadPixels` + `Straight`:

```
straight(c, a) = 0                  если a = 0
straight(c, a) = (c * 255 + a / 2) / a
```

Загрузка `AlphaMode::Straight` применяет `pm` к каждому текселю один раз. `AlphaMode::Premul` проверяет `канал ≤ альфа`; нарушение — `BufferLayout`. `Rgb8` записывается с альфой 255 без умножения.

Форматы загрузки: `Rgb8` (3 байта), `Rgba8` (4), `Alpha8` (1, покрытие глифа). Строки сверху вниз, без паддинга внутри пикселя. `stride` может быть больше строки; лишние байты не читаются.

`Alpha8` в store остаётся одним байтом покрытия. При `Blit` оттенок `tint` (прямой цвет) умножается на покрытие:

```
a = (tint.a * coverage + 127) / 255
```

и в кадр идёт premul этого `a`. Покрытие 0 пропускает пиксель. У `Rgb8` исходная альфа равна 255, дальше работает та же формула, что у `Rgba8`: `straight(c, 255) = c`, `tinted_c = (c * tint_c + 127) / 255`, `tinted_a = tint.a`, `result_c = (tinted_c * tinted_a + 127) / 255`. При `tint.a = 255` это `(c * tint_c + 127) / 255`; непрозрачный белый оставляет канал исходным. У `Rgba8` оттенок снимает premul, красит прямой цвет и собирает premul заново. `straight` — формула выше. При `a = 0` результат нулевой. Иначе `tinted_c = (straight(c, a) * tint_c + 127) / 255`, `tinted_a = (a * tint.a + 127) / 255`, `result_c = (tinted_c * tinted_a + 127) / 255`. Premul `r = 200`, `a = 200` и tint `r = 255`, `a = 100` дают `r = 78`, `a = 78`. У непосредственного `Blit` оттенок по умолчанию — непрозрачный белый, картинка не красится. У сущности `Glyph` оттенок по умолчанию — непрозрачный чёрный (§4.2). `Photo` красится тем же произведением своего формата, и этот `format` совпадает с `format` изображения в store.

Любая другая реализация деления на 255 допустима только если на всём диапазоне входов `u8 × u8` байт совпадает с формулой выше. Тест этого диапазона обязателен.

## 7. Память кадра

Буфер один: высота строк, шаг строки `stride = align_up(width * 4, 64)` байт, где `align_up(n, 64) = (n + 63) & !63`. Указатель первого пикселя выровнен на 64 байта (смещение внутри выделения, без `unsafe`). Хвост строки — паддинг, хост его не показывает.

Пока размер не изменился, `Begin` не выделяет память заново, только зануляет используемые байты (`height * stride`).


На движке с `Begin` живут ещё три куска, все повторно используемые: store изображений, стек клипа, одна строка аккумулятора покрытия длиной `width` (для вектора и для разделимого бокс-фильтра). На пиксель и на сканлайн рисования в уже живые буферы кучи нет. Выделение кадра в `Begin` и байтов store в `Upload` из этого запрета выведены.

Store хранит `Rgb8` и `Rgba8` как premul-байты до `Drop` или замены. `Alpha8` лежит покрытием до `Blit` (§6). Кадр их не дублирует. За кадр существует один буфер кадра: второй полнокадровый bitmap — несоответствие. `Begin` и `Blit` не переводят заново байты, которые store уже хранит как premul.

`End` не копирует. `ReadPixels` копирует, потому что вызывающий попросил владеющие байты.

Запись в кадр идёт кусками: непрозрачный ряд — копирование `u128` (16 байт) и хвост скаляром; прозрaчный — формула §6 пачками по пикселю `u32`. Результат пачки совпадает с попиксельной формулой.

## 8. Растр и вектор

### 8.1. Прямоугольник

`FillRect` пересекается с клипом. `radius` заменяет прямой прямоугольник скруглённой формой §8.5 и заливает её через `fill_shape`; `Blend::DstOut` стирает саму форму. Непрозрачный источник пишется в пересечение. Прозрачный смешивается по §6. Пиксель сетки, попавший в пересечение целиком, имеет альфу 0 или 255 у непрозрачной заливки. Серой кромки у прямоугольника нет.

### 8.2. Выборка изображения

`Sample::Crisp`:

```
sx = (x * src_w) / dest_w
sy = (y * src_h) / dest_h
```

`x` — индекс внутри dest, `0..dest_w`. При равных размерах это копирование.

`Sample::Area` — бокс-фильтр в целых числах. Левый край dest-пикселя `x` в числителе источника: `L = x * src_w`, правый `R = (x + 1) * src_w`, знаменатель `dest_w`. Пиксель источника `i` покрывает `[i * dest_w, (i + 1) * dest_w)`. Вес — длина пересечения. Сумма весов по `x` равна `src_w`. По `y` сумма весов равна `src_h`.

Вес текселя `(i, j)` в dest-пикселе — произведение перекрытий по осям. Делитель `divisor = src_w * src_h`. Канал считается один раз, аккумулятор `u64`:

```
(sum(channel_ij * overlap_x * overlap_y) + divisor / 2) / divisor
```

Разделимый проход может копить нескаленную сумму и разделить её в конце тем же делителем. Округление по одной оси до второй этим законом не является. При равных размерах `Area` совпадает с копированием и идёт копированием. Проверка неравных размеров: источник по строкам `1 2` / `3 4` / `5 6` в dest `1×2` даёт первый пиксель `2`, второй `5`. В сумме оттенка нет. `tint` красится на канале после деления, формулами §6. Источник `0 200` в один пиксель и tint канала `1` дают канал `0`.

Клип режет dest. Индекс источника считается от исходного dest, не от обрезанного куска.

Поворот растра в v1 отсутствует: dest — ось-параллельный прямоугольник.

### 8.3. Путь

Вершины пути сущности — локальные sPx её координатного бокса (§4.4), в пикселе `zero + local`. `align` их не сдвигает (§4.5). Вершины непосредственного `FillPath` и `StrokePath` — sPx окна, от левого верхнего пикселя. Пиксель с индексом `i` покрывает полуинтервал `[i, i+1)`. Край бокса при этом остаётся включительным индексом пикселя (§3.2).

Вершина пути — граница пикселя, не индекс. Пиксельный бокс `x1..=x2` — это путь с вершинами `x1` и `x2 + 1` по этой оси: путь с вершинами `(0,0)` и `(9,9)` покрывает 9×9 пикселей, а пиксельный бокс `0..=9` — путь с вершинами `(0,0)` и `(10,10)`.

`Move(x, y)`, `Line(x, y)`, `Quad(cx, cy, x, y)`, `Cubic(c0x, c0y, c1x, c1y, x, y)`, `Close`.

`FillRule::NonZero` и `FillRule::EvenOdd`.

Кривая дробится, пока отклонение контрольной точки от хорды больше четверти пикселя. В этой проверке `d`, `dx`, `dy` и `cross` — в 16.16 sPx (ниже); 1 sPx — это 65536 единиц, порог `d ≤ 1/4` — 16384 единиц. Сравнение без корня. Произведение считается в `i128`, где `cross² * 16` помещается. Предел координаты 1_048_576 не снижается.

```
cross² * 16 ≤ dx² + dy²
```

`cross` — модуль векторного произведения хорды и вектора на контрольную точку. Для кубика проверяются обе контрольные точки. Квадратичная кривая `(0,0) → (3,4)` с контролем `(1,1)` даёт `cross² * 16 = 16` и `dx² + dy² = 25`: порог не пробит, дробления нет. Контроль `(1,0)` на той же хорде даёт `256` против `25`: кривая дробится.

Разрез — де Кастельжо при `t = 1/2`, тем же правилом на каждой половине, пока неравенство не выполнено. Для квадратичной кривой середины отрезков — `(P0 + P1) / 2` и `(P1 + P2) / 2`, новая вершина — их середина. Разрез считается в целых с 16 дробными битами (16.16): деление на 2 — сдвиг вправо с округлением к ближайшему, ничья от нуля; произведение `cross² * 16` в этих единицах помещается в `i128` при пределе координаты 1_048_576. Точность 1/65536 sPx много меньше порога 1/4 sPx. В момент входа в ребро координата переводится в 8.8 к ближайшему, ничья от нуля: середина шага 1/256 уходит от нуля. `1/2` даёт 128, `1/512` даёт 1. `Quad (0,0) → (3,4)` с контролем `(1,0)` за первый разрез даёт точки `(1/2, 0)`, `(2, 2)` и вершину `(5/4, 1)`.

Растеризация — сканлайн. Фиксированная точка 8.8 (256 = 1 sPx) — у рёбер сканлайна, у покрытия и у `limit_q8` митры (§8.4). К порогу дробления она не применяется. **Покрытие пикселя — площадь пересечения залитой области с пикселем**, доля площади пикселя `0..=1`. Залитая область — множество точек пикселя, где правило заливки истинно для winding number ломаной после дробления: `NonZero` — winding ≠ 0, `EvenOdd` — нечётный winding. Площадь считается по правилу заливки, а не суммой знаковых площадей. Для каждой строки пикселей пересечения рёбер с нижней и верхней границей строки упорядочиваются по `x`; если два ребра пересекаются внутри строки, строка дополнительно делится по `y` в точке пересечения. Внутри каждого подынтервала порядок рёбер по `x` постоянен, и между соседними пересечениями winding number постоянен. Каждый интервал, где правило заливки истинно, интегрируется по `y` как трапеция между `x(y = row)` и `x(y = row + 1)`; сумма трапеций по интервалам и есть площадь пикселя. Знаковая площадь отдельных рёбер без разбиения на интервалы не допускается. Сканлайн обязан интегрировать площадь по `y` трапециями; выборка в одной точке (`y = row + 1/2`) площади не даёт и спецификации не соответствует. Площадь `A` в `0.1.0` считается аналитически в `f64` (входы рёбер — целые 8.8) и переводится в целое `cover = round(A * 256)` к ближайшему, ничья от нуля. Аккумулятор `i128` — после `0.1.0` (решение №61). `A = 1/2` даёт `cover = 128`; `A = 1/512` даёт `cover = 1`. Альфа из покрытия:

```
alpha = (cover * 255 + 128) / 256
```

`cover = 256` даёт 255. `cover = 128` даёт 128. Итоговая альфа пикселя — `(cover_alpha * color.a + 127) / 255`. При `color.a = 255` остаётся `cover_alpha`. Покрытие 256 и `color.a = 128` дают альфу 128. Смешение каналов с приёмником при итоговой альфе меньше 255 — по §6 в линейном свете; на прозрачном приёмнике результат равен premul источника.

Ось-параллельный путь с вершинами `(x1, y1)` и `(x2 + 1, y2 + 1)` покрывает те же пиксели, что `FillRect` бокса `x1..=x2, y1..=y2`: полуинтервалы `[x1, x2 + 1) × [y1, y2 + 1)`. У ось-параллельного пути с целыми вершинами при непрозрачной заливке (`color.a = 255`) альфа только 0 и 255. Наклон и кривая могут давать промежуточную альфу. Это покрытие внутри пикселя; позиция объекта по-прежнему целая.

### 8.4. Обводка

`Stroke::width_q8` — перпендикулярная ширина полосы в 1/256 sPx: `256` — 1 sPx, `205` — 0.8, `179` — 0.7. Ширина не округляется до пикселя: покрытие — площадь полосы `width_q8 / 256`, квант остаётся только у координат (8.8). `Stroke::px(width, align)` — короткая форма для целой ширины (`width_q8 = width · 256`, `Miter { limit_q8: 1024 }`, `Cap::Butt`, `Peak::Light`), `Stroke::q8(width_q8, align)` — для готового значения. `width_q8 = 0` — `BadStroke` во всех носителях: `StrokePath`, `StrokeRoundRect`, `Vector`, `Box { stroke }` и `Measure`. Верхний предел прежний — `u32` поля; слишком большая ширина упирается в `Overflow` координаты вершины.

`StrokeAlign` — `Inside`, `Outside`, `Center`.

- `Inside` — обводка внутрь замкнутого контура на `width_q8 / 256` sPx.
- `Outside` — наружу на `width_q8 / 256` sPx.
- `Center` — симметрично контуру, по половине ширины на каждую сторону. При чётном `width_q8` половины равны; при нечётном левая берёт `ceil`, правая `floor`: `half_left = width_q8 − ⌊width_q8 / 2⌋`, `half_right = ⌊width_q8 / 2⌋`. Запрошенные половины в сумме дают ровно `width_q8`, поэтому площадь полосы сохраняется, а середина смещается не более чем на 1/512 sPx; нормали каждой стороны округляются в 8.8 независимо, отклонение реальной ширины — не более 2/256 sPx. При `width_q8 = 256` это две полукромки по 128, при `512` — две полные строки по 255. `Center` всегда идёт через coverage-растеризатор, даже когда все сегменты ось-параллельны.
- Открытый контур допустим только для `Center`; `Inside` и `Outside` по незамкнутому контуру — `BadPath`.

Ось-параллельная обводка `Inside`/`Outside` бинарная. Контур пиксельного бокса `0..=9` — вершины `0` и `10`. `Inside`, ширина 1: непрозрачны ряды `y = 0` и `y = 9`, столбцы `x = 0` и `x = 9`; внутренность `1..=8` пустая; угол пишется один раз. При дробной ширине те же кромки получают покрытие `width_q8 / 256` вместо целого пикселя.

`Join::Miter { limit_q8 }` — порог в 8.8, по умолчанию 4.0 = 1024. Длина митры — расстояние в sPx от вершины пути до острия. У `Inside`/`Outside` остриё отстоит на полную ширину; у `Center` — на половину, поэтому в сравнении расстояние удваивается: `k · d ≤ (limit_q8 / 256) · (width_q8 / 256)`, где `k` — 2 у `Center` и 1 у остальных, `d` — расстояние в sPx. Сравнение без корня, в `u128`: `(k · d_q8)² · 256² ≤ (limit_q8 · width_q8)²`, где `d_q8` — расстояние в 8.8; произведения на входах `u32` в диапазон `u128` помещаются. Больший квадрат длины — bevel, равенство остаётся митрой. При ширине 1 и `limit_q8 = 1024` порог равен 4: остриё на 4 sPx от вершины остаётся митрой, на 5 sPx становится bevel. `Join::Bevel`. `Join::Round` и `Cap::Round` — дуга радиуса `width_q8 / 256` у `Inside`/`Outside` и `width_q8 / 512` у `Center`, с центром в вершине пути, от одной стороны обводки до другой. Концы лежат на этой окружности. У стыка это внешние углы двух примыкающих сторон. У `Cap::Round` это внешний угол у конечной вершины и точка на половину ширины дальше вдоль пути. Обход не длиннее половины окружности; разворот в половину идёт по внешнюю сторону обводки. Отдельный `Quad` или `Cubic` не публикуется. Единственная новая вершина разреза — точка окружности на биссектрисе угла концов. Она не диадическая, поэтому в ломаную входит уже в 8.8: к ближайшему, ничья от нуля. Эта вершина стоит в неравенстве §8.3 на месте контрольной точки; неравенство считается в sPx, произведение в `i128`. Пока оно не выполнено, дуга делится этой вершиной на две, и то же правило применяется к каждой половине. Таблицы float нет. Четверть радиуса 1 от `(1, 0)` до `(0, 1)` даёт один разрез `(√2/2, √2/2)`, на ребре `181, 181`. Обе половины порог не пробивают: ломаная 8.8 — `(256, 0)`, `(181, 181)`, `(0, 256)`. `Cap::Butt` кончается на вершине. `Cap::Square` выступает за конечную вершину на половину ширины у `Center` и на полную ширину у `Inside`/`Outside`; при нечётном `width_q8` выступ берёт `ceil` половины. Незамкнутый горизонтальный путь по пиксельному боксу `0..=9` (вершины `0` и `10`), ширина 1, `Square`: занят и пиксель `x = 10`. `Butt` его не красит.

Наклонный штрих идёт общим растеризатором покрытия. Его альфа на кромке может быть промежуточной.

`Stroke::peak` — опция, не закон. `Peak::Light` (по умолчанию) оставляет точный свет геометрии. `Peak::Nominal` нормирует весь штрих так, что его максимальное покрытие становится 256: `peak` — максимум покрытия `0..=256` по полной геометрии до клипа, `coverage' = min(256, (coverage · 256 + peak / 2) / peak)`, при `peak = 0` — no-op. Нормировка применяется ко всем носителям `Stroke`: `StrokePath`, `StrokeRoundRect`, `Vector`, `Box { stroke }`; `Measure` игнорирует `peak`. При `width_q8 = 256` нормированный пик совпадает с номинальной шириной 1 sPx; при дробной ширине он осознанно выше номинала — так калиброван крестик Luna: полоса `width_q8 = 179` на 45° имеет максимум покрытия ≈ 0.746, и `Nominal` поднимает его до 1. Для 45°, `w = 1`, `Peak::Light` пик ≈ 0.914, цена `Nominal` по свету ≈ +9.4 %.

Пустой путь, путь без `Move`, незакрытая фигура для `Inside` — `BadPath`. `Line`, `Quad`, `Cubic` или `Close` сразу после `Close`, без нового `Move`, — `BadPath`. Заливка (`FillPath` и `fill` сущности) перед `NonZero` и `EvenOdd` замыкает каждый подпуть без `Close` тем же ребром, что дал бы `Close`. Обводка это ребро не добавляет: незакрытый контур для `Inside` и `Outside` — `BadPath`; открытая полоса существует только у `Center`.

### 8.5. Скругление

`Radius { Edge(edge) | Percent(u8) }` — скругление бокса. `Edge` читается по грамматике §3.2–§3.3, но **не подчиняется `on_grid` сущности**: `Grid` — клетки 5/15 плюс sPx-добавка, `Pixel` — голое целое sPx. Отрицательный радиус — `BadRadius`. `Percent` — доля меньшей стороны бокса, `0..=50`; больше 50 — `BadRadius`. Результат `Percent` и любого `Edge` округляется до целых sPx и зажимается в `min(width, height) / 2`: `Percent(50)` на квадрате — круг, на прямоугольнике — капсула.

Пиксельный бокс `x1..=x2, y1..=y2` — это геометрия `[x1, x2 + 1) × [y1, y2 + 1)`. Скруглённая форма — прямоугольник с четырьмя дугами радиуса `r`, центры дуг — `(x1 + r, y1 + r)`, `(x2 + 1 − r, y1 + r)`, `(x1 + r, y2 + 1 − r)`, `(x2 + 1 − r, y2 + 1 − r)`. Радиус 0 или отсутствие радиуса — форма без скругления.

Покрытие пикселя — площадь пересечения формы с пикселем, `cover = round(A * 256)`, alpha — по §8.3. Прямые части (средняя полоса и полосы между углами) покрываются целиком; покрытие считается только в четырёх углах `r × r`. Поэтому стоимость скругления растёт с `r²`, а не с площадью бокса.

Применение делится на две роли. `fill_shape` заливает форму и применяет `Blend` к самой форме; `mask_corners` стирает углы вне формы через `DstOut` и оставляет контент внутри.

- `FillRect { radius }`, `Flat` и `Box` — `fill_shape`: заливка скруглённой формы (и обводка `Box` по её контуру). `FillRect { radius, blend: DstOut }` стирает форму, а не её углы.
- `Photo`, `Glyph` и `Blit` — `mask_corners`: контент рисуется в свой бокс, затем углы вне формы стираются `Blend::DstOut` с тем же покрытием. Бокс формы — `dest` блита или бокс сущности.
- `Vector` с `radius` — `BadRadius`.

Маска `DstOut` стирает уже нарисованное под ней, поэтому радиус у `Photo`/`Glyph`/`Blit` применяется сразу после своего контента и до дерева `End`.

## 9. Соседство с декодером

Ядро декодер не вызывает и по имени в коде не ссылается. Хост может принести уже собранные семплы чужого декодера, если они лежат так:

| Буфер хоста | Загрузка FGCE |
|-------------|---------------|
| 8-bit, по строкам, RGB, 3 байта на пиксель | `Rgb8`, `Straight` |
| 8-bit, по строкам, RGBA, 4 байта, прямая альфа | `Rgba8`, `Straight` |
| плоский YUV | сначала в RGBA8 у хоста, затем `Upload` |

Профиль ICC, магия контейнера и версия битстрима в FGCE не входят. Хост решает их до `Upload`.

Значение пересекает границу готовым: хост передаёт декодированные байты в `Upload`, а не вызывает чужой крейт.

## 10. Хост

Хост обязан показать буфер `End` блоком `d×d` на каждый sPx, без фильтра, с учётом `stride`. При `d = 1` это показ 1:1. Повторная выборка с дробным коэффициентом снова создаёт дробный пиксель.

Хост, которому нужна прямая альфа (canvas 2D `putImageData`), берёт `ReadPixels` с `Straight` и принимает копию. Хост, который умеет premul (GPU-текстура), берёт `End` и копии не делает.

Один кадр:

1. `DefineReference` / `UseReference`, если сменилась среда.
2. `Lattice` и `EdgePx` — только если хосту нужна справка. Раскладка кадра считается внутри `place`.
3. `Begin` с размером окна в sPx.
4. `Upload` новых изображений; старые `id` не грузить снова.
5. `Measure` — если нужен бокс `Vector` до `Entity`; затем `Entity`, `Group`, `Arbitrary`, `Place` или `Show`.
6. `End`: ядро рисует дерево и отдаёт кадр. Хост показывает его блоком `d×d`.

Между кадрами слой жеста вызывает `Snapshot` и по нему считает попадание. В шаги кадра этот запрос не входит.

`k` и `d` выбирает хост и записывает их в эталон. Ядро список «какой `k` влезает в окно» не содержит. Порог клеток на эталоне — единственный внутренний переключатель среды.

FFI и wasm-адаптер в ядро не входят. `wasm32-unknown-unknown` — проверка портируемости ядра, не JS ABI: у крейта нет экспортов, JS не может вызвать `submit` напрямую. wasm-хосту нужен отдельный адаптер (`wasm-bindgen` или C ABI), который копирует `Frame`/`Pixels` через границу; он не становится второй реализацией растра. Адаптер реализован крейтом `crates/fgce-wasm` (C ABI `3`, [`wasm-abi.md`](./wasm-abi.md)) и в поставку ядра не входит: геометрия поверхностей — ответственность хоста. Ядро и его контракт от этого не меняются. Нативный Rust-хост может использовать `End` без копии.

## 11. Оптимизации, которые обязательны

Все пункты сохраняют байты формул §6–§8.

1. Непрозрачный ряд — плотная запись, не SrcOver по пикселю.
2. Совпадающие размеры blit — копирование строки.
3. Ось-параллельные заливка и обводка — прямоугольники `span`, без сканлайна кривой.
4. Альфа 0 не читает назначение. Альфа 255 пишет источник. Покрытие переводится в итоговую альфу по §8.3 до этого выбора, уже после умножения на `color.a`. Полное покрытие 256 даёт альфу 255 только при `color.a = 255`. Покрытие 256 и `color.a = 128` остаётся альфой 128.
5. Изображение живёт в store между кадрами. `Begin` его не трогает и не конвертирует.
6. Буфер кадра живёт, пока размер тот же.
7. Аккумулятор строки и стек клипа не выделяются внутри пиксельного цикла.
8. Паддинг до 64 байт и выравнивание указателя — чтобы широкая запись не рвала строку.
9. Никакого замка, канала и аллокации в `span`.
10. Решётка окна — два целых `count` и два `origin`, без массива клеток.
11. Живой прямоугольник пересчитывается только вместе с поколением списка. Совпавшее поколение этот пересчёт пропускает. `End` после `Begin` пишет пиксели снова.

Отдельный SIMD-модуль с `unsafe` не вводится. Если компилятор не векторизует запись `u128`, это принимается: корректность важнее ручного `unsafe`, а запрет в манифестах продукта уже стоит.

## 14. Отложено

Жест, фокус, порядок обхода и захват указателя — слой над крейтом. Читает он только снимок поставленных боксов: id, id родителя, видимый прямоугольник в sPx, поколение, список в порядке рисования. Попадание точки считает по этому снимку, с конца списка к началу. У сущности поле `align`, у группы, произвольного бокса и окна поле `pin`; это разные поля. Кривую движения считает слой над крейтом: ядро принимает `Show` целым прямоугольником и не хранит `MotionClass`. Каретка и выделение — сущности того же слоя, не объекты ядра. До жеста и фокуса стабильны снимок, `Show` и одна запись канона из целого sPx. Снимок читается запросом `Snapshot`, запись канона — `Place { id, rect }`. Id живёт, пока жива сущность. Живое окно, один эталон, отступ верхнего бокса и родительская связь к этому моменту уже работают. Грамматика краёв при любом `k`, выбор эталона по порогу, жизнь узла и формулы `align` и `pin` закрыты для `0.1.0` вместе с §12. Поля снимка от этих формул не зависят: `id`, родитель, видимый `Rect`, поколение снимка.

Следующие вещи не уточняются этой версией документа и не входят в `0.2.0`: частичный кадр без очистки, поворот, градиент, клип-путь, шейпинг, GPU-растеризатор внутри ядра, FFI-крейт, адаптер в составе ядра (адаптер `fgce-wasm` поставляется отдельным крейтом), масштабирование `Photo`/`Glyph` в дереве, эллиптические радиусы, кривая на изменение окна. Любая из них — отдельное изменение спеки и, если меняется `Request`, смена minor при `0.y` или major при `1.y`. Дробная ширина штриха входит в `0.2.0` как `Stroke::width_q8` (§8.4).
