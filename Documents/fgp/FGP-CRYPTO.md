# FGP-CRYPTO — криптографический слой FGP/FPP

**Status:** Draft (RFC)
**Version:** 0.1
**Date:** 2026-07-14

Компаньоны: [`FGP.md`](./FGP.md) (v0.6 — механика, которую этот слой обслуживает), [`FPP.md`](../fpp/FPP.md) (v0.3 — personhood; здесь фиксируются его примитивы), [`FGP-THREATS.md`](./FGP-THREATS.md) (v0.5 — V-11 владеет операционной стороной этого документа). Нормативно: выбор примитивов, протокольные конструкции, форматы детерминированной арифметики, реестр доменных меток, требования к реализации и аудиту. История ревью — Приложение B (B.1: адверсариальный разбор черновика до фиксации 0.1, 10 находок).

---

## Overview

FGP обещает свойства («голос непродаваем», «журнал непереписываем», «маски несвязываемы»), которые держатся не на правилах, а на криптографии. Этот документ превращает обещания в перечень конкретных механизмов и говорит честно, **какое доверие остаётся** в каждом.

Дизайн-принципы (в порядке приоритета):

1. **Стандартизованное вместо самодельного.** Где существует RFC/стандарт с зрелыми Rust-реализациями — берётся он (Ed25519, HPKE, VOPRF, ECVRF, FROST). Собственные конструкции — только там, где стандарта нет, и с внешним ревью.
2. **Прозрачное вместо trusted setup.** Ни один механизм не должен зависеть от «церемонии, где кто-то честно удалил toxic waste». ZK-система выбирается из transparent-семейства; Bulletproofs и sigma-протоколы setup не требуют вовсе.
3. **Скучное вместо мощного.** Гомоморфная агрегация + sigma-доказательства покрывают тэлли без универсальных ZK-циркуитов; универсальный ZK остаётся только там, где без него нельзя (membership-с-nullifier, предикаты уровня).
4. **Одно ядро.** Всё реализуется в `flora-governance-crypto` (native + wasm32, FGP §8.1); сервер и клиент проверяют одним кодом. Монокультурная оговорка — THREATS V-11.
5. **Детерминизм.** Consensus-critical пути — целочисленные/фикс-пойнт (§10); спецификация арифметики — это test vectors, а не формулы на вещественных числах.
6. **PQ-хеджирование, не PQ-паника.** Хеш-структуры уже пост-квантово стойки; подписи мигрируемы; шифртексты бюллетеней уничтожаются (окно экспозиции ограничено); что PQ-слабо — названо (§11).

## Goals & Non-Goals

**Goals:** реестр примитивов и доменных меток; конструкции: commitment-набор и nullifier'ы, анонимные маски с отрицаемостью, анонимное расходование кредитов, бюллетени и проверяемый тэлли, приватные выборки, VRF-жеребьёвки, threshold-OPRF дедуп, журнал с косайнингом; профили зрелости P0/P1/P2 с гейтами; фикс-пойнт форматы; требования к реализации, аудиту и test vectors.

**Non-Goals:** криптография FSCP (задана в [`FSCP.md`](../fscp/FSCP.md); franking — target-расширение там же); юридические аттестации; конкретные размеры циркуитов и бенчмарки (появятся с реализацией); образовательный материал (см. FGP-GUIDE).

## Architecture Position

Реализация — крейт `flora-governance-crypto` (native + wasm32 для `@flora/client-core`), персональные артефакты (ключи, nullifier-деривации на устройстве) — клиентские SDK на том же ядре. Данные — по владельцам: commitment-набор и ревокации у Verification (FPP §10.2), бюллетени/журнал/леджер у Governance. Инварианты workspace: `unsafe_code = "forbid"`, RustCrypto/dalek-семейство без C-зависимостей, `cargo deny`/`audit`/`vet`, пиновка тулчейна и `Cargo.lock` (THREATS V-11).

## 1. Реестр примитивов

| Назначение | Примитив | Стандарт / реализация | Профиль |
| --- | --- | --- | --- |
| Хеш общего назначения, журнал, Merkle | BLAKE3 (256-бит) | `blake3` | P0+ |
| Подписи (гражданские ключи, витнессы, аттестации, релизы) | Ed25519 над DS-таггированным сообщением | RFC 8032; `ed25519-dalek` | P0+ |
| Группа для протоколов | Ristretto255 | `curve25519-dalek` | P1+ |
| KEM/шифрование доставки (креденшалы выборки, уведомления) | HPKE: X25519-HKDF-SHA256 + ChaCha20-Poly1305 | RFC 9180 | P1+ |
| VRF (жеребьёвки, назначение пар/аттесторов, самовыборка) | ECVRF-EDWARDS25519-SHA512-TAI | RFC 9381 | P1+ |
| Анонимные токены (кредиты, маски P1) | VOPRF / POPRF, ristretto255-SHA-512 | RFC 9497 | P1 |
| Пороговые подписи (косайны журнала, EC-действия) | FROST(Ed25519/Ristretto255) | RFC 9591; `frost-*` | P1+ |
| Гомоморфные бюллетени | экспоненциальный ElGamal над Ristretto255 | классика; ядро своё | P2 |
| Пороговый ключ комитета | Pedersen DKG + Feldman VSS, complaint-раунды | классика; ядро своё + внешнее ревью | P2 |
| Корректность частичной расшифровки | Chaum-Pedersen sigma-доказательства (батчево) | классика | P2 |
| Well-formedness бюллетеня (Σv² ≤ B, диапазоны) | Bulletproofs (R1CS/inner-product) | `bulletproofs` (dalek) | P2 |
| In-circuit хеш (membership, предикаты уровня) | Poseidon2 над полем выбранной ZK-системы | параметры — внешнее ревью | P2 |
| Универсальный ZK (membership + range «level ≥ L») | transparent, hash-based (STARK-класс); шорт-лист: Plonky3-семейство, RISC-Zero-класс zkVM, Winterfell-класс | финальный выбор — гейт v2, внешний аудит | P2 |
| Threshold-OPRF (дедуп документов V3) | t-of-n эволюция RFC 9497 | молодой примитив — гейт P2 + fallback §7 | P2 |

Правило эволюции: замена примитива = R3 (меняет проверяемость исторических артефактов); добавление профиля = R2.

### 1.1. Реестр доменных меток (domain separation)

Каждая подпись/хеш/PRF — над сообщением с префиксом `flora/<область>/v1/<операция>`. Стартовый реестр: `civic/sign`, `civic/commit`, `civic/id`, `nullifier/nk`, `nullifier/ctx`, `mask/register`, `mask/dv-sim`, `token/credit`, `ballot/encrypt`, `ballot/overwrite`, `tally/partial-dec`, `vrf/sortition`, `vrf/ceremony-pair`, `vrf/attestor-assign`, `vrf/self-select`, `log/leaf`, `log/node`, `log/sth`, `log/anchor`, `oprf/doc-dedup`, `treasury/ledger`, `device/tag` (эпохальный тег устройства, FPP-SIGNALS NS-D2; деривация — `fpp-crypto`), `sortition/seed`, `sortition/rank` (публичные жеребьёвки §6), `commit-reveal/commit` (скрытые агрегаты FGP §3.4), `bridging/init` (инициализация факторизации §10). Полный реестр живёт в `flora-governance-crypto` (`src/ds.rs`) и в test vectors; коллизия меток = инцидент V-11. Байтовое представление меток фиксируется вектором (правило FSCP «байт-в-байт»).

## 2. Идентичность, commitments, nullifier'ы

### 2.1. Ключи и деривации

```
sk_civic, pk_civic     Ed25519, генерируются на устройстве (FPP §1.1)
nk                     nullifier-ключ: BLAKE3-KDF(sk_civic, "flora/nullifier/v1/nk")
commitment             P1: BLAKE3(pk_civic || salt_dev);  P2: Poseidon2(pk_civic, salt_dev)
civic_id               BLAKE3(commitment, "flora/civic/v1/id") — стабильный тег (FPP §10.0)
nullifier(ctx)         P1: выводится токенами (§4);  P2: Poseidon2(nk, ctx_id) в циркуите
```

`ctx_id` — из реестра контекстов: `(тип_окна, id_объекта, эпоха)`; реестр нормативен, добавление контекста — R2 (каждый новый контекст — новая ось связываемости).

### 2.2. Набор аттестованных и ревокации

Append-only Merkle-набор commitments (владелец — Verification): P1 — BLAKE3-дерево, P2 — Poseidon2-дерево (для membership-циркуитов) с BLAKE3-кросс-обязательством корня в журнале. Ревокация — отдельный список; пруфы валидны против пары корней `(attestation_root, revocation_head)` конкретной эпохи; после смены эпохи старые пруфы не принимаются (FPP §1.2).

### 2.3. Два пути анонимности (честная лестница доверия)

| | **P1 — слепые токены** | **P2 — ZK-membership** |
| --- | --- | --- |
| Механизм | Verification слепо подписывает эпохальные токены каждому активному `civic_id` (VOPRF/blind-issuance) | пользователь доказывает в ZK: «мой commitment в наборе, уровень ≥ L, nullifier для ctx корректен» |
| Несвязываемость | к выпуску — криптографическая; выпускающий не видит, где токен потрачен | полная; выпускающего нет |
| Остаточное доверие | **выпускающий может перевыпустить** → закрыто публичной бухгалтерией выпуска (§4.1) | доверие только к math + аудиту циркуита |
| Зрелость | RFC 9497, продакшн-класс (Privacy Pass) | молодой инструментарий — гейт v2 |

P1 сознательно принимает выпускающего как доверенную точку (та же точка, что связь «аккаунт ↔ commitment», FPP §9.3) — потому что P1 отпирает только R0/R1 (низкие ставки), а бухгалтерия выпуска делает злоупотребление наблюдаемым. P2 убирает точку до включения R2/R3.

## 3. Маски делиберации и отрицаемое авторство

- **Регистрация маски** (одна на `(civic_id, proposal)`): P1 — предъявление proposal-токена (уникальность = ключ токена); P2 — ZK-пруф с nullifier'ом `mask/register`. Тир-предикат («тир ≥ T») — range-часть того же пруфа.
- **Отрицаемость (FGP §3.1):** валидация происходит **в момент подачи** протоколом; в журнал пишется только факт «маска валидна». Вместе с созданием предложения публикуется **симуляционный ключ** `mask/dv-sim`: любой желающий может изготовить неотличимый «пруф авторства» любого узла. Экспортированный артефакт ничего не доказывает по построению — публичные заявления авторства остаются cheap talk. Протокол отличает реальные маски от симулированных только внутренним состоянием сессии подачи, которое наружу не выходит.
- Подпись узлов — эфемерным ключом маски (Ed25519, `mask/register` связывает его с пруфом); ключ уничтожается после закрытия предложения.

## 4. Кредиты: анонимное расходование

### 4.1. P1 — эпохальные токены

- В начале эпохи Verification выпускает каждому активному V1+ `B = 100` слепых единичных токенов с меткой эпохи (`token/credit`, POPRF с public input = epoch_id). Голос силой `v` тратит `v²` токенов (FGP §4.4); залоги и ставки — те же токены.
- **Бухгалтерия выпуска (закрытие доверия к выпускающему):** в журнал пишется `issued_count(epoch)`; он обязан равняться `|active V1+|` из аттестационного набора той же эпохи × B. Каждый пользователь клиентски проверяет получение ровно B; расхождение счётчиков или двойная трата токена = событие V-11 с деградацией (FGP §7.3).
- Токены **не переживают эпоху** (метка эпохи в PRF-входе — стокпайлинг исключён криптографически, не правилом).
- Признано: паттерн трат внутри одного окна образует связываемый псевдоним окна (не личности). Для R0/R1-приоритизации это приемлемо; скрытые агрегаты (FGP §3.4) остаются; полная receipt-freeness ставок — P2.

### 4.2. P2 — ZK-spend

Баланс-обязательство на `civic_id`; трата = ZK-пруф «баланс ≥ v², nullifier траты корректен» без раскрытия истории. Убирает и псевдоним окна.

## 5. Бюллетени и проверяемый тэлли (P2, binding R2/R3)

Конструкция класса «Helios + MACI-свойства», без универсального ZK в самом тэлли:

1. **Ключ окна:** комитет 5-of-9 (FGP §4.6) проводит Pedersen DKG с Feldman-VSS и complaint-раундом; провал → пересбор комитета (окно не открывается с подозрительным ключом). Публичный ключ окна — в журнале.
2. **Бюллетень:** по каждому варианту — exp-ElGamal шифртекст голоса; Bulletproof-пруф well-formedness: значения в допустимом диапазоне, Σv² ≤ B (для QV-окон), один бюллетень = один nullifier.
3. **Перезапись (coercion override):** повторная подача с тем же nullifier'ом и большим счётчиком заменяет бюллетень (last-write-wins). Счётчик подписан ключом маски окна; сервер обязан включить в журнал **все** поданные версии (inclusion-пруфы), финальный набор «последних» коммитится в журнал **до** начала расшифровки — тихое отбрасывание перезаписи ловится клиентом по журналу.
4. **Агрегация до расшифровки:** шифртексты суммируются гомоморфно; комитет расшифровывает **только агрегат**. Частичная расшифровка — с Chaum-Pedersen пруфом корректности каждой доли; любой транскрипт частичной расшифровки над не-агрегатным шифртекстом — криптографическое доказательство злоупотребления (журналируется, слэшинг, V-11). Сговор ≥ 5 офф-протокольно — признанный остаточный риск (THREATS V-11).
5. **Публикация:** агрегат + пруфы (Chaum-Pedersen, батч Bulletproofs, inclusion-корни) — всё проверяется в `@flora/client-core`. **k-анонимность страт:** агрегаты страты публикуются только при ≥ `k_min` бюллетеней в страте, иначе страты сливаются по заранее объявленному правилу (малые страты не должны деанонимизироваться агрегатом).
6. **Уничтожение шифртекстов** после окна оспаривания 30 дней (FGP §4.6): PQ-экспозиция ограничена окном.
7. Conviction-обязательства (FGP §4.8) и грант-сигналы (FGP §10.2) — та же конструкция с медленным темпом окон.

**Верификационная стоимость:** батч-верификация Bulletproofs; клиенты проверяют пруфы асинхронно и допускается **выборочная** проверка (каждый клиент — случайное подмножество + все witness-узлы проверяют всё): цель — общее покрытие, а не 100 % на каждом устройстве (бюджеты — Приложение A).

## 6. Жеребьёвки и публичная случайность

- **Сид:** `seed = BLAKE3(sth_T || external_anchor_T)` — head журнала на заранее объявленный момент T (после закрытия деклараций/реестров — анти-grinding, FPP §3.1) + внешний якорь (публичный маяк случайности / хеш внешнего журнала; манипуляция требует контроля обеих сторон).
- **Публичные жеребьёвки** (пары церемоний, назначение аттесторов, порядок очередей): детерминированная выборка из commitment-реестра по сиду — пересчитываема любым, VRF-ключей не требует.
- **Приватные выборки референдумов (FGP §5.6):** самовыборка Algorand-класса — каждый член реестра локально вычисляет `ECVRF(sk, seed || stratum)`; выбран ⇔ выход < порога страты. Состав не публикуется и **никому не известен** (даже серверу — сильнее исходного требования); голосуя, выбранный доказывает «мой VRF-выход ниже порога» тем же пруфом, что и membership.
- **Неответившие** (следствие приватности состава: индивидуальная замена невозможна): порог страты ставится с **оверсэмплингом** `1/expected_response`; фактический отклик страты сверяется с биномиальным ожиданием — статзначимый недобор триггерит tripwire «аномалия отклика страты» (FGP §7.2). Резерв страты из FGP §5.6 реализуется как второй VRF-порог, активируемый продлением окна. Жюри и панели (состав известен по необходимости — люди совещаются) используют публичную жеребьёвку по приватному пулу с журналированием обоснования выборки.

## 7. Threshold-OPRF дедуп документов (V3)

- Цель (FPP §5.1): глобальный дедуп-тег документа, невычислимый одним участником. Конструкция: t-of-n POPRF — ключ расщеплён между независимыми держателями (не аттесторами!); аттестор шлёт блайндированные нормализованные поля, получает тег после t частичных вычислений.
- Держатели ключа: организации класса витнессов, ≥ 3 юрисдикции; ротация ключа — Proactive Secret Sharing ежегодно.
- **Честно о зрелости:** threshold-OPRF моложе остального реестра — гейт P2 с внешним ревью. **Fallback до готовности:** per-attestor соль (схема FPP v0.1) + VRF-назначение аттесторов; кросс-аттесторная слепая зона признана и компенсируется назначением (нельзя выбрать «удобную пару») и канареечными пробами.

## 8. Журнал прозрачности

- CT-класс: append-only Merkle-лог (BLAKE3), периодические STH (`log/sth`), inclusion- и consistency-пруфы; клиент отвергает журнал без ≥ 3 валидных витнесс-косайнов STH (FROST-агрегат или множество Ed25519 — формат в векторах).
- Витнессы хранят полные реплики; **внешнее якорение** — STH в независимые носители по расписанию (`log/anchor`); split-view = криптографическое событие уровня 3 (THREATS §6.2).
- Все артефакты этого документа (корни наборов, ключи окон, агрегаты, пруфы, бухгалтерия токенов, леджер казны) — листья журнала: единая точка проверяемости.

---

## 9. Комитетные протоколы

- **DKG (ключи окон, OPRF-пул):** Pedersen-DKG, Feldman-VSS, complaint-раунд; любые жалобы → пересбор с новой сортицией (окно = задержка, не результат — FGP §4.6). Доли — в HSM/секьюр-энклейве где доступно; zeroize после окна.
- **FROST-косайны:** витнессы (STH), EC-действия 4-of-7 (FGP §5.9) — стандартные FROST-сессии, nonce-гигиена по RFC 9591.
- Комитетные транскрипты (без секретов) — в журнал: DKG-события публично воспроизводимы.

## 10. Детерминированная арифметика (нормативно)

- Формат: **Q32.32** со знаком (i64; промежуточные — i128); переполнение = saturate + событие телеметрии (не паника и не wrap).
- Округление: **round-half-even** во всех делениях/сдвигах.
- `exp2/log2` (репутация, затухания, conviction, насыщение делегаций): таблица 256 узлов + линейная интерполяция в Q32.32; таблицы — константы ядра, зафиксированы в test vectors. Формулы FGP §4 на вещественных числах — **пояснение семантики; нормативна аппроксимация из векторов** (изменение таблиц = R3, FGP Приложение A).
- Итеративные алгоритмы (bridging-факторизация §6.2 L3, корреляционный дисконт §4.7): фиксированное число итераций, фиксированный порядок обхода (по возрастанию id), фиксированная инициализация из сида окна — никакой зависимости от порядка прибытия данных.
- Property-тесты паритета native ↔ wasm32 на одних векторах — CI-гейт (FGP §8.4).

## 11. Жизненный цикл ключей и PQ

- Гражданские ключи: генерация и хранение на устройстве (secure enclave где есть); zeroize (`zeroize` crate) для всех секретов ядра; ротация civic-ключа = FPP §6 (восстановление).
- Серверные/комитетные ключи: эпохальные, DKG на окно, PSS-ротация OPRF-пула, не переживают назначение.
- **PQ-статус по слоям, честно:** журнал/Merkle/BLAKE3 — стойко; Ed25519-подписи — мигрируемы (двойная подпись Ed25519+ML-DSA как target миграции, отдельный RFC при созревании стека); бюллетени — экспозиция ограничена окном (шифртексты уничтожаются, §5.6); VOPRF/ECVRF/Ristretto-протоколы — **PQ-слабы, замены пока нет**: harvest-now-decrypt-later здесь означает будущую деанонимизацию паттернов трат P1-эпох — ещё один довод довести P2 (ZK-spend) до продакшна. Исследовательский трек — THREATS §7.

## 12. Требования к реализации, аудиту, векторам

- Ядро: `flora-governance-crypto`; только константное время для секретных путей (dalek-инварианты), `unsafe_code = "forbid"`, без C-зависимостей; version-pin всех криптокрейтов; `cargo deny`/`audit`/`vet`.
- **Гейты аудита:** P1 — внешнее ревью токенов/VRF/журнала + фаззинг форматов; P2 — полный внешний криптоаудит (DKG, тэлли, циркуиты, OPRF) до включения binding R2/R3 (FGP §8.3); каждое изменение циркуита/таблиц — повторный аудит затронутого + новые вектора.
- **Test vectors:** `Documents/test-vectors/governance/` по правилам FSCP-набора (base64url без padding, `protocolVersion`, негативы отдельными файлами, consumer-тесты обязательны): деривации (`nk`, `civic_id`, nullifier'ы), DS-метки байт-в-байт, VRF-выходы и самовыборка, токены (issue/spend/double-spend-negative), транскрипт тэлли (DKG → бюллетени → перезапись → агрегат → частичные расшифровки → пруфы), inclusion/consistency журнала, фикс-пойнт таблицы и краевые случаи (saturate, округление), OPRF-теги. Личностные вектора (церемонии, поручительства) — `Documents/test-vectors/personhood/` (FPP §10.4).
- **Состав P0 (зафиксирован):** 11 файлов — ds-tags, fx-q32, log-merkle, log-sth (STH + витнесс-косайны, правило «≥ 3»), sortition, commit-reveal, fgp-weights, bridging и негативы (merkle / sth / commit-reveal). Consumer-тест — `tests/governance_vectors.rs` крейта; wasm32-сборка ядра — CI-гейт `fgp-wasm`.
