# Перенос C# → Rust: обязательный порядок работы

Нормативный источник — `next-architecture.md` (корень репо). Этот skill — операционный чек-лист; при противоречии прав документ.

## 0) Перед началом любой задачи переноса

1. Прочитай `next-architecture.md` §4 (инварианты) и §5.3 (владение данными).
2. Сверься с таблицей статуса миграции (§6.0): кто владеет модулем сейчас, нет ли freeze-окна.
3. Убедись, что задача — **одна группа эндпоинтов или один инвариант**, не «модуль целиком». Если крупнее — предложи декомпозицию, не начинай.

## 1) Тесты раньше кода (обязательно)

- Сначала зафиксируй эталон: contract fixtures (`tests/Flora.ContractFixtures`, `UPDATE_CONTRACT_FIXTURES=1`) и/или golden-вектора, сгенерированные **из C#-реализации**. Они коммитятся до/вместе с Rust-кодом.
- `Documents/test-vectors/**` и `Artifacts/contract-fixtures/**` руками не редактировать — только регенерация из эталона.
- Rust-код пишется против этих фикстур. Если Rust-тест требует «подправить фикстуру» — это сигнал ошибки в Rust-коде, а не в фикстуре.

## 2) Чек-лист паритета эндпоинта

- **JSON:** camelCase; null-поля сериализуются явно (никаких `skip_serializing_if` на nullable-полях контрактов); GUID lowercase с дефисами; даты ISO 8601 UTC; `nextCursor` — opaque, формат воспроизводится как есть.
- **Статус-коды и тела ошибок** — часть контракта (включая 401/403/404/409/422/426/429).
- **Auth:** JWT HS256, clock skew 1 мин; клеймы как в C#-токене (см. §4.1); анонимные маршруты остаются анонимными.
- **Rate limit:** политика маршрута из §4.5 (fixed window, партиция IP / JWT sub, 429).
- **Идентификаторы:** UUID v7 для новых сущностей; деривации UUID v5 (`DmConversationUuid`, `AgreementPublicKeyId`) — байтовый паритет с `Flora.Shared/UuidV5.cs` и TS.
- **Заголовки:** `X-Flora-Client` (426 при старой версии), корректный `X-Forwarded-For`.
- **БД:** те же таблицы схемы `flora_core`, никаких изменений схемы; `created_at`/`updated_at` проставляются кодом (в C# это делал EF-интерцептор).

## 3) Границы (компилируемые)

- Модуль видит чужие модули **только** через их `*-contracts` crate. Публичные порты — только в contracts.
- `flora-social` — единственное место композиции; `flora-api` не знает о модулях.
- Прогони валидатор границ и линтеры: `cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace`.

## 4) Жёсткие запреты на время миграции

- Не менять C#-код модуля в его freeze-окно (и Rust-код чужого модуля — вне своей задачи).
- Не «улучшать» поведение при переносе: формулы FIRA, тексты ошибок, лимиты — 1:1. Улучшения — отдельной задачей после стабилизации.
- Не трогать публичный HTTP-контракт и схему БД.
- Не вводить второго писателя в таблицы модуля (фоновые воркеры переезжают вместе с HTTP-поверхностью).

## 5) Перед завершением задачи

1. Зелёные: cargo fmt/clippy/test, паритетные тесты на фикстурах, `cargo test` (пока жив C#-хост), `npm run ci` (TS-парсеры — арбитр контракта).
2. Обнови таблицу статуса миграции (§6.0 `next-architecture.md`), если изменилось владение/статус.
3. В описании изменений укажи: какие инварианты §4 задеты, чем доказан паритет (какие фикстуры/вектора), план отката (флип маршрута).
4. Диф должен быть маленьким и читаемым (порядка сотен строк). Если вышло больше — разбей на серию.
