# FPP — Flora Personhood Protocol

**Status:** Draft (RFC)
**Version:** 0.1
**Date:** 2026-07-13

Компаньоны: [`FGP.md`](../fgp/FGP.md) (потребитель аттестаций: §4.1 определяет права уровней) и [`FGP-THREATS.md`](../fgp/FGP-THREATS.md) (V-01 — операционная программа защиты personhood). Нормативная механика уровней V0–V3, церемоний, поручительств, якорей, восстановления, nullifier'ов и замера `C_identity` — **здесь**; FGP на неё ссылается и не дублирует.

---

## Overview

FPP отвечает на один вопрос: **«за этим криптографическим идентификатором стоит ровно один живой человек — и сколько стоит это подделать?»**

Это не KYC и не идентификация. Протокол не устанавливает, *кто* этот человек (имя, возраст, гражданство), — только что он *один* и *живой*. Псевдонимность — норма; сибильность — атака. Разница между ними измеряется деньгами: главный выход протокола — публичный параметр безопасности `C_identity(L)`, эмпирическая цена создания поддельной личности уровня `L`. Пока `C_identity(L) · k > Δp(k) · V_decision`, атака на governance нерентабельна (FGP §4.1.1).

Дизайн-принципы:

- **Стоимость, не невозможность.** Подделку личности нельзя исключить — её можно сделать дорогой, медленной, рискованной и откатываемой (протокол сибил-инцидента FGP §4.1.4). FPP спроектирован переживать удешевление подделки, а не отрицать его.
- **Минимум данных.** Сервер не хранит ни биометрии, ни документов, ни записей церемоний — только факты аттестаций и криптографические артефакты. Чего нет — то нельзя изъять, слить или продать (THREATS V-08).
- **Якорный ресурс — синхронное человеческое время.** GPU дешевеют, документы подделываются, аккаунты продаются; параллельное живое внимание конкретных людей в конкретный момент — ресурс, цена которого для атакующего растёт линейно с числом личностей.
- **Уровень = поддержание, не событие.** Аттестация истекает и деградирует без поддержания; «мёртвые души» вымываются из электората автоматически, без реестров смерти.

## Goals & Non-Goals

**Goals:**

- Нормативные уровни V0–V3: требования, поддержание, деградация, восстановление.
- Nullifier-модель: одна личность = один непереносимый идентификатор на контекст; ZK-предъявление «уровень ≥ L» без раскрытия личности и точного уровня.
- Публичный `C_identity(L)` и воспроизводимая методика его замера.
- Исчерпывающий и минимальный перечень хранимых данных.
- Реализация в модуле Verification (целевой стек — Rust: `flora-verification`) без нарушения границ модулей.

**Non-Goals:**

- Идентификация и compliance-KYC. Расширение FPP до сбора установочных данных затрагивает слой 0 FGP (приватность) — конституционный класс R3.
- Глобальная уникальность за пределами инсталляции Flora (федерация personhood — исследовательский трек, THREATS §7).
- Биометрические базы: протокол не собирает и не хранит биометрию; церемонии построены на взаимной человеческой оценке в реальном времени без записи.
- Права уровней (что открывает V1/V2/V3) — определяет FGP §4.1.2, не этот документ.

## Architecture Position

Владелец — модуль **Verification**. Сегодняшняя реализация (email-коды) — это V0; FPP расширяет модуль до полного personhood-стека. Governance — потребитель через контракт.

Целевой стек — Rust-workspace `Backend/` ([`next-architecture.md`](../../next-architecture.md)): `Backend/crates/modules/flora-verification` + `flora-verification-contracts`. Verification переводится на Rust в **Фазе 2a** миграции; вся реализация FPP пишется **только в Rust после cutover 2a** — двойной реализации personhood не существует ни в один момент времени. До этого FPP-работы ограничены спецификацией, крипто-RFC, test vectors и песочницей.

```
flora-governance ──→ flora-verification-contracts   (trait PersonhoodAttestor, события)
flora-verification ──владеет──> personhood_*        (аттестации, поручительства, церемонии,
                                                     nullifier-реестр, ревокации; flora_core,
                                                     своя история миграций через flora-migrate)
```

Границы: Verification не знает о предложениях и голосованиях (домен Governance); Governance не читает таблиц Verification — только контракт. Социальный граф (Users) в поручительствах не участвует: подписка ≠ поручительство (§4.1).

## 1. Модель идентичности

### 1.1. Ключи

- **Гражданская пара ключей** (Ed25519) генерируется на устройстве пользователя; приватный ключ сервера не покидает устройство никогда.
- Гражданский ключ **криптографически не связан** с identity key FSCP (E2E-переписка) и с социальным профилем: деривации независимы. Единственная связь «аккаунт ↔ commitment» хранится внутри модуля Verification (без неё нельзя выдавать аттестации) и не покидает его: Governance видит только nullifier'ы и ZK-предикаты. Это признанная доверенная точка — см. §9.3.
- Утрата ключей ≠ утрата гражданства: восстановление — §6.

### 1.2. Nullifier

```
commitment = Commit(pk_civic)                  — лист в публичном наборе аттестованных
nullifier(u, ctx) = PRF(sk_civic, ctx)         — деривация на устройстве
```

- `ctx` — контекст: эпоха QV-бюджета, конкретное предложение (маски делиберации FGP §3.1), окно голосования и т.д. Один человек = один nullifier на контекст; связать nullifier'ы разных контекстов без `sk_civic` вычислительно невозможно.
- Verification публикует **корень набора commitments** (аккумулятор/Merkle) и head revocation list. Предъявление: ZK-пруф «я знаю sk для commitment из набора, его уровень ≥ L, вот мой nullifier для ctx» — без раскрытия, какой именно commitment.
- Ревокация: commitment переносится в revocation list; пруфы против устаревшего корня перестают приниматься со следующего окна.

### 1.3. Аттестация

`PersonhoodAttestation { commitment, level, issued_at, expires_at, flags }` — подписанная модулем запись. Потребителям уровень предъявляется только ZK-предикатом «level ≥ L» (точный уровень не раскрывается — требование анонимных множеств FGP §3.1).

## 2. Уровни верификации

Нормативное расширение таблицы FGP §4.1.2 (права уровней — там):

| Уровень | Требования | Поддержание | Деградация |
| --- | --- | --- | --- |
| **V0** | email-код (текущий Verification) | — | — |
| **V1** | V0 + церемония liveness (§3) | 2 церемонии/год (или асинхронный путь §3.3) | 2 пропуска подряд → V0 |
| **V2** | V1 + ≥ 3 живых поручительства V2+ (§4) | поручительства не отозваны; церемонии V1 | < 3 живых рёбер → V1 |
| **V3** | V2 + внешний якорь (§5) | якорь действителен; всё нижележащее | якорь отозван → V2 |

- Лестница монотонна: каждый уровень включает поддержание предыдущих.
- Деградация автоматична, с уведомлением и льготным окном 30 дней (кроме ревокации за подтверждённый фрод — немедленно, FGP §4.1.4).
- «Активный V1+» (пороги Genesis, FGP §9.3) = аттестация уровня ≥ V1 не истекла.

## 3. Церемонии liveness (V1)

### 3.1. Механика

- **Календарь:** цикл — полгода; в цикле ≥ 12 синхронных слотов, распределённых по часовым поясам. Участие — один слот за цикл, ~20–30 минут.
- **Назначение пар:** участник декларирует доступные слоты; финальный слот и пара (или тройка) назначаются VRF из публичного head реестра аттестаций (собственный сид Verification — Governance-журнал не привлекается, границы модулей чисты). Назначение раскрывается участникам в момент старта слота: подготовить таргетированный deepfake конкретного собеседника некогда.
- **Сессия:** realtime-видеозвонок P2P (E2E, без записи; сервер — только сигналинг). Устройства генерируют из общего сида скрипт непредсказуемых взаимных челленджей: жесты, произнесение фраз, реакция на визуальные стимулы, свободный микро-диалог. Стороны взаимно аттестуют «живой человек, челленджи пройдены»; на сервер уходят **только подписанные вердикты и enum-флаги аномалий** — не медиа.
- **Коллизии как механизм:** одновременность — суть защиты. Один человек не может вести две параллельные сессии; `k` личностей в одном окне требуют `k` живых людей одновременно. Назначение слотов протоколом (а не свободный выбор) мешает ферме развести своих людей по разным слотам; концентрация деклараций — телеметрия V-01.
- **Несовпадение вердиктов** (один «живой», другой «нет»/таймаут): пересбор пары в том же окне; повторный fail → флаг + повтор в следующем окне. Уровень падает от **паттерна** фейлов, не от единичного случая.
- **Приватность сессии:** стороны видят лица друг друга (цена метода — признана), но не видят ни аккаунта, ни имени: сессионный псевдоним не связывается с социальным профилем. Вербовка собеседников как канал атаки гасится случайностью пар.

### 3.2. Deepfake-гонка (честно)

Realtime-генерация видео дешевеет. Парный челлендж поднимает цену (согласованная невербальная динамика, латентность, свободный диалог), но не исключает подделку. Следствия для дизайна:

1. V1 — **гражданский базис, не крепость**: открывает равный голос (капы QV — FGP §4.4), не открывает ни веса, ни ролей.
2. Даже идеальный deepfake-пайплайн требует оператора реального времени на каждую сессию — синхронное человеко-время остаётся якорем цены (§8.2: это пол, а не потолок).
3. `C_identity(V1)` замеряется ежеквартально (§7); падение ниже порога класса решений **автоматически** переводит этот класс в advisory (лестница деградации FGP §7.3). Протокол переживает дешёвый deepfake деградацией полномочий, а не отрицанием проблемы.

### 3.3. Асинхронный путь эквивалентной стоимости (доступность)

Для тех, кому синхронные сессии недоступны — часовые пояса, инвалидность, уход за близкими (FGP §4.1.2):

- Серия из ≥ 5 коротких челлендж-задач в **случайные моменты** 30-дневного окна; окно ответа ~1 ч после уведомления (непредсказуемость моментов заменяет одновременность).
- Артефакт задачи проверяется случайно назначенными валидаторами V2+ и **уничтожается ≤ 72 ч**; хранится только вердикт. Это единственное место FPP, где медиа-артефакт временно существует, — цена доступности, отражена в §9.1.
- Плюс 1 дополнительный поручитель V2+ сверх требований уровня.
- Эквивалентность подтверждается рыночным замером (§7) **отдельной строкой**: если асинхронный путь окажется дешевле синхронного — его параметры ужесточаются (R2). Аудит доступности — ежегодный (THREATS, каденции V-01).

## 4. Web-of-trust (V2)

### 4.1. Поручительство

- Поручитель — V2+, стаж ≥ 6 мес. Поручительство — формальный акт «я лично убеждён, что это отдельный живой человек» с материальной ответственностью (слэшинг §4.2); рекомендованный канал убеждения — личная встреча или совместная церемония §3. Подписка/дружба/переписка поручительством **не являются**.
- Набор: ≥ 3 поручителя, попарно из разных Polis-кластеров или географий (кольцу нужны рёбра наружу — самая дорогая часть).
- Кап скорости: поручитель выдаёт ≤ `N_vouch = 8` новых поручительств за эпоху (90 дней) — граф растёт медленно, кольца дорожают во времени.
- Отзыв поручительства («потерял контакт») — в любой момент, без штрафа до инцидента; ребро умирает через grace 30 дней.

### 4.2. Слэшинг

Детерминирован, без усмотрения: подтверждённый сибил (вердикт по FGP §4.1.4) → каждый **действующий** поручитель теряет `q_slash` = 25 % текущей суммарной репутации (min 10 q, пропорционально по доменам) + запрет поручительства 12 мес. Повторный инцидент — ревью собственного статуса V2. Слэшинг не ретроактивен к рёбрам, отозванным ≥ 90 дней до инцидента, — иначе честный отзыв станет невыгодным.

### 4.3. Аналитика графа (приватная)

Рёбра поручительств **непубличны**: публичный граф = карта для таргетинга и деанонимизации. Публикуются агрегаты: распределение степеней, модульность, плотные подграфы, короткие циклы, темпоральные всплески (CUSUM). Доступ к рёбрам — только следственная панель по вердикту (V-01/V-03), с журналированием доступа.

## 5. Внешние якоря (V3)

Два равноправных пути — мультипутёвость сознательна (FGP §4.1.2): документы не должны быть единственной дорогой к V3.

### 5.1. Blind-документная верификация

- Аттесторы — независимые аккредитованные организации/лица; пул ≥ 2 юрисдикций; аккредитация — R2-решение; реаккредитация ежегодно.
- Процедура: пользователь предъявляет документ аттестору (лично или видеосессией); в систему уходит **один бит** («документ гос. образца, соответствует живому предъявителю, ранее мне не предъявлялся») + дедуп-обязательство `H(doc_fields, salt_attestor)`. Соль аттестора делает кросс-аттесторную корреляцию невозможной; ни скан, ни номер, ни имя в систему не попадают.
- ≥ 2 независимых аттестора на якорь: сговора с одним недостаточно.
- Коррупция аттестора: канареечные пробы red team (V-01); проваленная канарейка → деаккредитация + отзыв всех его якорей за период (честным — fast-track повторная верификация).

### 5.2. Labor anchor (якорь вкладом)

- ≥ 12 мес непрерывного валидированного вклада: ≥ 1 валидированный `q_i` в ≥ 9 из последних 12 месяцев.
- Данные о вкладе живут в Governance (ReputationEvent). Направление зависимостей не ломается инверсией порта: trait `LaborAnchorSource` объявлен в `flora-verification-contracts`, **реализует его Governance**, внедряет композиция `flora-social` — тот же паттерн, что `IMessageSentNotifier` в паре Messaging/Notifications.
- Экономика: подделка = год реального валидированного труда на личность — дороже документного фрода; фарминг микро-вкладов упирается в панельную валидацию и капы (THREATS V-09).

### 5.3. Что якорем не является

Подписки и соцграф (покупаемы), стаж аккаунта (спит), платёж (реинтродукция капитала — нарушает FGP A2), телефонный номер (дёшев на сером рынке и дискриминирует по юрисдикциям).

## 6. Восстановление и ревокация

Нормативная механика для FGP §1.3:

- **Инициация с нового устройства:** challenge 3-of-5 поручителей V2+ (V1 без поручителей — повторная церемония + тот же cooldown). Cooldown 30 дней; уведомления на все прежние каналы.
- **Окно оспаривания:** старый ключ отменяет восстановление одной подписью — живой владелец всегда сильнее «восстановителя»-похитителя.
- Частота ≤ 1 / 12 мес; история восстановлений — приватный флаг для панелей (частые восстановления — маркер аренды/кражи личностей, §8.2).
- Новый commitment наследует уровень и репутацию; старый — в revocation list; активные делегации и мандаты сбрасываются (FGP §1.3).
- **Смерть и уход:** реестра смерти нет — неподдержание церемоний деградирует уровень до V0 за ≤ 12 мес; электорат самоочищается.
- **Добровольный выход:** ревокация по подписи + удаление данных модуля (§9.2).

## 7. C_identity: замер и публикация

### 7.1. Определение

```
C_hat(L) = min( рыночная цена готовой личности уровня L,
                себестоимость производства с нуля,
                стоимость аренды (§8.2) )
```

Консервативный минимум по **всем** известным путям, включая асинхронный (§3.3).

### 7.2. Методика

- Ежеквартальные **санкционированные закупочные пробы** red team (THREATS §3): попытка купить/заказать личность каждого уровня на сером рынке; бюджет и результаты логируются, канарейки декларируются закрытыми записями.
- Honeypot-мониторинг предложений («продам Flora V2») — пассивная нижняя граница рынка.
- Производственная оценка: red team строит сибил-кольцо в песочнице по действующим правилам; считаются фактические человеко-часы × ставки.
- Против Goodhart на самом замере (атакующий-«продавец» показывает пробам завышенные цены): несколько независимых методик, публикуется консервативный минимум.

### 7.3. Использование

Ежеквартальный отчёт `C_hat(L)` по уровням и путям + методика. Потребители: условие Sybil-безопасности (FGP §4.1.1), гейты фаз (FGP §8.3), лестница деградации (FGP §7.3): `C_hat` ниже порога класса → автоматический advisory для класса. Численные пороги фиксируются в Приложении A FGP как R2-параметры **после первых двух замеров v0** — выдумывать значения до данных протокол отказывается.

## 8. Экономика атак

### 8.1. Векторы по уровням

| Вектор | Цена определяется | Ограничитель | Детекция |
| --- | --- | --- | --- |
| Ботоферма V0 | ~0 | governance-прав нет | — |
| Человеко-ферма V1 | синхронное человеко-время × 2/год × k | коллизии слотов | темпоральная кластеризация, fail-паттерны |
| Deepfake V1 | оператор realtime на сессию | §3.2 | латентность, артефакты, канарейки |
| Кольцо V2 | ≥ 3 реальных V2 × риск слэшинга | кап `N_vouch`, разнокластерность рёбер | плотные подграфы, циклы, CUSUM |
| Документный фрод V3 | ≥ 2 коррумпированных аттестора | канареечные пробы | несовпадение дедуп-обязательств |
| Аренда личностей | зарплата соучастника | §8.2 | поведенческая монотонность |

### 8.2. Аренда — честный пол стоимости

Самая дешёвая масштабируемая атака — не подделка, а **аренда**: живой человек честно проходит церемонии и отдаёт ключ или голосует по инструкции. Криптографического решения не существует; есть экономика и риск:

- Личность требует **поддержания** (церемонии 2/год, живые поручительства) — аренда — это постоянная зарплата соучастника, а не разовая покупка. Эта зарплата и есть нижняя граница `C_identity`, публикуемая честно.
- Каждый соучастник — свидетель: подтверждённый доклад об аренде вознаграждается репутацией в protocol-security (аналог governance bounty, THREATS §3) — рынок предательства дестабилизирует схему изнутри (тот же принцип, что в V-03).
- Receipt-freeness бьёт и сюда: соучастник, сохранивший ключ, может молча переголосовать (coercion override, FGP §4.6) — арендодатель не может проверить, что купил.
- Массовая аренда даёт поведенческую монотонность (девайсы, время активности, паттерны расходования кредитов) — эвристики V-01/V-03: сигнал к следствию, не автоматический приговор.

## 9. Приватность и данные

### 9.1. Что хранит сервер (исчерпывающе)

| Уровень | Хранится | Не существует нигде |
| --- | --- | --- |
| V0 | email-верификация (текущий модуль) | — |
| V1 | commitment, уровень, сроки; прошедшие слоты; вердикты пар (bit + enum-флаги) | видео/аудио/биометрия сессий |
| V1 async | + вердикты валидаторов; медиа-артефакт TTL ≤ 72 ч | артефакты старше 72 ч |
| V2 | рёбра поручительств (приватные), стейк-записи | публичный граф |
| V3 | бит якоря, ID аттестора, salted-дедуп-обязательство | документы, имена, номера |

- Все вердикты и флаги — enum-коды без свободного текста: свободный текст = канал утечки PII.
- TTL: записи слотов и вердиктов старше 24 мес удаляются; для статистики `C_identity` достаточно агрегатов.

### 9.2. Право на удаление

Выход (§6) удаляет всё в модуле Verification, включая связь «аккаунт ↔ commitment». В журнале governance остаются только nullifier'ы в исторических тэлли — псевдонимные криптографические артефакты, связывающий секрет которых уничтожен: это анонимизация, append-only история не переписывается (FGP §4.1.3).

### 9.3. Unlinkability и доверенная точка

- Governance видит nullifier'ы и ZK-предикаты — не аккаунты.
- Церемонии не связывают сессионный псевдоним с профилем; дедуп-обязательства аттесторов посолены per-attestor.
- Остаточный канал: Verification знает связь «аккаунт ↔ commitment» — это единственная доверенная точка протокола. Минимизация: связь не покидает модуль, доступ журналируется; **blind issuance** (выдача аттестации без знания связи) — исследовательский трек P2 (THREATS §7).

Направления зависимостей соответствуют правилам workspace (`next-architecture.md` §2.3): `flora-governance → flora-verification-contracts` — и потребление аттестаций, и реализация `LaborAnchorSource` (инверсия порта).

### 10.2. Данные

`personhood_attestations`, `personhood_vouch_edges`, `personhood_ceremonies`, `personhood_nullifier_roots`, `personhood_revocations`, `personhood_anchor_receipts` — схема `flora_core`, владелец Verification, миграции через `flora-migrate` со своей таблицей истории. Nullifier-реестр и аттестации принадлежат **Verification, не Governance** — Governance хранит только nullifier-теги в своих артефактах.

### 10.3. Криптография

- Подписи — Ed25519 (RustCrypto-семейство, без C-зависимостей — как в остальном workspace). PRF nullifier'ов, commitment-схема и ZK-система (membership + range «level ≥ L») фиксируются **отдельным крипто-RFC** до P1/P2: выбор между ZK-friendly хешами (Poseidon) и консервативными (BLAKE3 + обвязка) — трейд-офф зрелости и производительности, решается с внешним ревью.
- Инварианты workspace обязательны: `unsafe_code = "forbid"`, `cargo deny` (лицензии, дубли), `cargo audit`/`cargo vet` для personhood-критичных крейтов, пиновка `Cargo.lock`.
- Верификатор пруфов — **одно Rust-ядро**, компилируемое в native (сервер) и wasm32 (`@flora/client-core`): дрейф паритета исключён по построению. Монокультурная оговорка: golden-вектора (`docs/test-vectors/personhood/`) — кросс-проверка, независимая реализация верификатора — желательный community-артефакт (THREATS V-11).
- Consensus-critical вычисления — целочисленные/фикс-пойнт (требование FGP §8.1): float в путях, влияющих на пруфы, запрещён.

### 10.4. Согласование с Rust-миграцией

- Verification мигрирует в Фазе 2a (`next-architecture.md` §6, статус — в таблице §6.0); FPP-имплементация стартует **после** cutover 2a, только в Rust.
- Церемонии §3 требуют P2P-видеоканала (WebRTC, E2E) — новой клиентской поверхности Apps/Web и Apps/Mobile; сервер — только сигналинг. Это самая дорогая часть P1 и она честно входит в его стоимость.
- Test vectors: `docs/test-vectors/personhood/` — nullifier-деривации, membership/range-пруфы, дедуп-обязательства (паритет server ↔ client-core, по образцу FSCP).

## 12. Угрозы и остаточные риски

Операционные программы — THREATS V-01; здесь — сводка честных остатков:

- **Deepfake-гонка** (§3.2): перманентный фронт; протокол переживает деградацией полномочий, не отрицает.
- **Аренда** (§8.2): пол стоимости = зарплата соучастника; ниже него `C_identity` не опустится, но и не поднимется без роста риска для арендодателя.
- **Коррупция аттесторов** (§5.1): канарейки ловят постфактум; сговор ≥ 2 аттесторов живёт до первой пробы.
- **Accessibility-путь как дешёвый обход** (§3.3): отдельная строка рыночного замера; дешевле синхронного → ужесточение (R2).
- **Coercion в домохозяйстве** (принуждение к церемонии/передаче ключа): голоса защищены override (FGP §4.6), сама личность — окном оспаривания (§6); полностью не решается.
- **Доверенная точка Verification** (§9.3): связь «аккаунт ↔ commitment» — цель для инсайдера и юридического принуждения; митигации — журналирование доступа, blind issuance как P2-трек, минимум остального (V-08: выдавать почти нечего).
- **Goodhart на `C_hat`** (§7.2): замер — сам поверхность манипуляции; несколько методик, консервативный минимум.
