## Overview

FSA (Flora Search Algorithm) — алгоритмический фундамент полнотекстового поиска в экосистеме FLORA. Все поверхности поиска (FSA-F, FSA-A, FSA-M, FSA-P, FSA-C, FSA-N, FSA-D) строятся на одном ядре, определённом в этом документе: единый анализ текста, единый инвертированный индекс, единый исполнитель запросов и единая формула ранжирования с управляемой персонализацией.

**Модель разделения труда:** ядро выполняет всю работу — модули лишь направляют его. Модуль FSA-X описывает *декларативный профиль* (поля и веса, режим свежести, политику расширения запроса, потолок персонализации) и типизирует API своего домена. В модуле нет ни поисковой логики, ни скоринга; добавление новой поверхности не меняет ядро.

Этот документ нормативен: каждый компонент **обязан** соответствовать описанным здесь принципам и интерфейсам. Специфика каждой поверхности — в её собственном spec-файле.

## Goals & Non-Goals

**Goals:**
- Единое переиспользуемое ядро поиска: анализ → индекс → запрос → ранжирование.
- Максимальная скорость **без потери качества**: все ускорения точные (индексные структуры, document-at-a-time с seek, точный top-k); эвристики, способные потерять релевантный документ, запрещены.
- Управляемая индивидуальность: уровень `α ∈ [0, 1]` — от полного отсутствия интеграции с FIRA (`α = 0`) до максимальной персонализации (`α = 1`).
- Детерминизм: инъекция времени, нормативные tie-break, воспроизводимость бит-в-бит.
- Переносимость: ядро компилируется в `wasm32` (клиентский поиск по E2E-сообщениям, FSA-M).

**Non-Goals:**
- Персистентность и шардирование индекса — зона интегрирующего модуля (ядро — in-memory структура без I/O).
- Семантический / векторный поиск — v2+ (§Open Questions).
- Рекомендации «что посмотреть» без запроса — это FIRA, не FSA.
- UI поиска, сниппеты и подсветка — зона Apps (ядро отдаёт байтовые смещения токенов и совпавшие термы).

## Architecture Position

FSA — **functional product** [`Products/FSA`](../../Products/FSA) (headless/embeddable), как FSCP/FRC/FIRA:

- `fsa-contracts` — DTO-мост: `PersonalizationLevel`, `AffinitySnapshot`, `SearchDomain`, `SearchPreferences`, словарь `affinity_key`. Зависимости: только `serde`.
- `fsa-core` — ядро + поверхностные модули (профили и типизированные обёртки). Зависимости: только `fsa-contracts`.

Запрещённые зависимости (portable surface): `sqlx`, `axum`, `tokio`, `flora-shared`, любые crates Social/FIRA. **Мост FIRA → FSA — данные, не код:** composition-слой Social собирает `AffinitySnapshot` из сигналов FIRA и передаёт его в FSA запросом; FSA не знает, как снимок построен.

```
Server-side (Social):                        Client-side (E2E, wasm):
Apps → flora-api → flora-social              Apps/Web (worker)
  ├─ flora-content   → fsa_core::feed          └─ fsa_core::messages (FSA-M)
  ├─ flora-music     → fsa_core::audio             ← документы: расшифрованные
  ├─ flora-users     → fsa_core::people               сообщения локально
  ├─ flora-content   → fsa_core::communities
  ├─ flora-notifications → fsa_core::notifications
  └─ flora-content   → fsa_core::drafts
       + AffinitySnapshot из FIRA (композиция, read-only DTO)
```

Владение данными не меняется: модуль-владелец поставляет документы в «свой» экземпляр движка и обязан применять фильтры видимости (блокировки, приватные сообщества) **до** индексации либо структурными фильтрами запроса. Ядро не проверяет права доступа.

## 1. Философия и принципы

1. **Качество без потерь.** Результат исполнителя бит-в-бит совпадает с наивным полным перебором документов при той же формуле (§7). Отсечения — только по строгой AND-семантике; вероятностные пропуски документов запрещены.
2. **Скорость без компромисса.** Ускорение достигается структурами (инвертированный индекс, отсортированные постинги, seek от самой редкой группы, ограниченная top-k куча), а не деградацией качества. Все лимиты (§6, `EngineLimits`) — явные и настраиваемые.
3. **Индивидуальность под контролем пользователя.** Один параметр `α ∈ [0, 1]` управляет глубиной интеграции с FIRA. `α = 0` — никакой персонализации: выдача идентична для всех пользователей. Настройка пользователя сильнее глобальных дефолтов (FGP §1.2 п. 2).
4. **Детерминизм.** Ядро не читает часы (`now` инъецируется запросом), не содержит случайности; tie-break нормативны. Одинаковый индекс + одинаковый запрос ⇒ одинаковый ответ, независимо от порядка индексации документов.
5. **Privacy-first.** Поиск по E2E-контенту выполняется только на клиенте (FSA-M): plaintext и индекс не покидают устройство. Серверные поверхности индексируют только контент, доступный пользователю по правилам владельца данных.

## 2. Анализ текста

### 2.1 Нормализация FSA-N1

Профиль нормализации **FSA-N1** (нормативный, без внешних Unicode-таблиц):

1. `lowercase` (Unicode);
2. кириллица: `ё → е`;
3. combining-диакритики `U+0300–U+036F` срезаются;
4. статическая таблица частых прекомпозитных латинских букв (`é→e`, `ü→u`, `ç→c`, …); лигатуры: `ß→ss`, `æ→ae`, `œ→oe`.

Полный NFKD — roadmap v2. **Смена профиля нормализации требует переиндексации** (мажорная версия индекса).

### 2.2 Токенизация

Токен — непрерывная последовательность alphanumeric-символов (Unicode); всё остальное — разделители. Каждый токен несёт `position` (порядковый номер в поле) и байтовые смещения `byte_start..byte_end` в **исходной** строке — этого достаточно для подсветки на стороне UI без повторного анализа.

Лимиты: `max_field_tokens` на поле (хвост усекается), `max_token_chars` на терм (терм **усекается, не отбрасывается** — усечённый префикс остаётся находимым префиксным поиском).

### 2.3 Коррекция раскладки ru↔en

Для токена запроса строится альтернатива в противоположной раскладке (таблица физических клавиш QWERTY ↔ ЙЦУКЕН). Правила:

- токен конвертируется целиком; смешанные скрипты — не конвертируются;
- буквы пунктуационных клавиш (`ж э б ю х ъ`) дисквалифицируют токен (пунктуация не переживает токенизацию);
- вариант добавляется в план запроса **только если существует в словаре индекса** — ложных срабатываний нет;
- штраф варианта — `layout_penalty` (§4.2).

### 2.4 Fuzzy (d = 1)

Опечатки исправляются на расстоянии Дамерау—Левенштейна 1 (OSA: вставка, удаление, замена, транспозиция):

- **Кандидаты** — через deletion-сигнатуры (SymSpell): при интернировании терма индекс сохраняет FNV-1a-хеши всех строк, получаемых удалением одного символа; сигнатуры строятся для термов длиной 2..=24 символа (`MAX_SIGNATURE_CHARS`).
- **Верификация** — каждый кандидат проверяется точным ограниченным OSA-расстоянием; коллизии хешей и ложные кандидаты отсеиваются. Точность важнее охвата.
- Детерминированный порядок кандидатов: `df desc → терм лексикографически`; лимит `fuzzy_max_candidates`.

## 3. Документ и индекс

### 3.1 Модель документа

```
Document {
    id:            String        // внешний стабильный id (владелец данных)
    timestamp:     i64           // unix-секунды (свежесть, tie-break)
    static_rank:   f64 ∈ [0, 1]  // глобальный (неперсональный) приор качества
    fields:        [(имя, текст)]        // текстовые поля профиля
    attrs:         [(имя, значение)]     // точные атрибуты для фильтров
    personal_keys: [String]              // ключи аффинити (§5.2)
}
```

### 3.2 Инвертированный индекс

- Словарь термов — упорядоченная структура (`BTreeMap`): префиксные сканы за `O(log |V| + k)`.
- Постинг-листы отсортированы по внутреннему id документа (id растёт монотонно ⇒ вставка в конец сохраняет порядок). Постинг: `doc + [FieldHit { field, tf, positions }]`; позиции хранятся только у полей с `positions = true`.
- Атрибуты индексируются в общем словаре как псевдо-поле `255` с ключами `\u{1}name\u{1}value`: `\u{1}` не встречается в токенах, поэтому пространство атрибутов не пересекается с термами и не участвует в префиксных сканах.
- Средняя длина поля (`avg_field_len`) поддерживается инкрементально по живым документам.

### 3.3 Структурные фильтры

`SearchFilters` — сравнение точных атрибутов байт-в-байт:

| Фильтр | Семантика |
|--------|-----------|
| `all_of` | документ обязан иметь каждый атрибут |
| `any_of` | для каждой группы — хотя бы один атрибут из группы (скоупы) |
| `none_of` | документ не должен иметь ни одного из атрибутов |

Отсутствующий в словаре атрибут: `all_of`/`any_of` (все альтернативы) → пустая выдача; `none_of` → игнорируется.

### 3.4 Обновления и compaction

- `upsert` = tombstone старой версии + новая версия с новым внутренним id.
- `remove` = tombstone. Tombstone-документы отфильтровываются при исполнении.
- `df` терма учитывает tombstones до `compact()` — это влияет только на idf (одинаково для всех документов запроса) и не нарушает точность top-k относительно текущего состояния индекса.
- `compact()` — полная перестройка: перенумерация документов, пересчёт df, восстановление deletion-сигнатур. Рекомендация интегратору: compact при `tombstones / docs > ~0.2`.

## 4. Запрос и ранжирование

### 4.1 Синтаксис запроса

| Элемент | Семантика |
|---------|-----------|
| `терм` | обязателен (AND-семантика); допускает расширения §4.2 |
| `"фраза из слов"` | все термы точные + смежность позиций в одном позиционном поле; ≤ 8 токенов |
| `-терм` | исключает документы, содержащие терм (в любом поле) |

Бюджет позитивных токенов — `max_query_tokens` (лишнее отбрасывается). Пустой запрос → пустой ответ.

### 4.2 План: группы вариантов

Каждый токен запроса разворачивается в **группу вариантов** (union внутри группы, AND между группами):

| Вариант | Условие | Штраф (дефолт) |
|---------|---------|-----------------|
| точный терм | есть в словаре | 1.0 |
| раскладка ru↔en | §2.3, есть в словаре | `layout_penalty` = 0.85 |
| префикс | длина ≥ `prefix_min_chars`; по умолчанию только последний токен (typeahead) | `prefix_penalty` = 0.5 |
| fuzzy d=1 | длина ≥ `fuzzy_min_chars` | `fuzzy_penalty` = 0.45 |

Дедупликация по терму — максимум штрафа; порядок вариантов детерминирован. Группа без вариантов ⇒ пустая выдача (AND). Фразовые термы расширений не получают.

**idf группы** считается по **суммарному df всех вариантов**:

```
idf(group) = max( ln(1 + (N − df_total + 0.5) / (df_total + 0.5)),  MIN_IDF )
N          = живых документов;  MIN_IDF = 1e-3  (пол; защита при df > N из-за tombstones)
```

Нормативное обоснование: расширение (префикс/fuzzy) не должно выигрывать от собственной редкости — все документы группы скорятся в одном масштабе селективности *токена запроса*, а не его случайного варианта.

### 4.3 Исполнение (document-at-a-time)

- По каждому варианту — курсор постинг-листа с продвижением только вперёд (`seek` через `partition_point`); группа — union-курсор (минимум по вариантам).
- Пересечение ведёт **самая редкая группа** (наименьший суммарный df); остальные группы согласуются seek'ами до общего документа.
- На согласованном документе проверяются: tombstone, фильтры §3.3, `-исключения`, фразовые ограничения (смежность позиций `p, p+1, …` в одном поле).
- Сложность: `O(df_min × Σ log df)` seek-операций + скоринг только полностью согласованных документов. Отсечений по скору нет — при строгой AND-семантике они не дают выигрыша, точность top-k гарантирована конструкцией.

### 4.4 Скоринг

**Текстовая релевантность** — BM25F с насыщением per-field (вес поля применяется **после** насыщения — короткие сильные поля вида `title`/`name` честно доминируют над длинными полями с высоким tf):

```
tfn_f    = tf_f / B_f,   B_f = (1 − b_f) + b_f · len_f / avg_len_f
sat_f    = tfn_f / (k1 + tfn_f)
w(v, d)  = penalty_v · Σ_f  weight_f · sat_f
S_text   = Σ_groups  idf(group) · max_{v ∈ group, v матчит d} w(v, d)
```

Вклад группы — **максимум** по совпавшим вариантам (документ не получает двойной бонус за точный терм и его же префикс); `matched_terms` ответа — лучший вариант каждой группы (для подсветки).

**Мультипликативные надстройки** (в порядке применения):

```
S = S_text
  × (1 + proximity_weight · tightness)      // §близость
  × (1 + exact_boost_f)                     // поле f целиком равно запросу
  × (1 + static_rank_weight · static_rank)  // глобальный приор
  × (1 + w_recency · 2^(−age / half_life))  // RecencyMode::Boost
  × (1 + α · λ_m · A(d))                    // персонализация, §5
```

- **Близость** (`proximity_weight > 0`, ≥ 2 групп, есть позиционные поля): по каждому позиционному полю ищется минимальное окно, покрывающее все группы (sliding window по слитым позициям); `tightness = min(1, групп / span)`; берётся лучшее поле.
- **Точное совпадение поля**: FNV-1a-хеш нормализованных термов поля сравнивается с хешем термов запроса; при совпадении — `× (1 + exact_boost)` максимального из совпавших полей. Навигационные запросы (точный username, точное название трека) выигрывают у частичных совпадений.
- **Свежесть** — §4.5; отрицательный возраст (документ «из будущего») зажимается в 0.

### 4.5 Режимы свежести

| `RecencyMode` | Поведение |
|---------------|-----------|
| `None` | свежесть не влияет |
| `Boost { half_life, weight }` | множитель `× (1 + weight · 2^(−age/half_life))` — плавное экспоненциальное затухание |
| `Primary` | сортировка `timestamp desc → Score desc → id asc`; текст остаётся фильтром и tie-break (уведомления) |

### 4.6 Top-k и пагинация

Точная top-k куча размера `offset + limit` (ограничен `max_results_window`). Нормативный tie-break:

```
Score desc → timestamp desc → внешний id asc          (RecencyMode::None | Boost)
timestamp desc → Score desc → внешний id asc          (RecencyMode::Primary)
```

`matched_total` — точное число документов, удовлетворивших запросу. Пагинация стабильна: страницы `offset/limit` — срезы одного и того же полного порядка.

## 5. Индивидуальность (мост FIRA → FSA)

### 5.1 Уровень α

`PersonalizationLevel` — `α ∈ [0, 1]` (`fsa-contracts`): `0` — отсутствие индивидуального поиска (никакой интеграции с FIRA), `1` — максимальный уровень. Значения вне диапазона зажимаются, `NaN → 0`. Продуктовый дефолт — `1.0`; хранится в `SearchPreferences` пользователя (персистенс — Social Users). Пользовательская настройка сильнее глобальных дефолтов (FGP §1.2 п. 2).

### 5.2 AffinitySnapshot

Снимок аффинити пользователя — read-only DTO, собираемый composition-слоем Social из данных FIRA (UIP, author affinity, социальный граф) на время запроса; для FSA-M снимок строится на клиенте из локальных данных. FSA не знает происхождения весов — нормативен только словарь ключей:

```
author:{id} · user:{id} · community:{id} · topic:{id} · artist:{id}
genre:{id} · sender:{id} · conversation:{id} · actor:{id} · tag:{slug}
```

Конструкторы — `fsa_contracts::affinity_key` (строковый формат ключей — контракт). Веса зажимаются в `[0, 1]`, `NaN` отбрасывается, дубликаты — максимум. Документ объявляет свои ключи в `personal_keys` при индексации.

### 5.3 Блендинг и инварианты

```
A(d)    = max по personal_keys(d) веса из снимка   ∈ [0, 1];  0 — нет совпадений
S_final = S × (1 + α · λ_m · A(d))
```

`λ_m ∈ [0, 1]` — потолок влияния персонализации, задаётся профилем модуля (§6): насколько домен *в принципе* персонализируем. `λ_m = 0` — модуль неперсонализируем (FSA-D: черновики — личные данные, персонализировать нечего).

**Нормативные инварианты** (закреплены интеграционными тестами, §7):

1. **Эквивалентность выключения:** `α = 0` ⇒ множитель ровно `1.0`; выдача **бит-в-бит** совпадает с запросом без снимка. Пустой снимок эквивалентен `α = 0`.
2. **Монотонность:** рост `α` не понижает скор документа с положительным аффинити и не меняет скоры документов без аффинити.
3. **Состав неизменен:** персонализация переупорядочивает найденное, но никогда не добавляет и не убирает документы (`matched_total` и множество id инвариантны относительно `α`).

### 5.4 Приватность персонализации

Снимок живёт в памяти запроса и не персистируется ядром. Ядро не логирует ключи. Границы FIRA §12 наследуются: снимок не может содержать сигналов из E2E-переписки; для FSA-M аффинити строится только на клиенте.

## 6. Контракт модулей: SearchProfile

Модуль FSA-X направляет ядро декларативным профилем:

```rust
SearchProfile {
    domain:  SearchDomain,           // feed | audio | messages | people | communities | notifications | drafts
    fields:  Vec<FieldSpec>,         // ≤ 32 полей
    ranking: RankingParams,
    expansion: ExpansionPolicy,
    personalization: PersonalizationPolicy,  // λ_m
    limits:  EngineLimits,
}

FieldSpec   { name, weight > 0, b ∈ [0,1] = 0.75, positions = false, exact_boost ≥ 0 = 0 }
RankingParams { k1 = 1.2, recency = None, static_rank_weight = 0, proximity_weight = 0 }
```

`ExpansionPolicy` (дефолты): `layout_correction = true`, `prefix_min_chars = 3`, `prefix_last_token_only = true`, `prefix_max_terms = 64`, `fuzzy_min_chars = 4`, `fuzzy_max_candidates = 24`, штрафы §4.2.

`EngineLimits` (дефолты): `max_field_tokens = 8192`, `max_token_chars = 64`, `max_query_tokens = 16`, `max_results_window = 1000`.

Профиль валидируется при создании движка (`validate()`): дубликаты полей, неположительные веса, `b`/`λ` вне `[0, 1]`, нулевые лимиты — ошибка конструирования, не runtime-сюрприз.

**Добавление новой поверхности** = профиль + типизированная обёртка (документ домена → `Document`, параметры домена → `SearchFilters`). Ядро не меняется.

## 7. Детерминизм и инварианты (тестируемые)

Ядро — чистые функции над `f64`; `now` инъецируется; случайности нет. Нормативные инварианты закреплены тестами `Products/FSA/crates/fsa-core/tests/invariants.rs` и unit-тестами модулей:

| Инвариант | Тест |
|-----------|------|
| `α = 0` ⇔ бит-в-бит без персонализации; пустой снимок ⇔ `α = 0` | `alpha_zero_is_bit_identical_to_disabled_personalization` |
| Монотонность `α`; скоры документов без аффинити неизменны | `alpha_is_monotonic_and_touches_only_affine_docs` |
| Персонализация не меняет состав выдачи | `personalization_never_changes_result_set` |
| Повторные запросы идентичны; порядок индексации не влияет | `search_is_deterministic_across_runs_and_insertion_orders` |
| Пагинация — срезы одного порядка | `offset_pagination_is_stable` |

Правки формул ранжирования — класс R2 по дисциплине FGP §2.2 (меняют публичное поведение); требуют обновления этой спеки и инвариантных тестов.

## 8. Сложность и производительность

| Операция | Стоимость |
|----------|-----------|
| Индексация документа | `O(токенов × log |V|)` + deletion-сигнатуры `O(len²)` на новый терм |
| Точный терм | `O(log |V|)` |
| Префиксный скан | `O(log |V| + prefix_max_terms)` |
| Fuzzy-кандидаты | `O(len)` хеш-проб + верификация `O(len²)` на кандидата |
| Пересечение | `O(df_min × Σ log df)` seek-операций (драйвер — самая редкая группа) |
| Top-k | `O(log(offset + limit))` на согласованный документ |
| `compact()` | `O(размер индекса)`, амортизируется порогом tombstones |

Память: постинги + позиции только у полей с `positions = true`; атрибуты — по постингу на пару. Ядро однопоточное по построению (без блокировок); конкурентный доступ (RwLock, шардирование по доменам/тенантам) — зона интегратора.

## 10. Governance (FGP)

- **Суверенитет настройки:** `α` — пользовательская настройка (`SearchPreferences`); никакие глобальные изменения дефолтов её не переопределяют (FGP §1.2 п. 2).
- **Неалгоритмический fallback:** `α = 0` — полноценный честный режим поиска, а не деградация; выключение персонализации не наказывается качеством (инвариант состава §5.3 гарантирует это конструкцией).
- **Никаких теневых санкций:** FSA не понижает документы скрытыми per-user коэффициентами; единственный per-user сигнал — прозрачный `AffinitySnapshot`, действующий только вверх (`A(d) ≥ 0`).
- **Engagement-KPI — не целевая функция:** качество поиска измеряется попаданием (клик по результату, dwell), не временем в приложении.

## Open Questions / Future Work

- **Морфология:** стемминг/лемматизация ru/en (v2) — потребует версионирования анализатора и переиндексации; выбор между лёгким стеммером и словарной лемматизацией.
- **OR / weak-AND:** ослабленная семантика для длинных запросов; вместе с ней — MaxScore/WAND-отсечения (при строгом AND не нужны).
- **Персистентный индекс:** сегментный формат (immutable segments + merge) для серверных поверхностей и IndexedDB-снапшоты для FSA-M.
- **Гибридный поиск:** векторные эмбеддинги как второй канал retrieval с поздним слиянием (RRF) — после появления инфраструктуры эмбеддингов.
- **Федеративная строка поиска:** единый запрос по всем доменам с маршрутизацией через `SearchDomain` и слиянием выдач на уровне композиции.
- **Синонимы/алиасы:** словарь на уровне профиля модуля (например, транслитерация имён артистов).
