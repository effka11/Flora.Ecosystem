## Overview

FEP — экономический протокол Flora: **пост-дефицитная** денежная система, спроектированная так, чтобы деньги оставались средством обмена и координации и **не могли** стать инструментом власти. Валюта — **LIV** (Leaves): официальная крипта экосистемы (протокол ещё не в проде); она полезна только в движении; лежащая без движения, она медленно возвращается в общую казну.

Три источника ликвидности:

1. **UBI-эмиссия по числу людей** — каждый подтверждённый человек (FPP V1+) получает равный безусловный поток LIV. Других источников эмиссии не существует: ни премайна, ни аллокаций, ни эмиссии под залог капитала.
2. **Демерредж** («ржавеющие деньги» Гезелля) — облагаемые балансы теряют ~6.7 %/год в пользу Commons-казны. Копить невыгодно; тратить, вкладывать и делиться — выгодно.
3. **Взаимный кредит** (традиция WIR/LETS/Trustlines) — пары людей открывают линии доверия; платёж проходит по цепочке линий без единого LIV. Ликвидность создаётся доверием, беспроцентно.

Учёт — **публичный проверяемый журнал** (append-only хеш-цепочка + Merkle-дерево, класс Certificate Transparency), а не блокчейн с плутократическим консенсусом: PoW и PoS отвергнуты аксиоматически (§0). Любой клиент реплеит журнал и проверяет каждый инвариант сам — включая wasm-сборку того же ядра, что работает на сервере.

## Goals & Non-Goals

**Goals**

- Средство обмена и учёта вклада, устойчивое к концентрации: богатство не самовоспроизводится (нет процента, нет доходности на капитал внутри протокола).
- Эмиссия, привязанная к людям, а не к капиталу или энергии.
- Полная проверяемость: любой участник восстанавливает всё состояние из публичного журнала.
- Файервол «деньги ↛ власть»: LIV не конвертируется ни в какой параметр FGP (вес голоса, репутацию, QV-кредиты, места в жюри).

**Non-Goals**

- Спекулятивный актив / store of value. Демерредж целенаправленно делает LIV плохим объектом накопления.
- Инвестиционный инструмент. Внутри протокола отсутствует процент и любые деривативы.
- Анонимная наличность. Аккаунт = человек (или commons-структура); приватность обеспечивается на уровне выше (агрегаты, минимизация раскрытия), а не анонимными кошельками — Sybil-защита эмиссии важнее (см. FEP-THREATS §3).
- Замена fiat/криптовалют вне Flora. FEP — внутренняя экономика экосистемы.

## Architecture Position

```
Клиенты (Apps/Web, Apps/Mobile, @flora/client-core + wasm flora-economy-crypto)
        │ HTTP /api/economy/* (подписи Ed25519 — на устройстве)
        ▼
flora-api → flora-social (композиция; флаг Economy:Enabled)
        ▼

   │ порт PersonhoodAttestor ← flora-verification-contracts (FPP V1+)
   │ порты EconomyReadPort / EconomyAccountProvisioner → flora-economy-contracts

```

Правило зависимостей (next-architecture.md §2.3): `flora-economy-crypto` не видит ни одного бизнес-модуля; модуль `flora-economy` общается с чужими модулями только через `*-contracts`.

## 0. Аксиомы проектирования

Продолжение аксиом FGP §0 в экономическую плоскость:

- **A1. Деньги не конвертируются во власть.** Ни один параметр FGP не может зависеть от баланса LIV. Обратное направление (власть → деньги) ограничено ратифицированным бюджетом казны (§8).
- **A2. Богатство не самовоспроизводится.** Внутри протокола нет процента, стейкинга, доходности на остаток. Единственная «доходность» — отрицательная (демерредж).
- **A3. Эмиссия принадлежит людям поровну.** Новые LIV появляются только как UBI на подтверждённых людей. `Σ эмиссии = Σ UBI` — проверяемо по журналу.
- **A4. Дефицит — не источник ценности.** Взаимный кредит позволяет платить доверием: нулевой баланс не исключает человека из экономики.
- **A5. Не верь — проверяй.** Всё состояние — детерминированная функция публичного журнала. Расхождение реплея — событие деградации (FGP §7.3), протокол замирает в статус-кво.
- **A6. Параметры — у людей.** Все экономические константы (Приложение A) меняются только решением FGP класса R2; в коде нет «магических» ручек, недоступных governance.

## 1. Единицы и типы

| Понятие | Определение |
| --- | --- |
| **LIV** (Leaves) | Учётная единица FEP; тикер `LIV`. Символ в UI — `🍃` (рекомендация, не норматив). |
| **grain** | Атомарная единица: **1 LIV = 10⁶ grain**. Все суммы протокола — целые grain (`i64`). Дробных grain не существует. |
| **AccountId** | 16 байт; равен UUID пользователя Flora (v7) или commons-структуры. |
| **Timestamp** | Unix-миллисекунды UTC, `i64`. |
| **Epoch (UBI)** | Целочисленный индекс: `epoch = ⌊(t − genesis_at) / ubi_epoch_ms⌋`. |
| **Период (демерредж)** | Целочисленный: `periods = ⌊(t − last_applied) / demurrage_period_ms⌋`. |

Отрицательные балансы запрещены инвариантом. Переполнения невозможны: вся арифметика — checked; консенсусные коэффициенты — Q32.32 (§9).

## 2. Эмиссия: PoP-UBI

### 2.1. Правило

Каждый аккаунт человека с **активной** personhood-аттестацией уровня **V1+** (FPP §2) имеет право на `ubi_per_epoch` grain за каждую UBI-эпоху. Начисление — по требованию (claim), записью `UbiIssued` в журнал.

- Одна эпоха — одно начисление на аккаунт (движок отклоняет повтор).
- Ретроактивный хвост ограничен `ubi_max_backfill_epochs` (включая текущую): вернувшийся после перерыва получает ограниченный догон; «мёртвые души» не аккумулируют UBI (рифма с вымыванием неактивных из электората FPP).
- Диапазон эпох и сумма в записи **пересчитываются движком** при применении; расхождение = `ReplayDiverged`.

### 2.2. Sybil-экономика эмиссии

Стоимость атаки на эмиссию = стоимость подделки личности `C_identity(V1)` (FPP §5). Атака окупается только при `C_identity < UBI · T_обнаружения`. Следовательно `C_identity` — публичный экономический параметр безопасности FEP (он уже замеряется программой FGP §4.1.1); при его падении governance обязан поднять требования V1 или снизить `ubi_per_epoch` (FEP-THREATS §3).

### 2.3. Стационарность денежной массы

В паре с демерреджем масса на человека сходится к пределу:

```
M∞ = ubi_per_epoch / (1 − retention_epoch),   retention_epoch = (1 − δ)^(periods_per_epoch)
```

При параметрах genesis (Приложение A): δ = 191 ppm/сутки, эпоха 30 суток → `retention_epoch ≈ 0.9943`, `M∞ ≈ 175 000 LIV` на человека. Эмиссия **не** гиперинфляционна: система стремится к динамическому равновесию, где приток UBI равен оттоку демерреджа. Диагностика — `issuance::steady_state_per_person` (не consensus-путь).

## 3. Демерредж

### 3.1. Правило

Для баланса `b` и `n ≥ 1` полных периодов:

- если `b ≤ demurrage_exempt_threshold` — начисления нет (защита малых кошельков);
- иначе `b' = round_half_even(b · (1 − δ)^n)`, ограничено `[0, b]`; списание `b − b'` зачисляется в Commons-казну записью `DemurrageCharged`.

Порог — **классификатор, а не вычет**: облагаемый баланс ржавеет целиком. Вычет создавал бы выгоду дробления на кошельки ровно у порога (Sybil-стимул). Дробление на кошельки *людей* невозможно по построению: аккаунт = человек (§1), второй аккаунт = вторая личность = `C_identity`.

Метка `demurrage_applied_at` сдвигается ровно на `n · period_ms` (не на «сейчас») — дробный хвост периода не сгорает и не теряется.

### 3.2. Сохранение

Точно, в целых grain, на каждой записи: `b' + to_commons = b`. Глобально (инвариант движка после каждой записи):

```
Σ балансов аккаунтов + баланс казны = Σ эмитированного UBI
```

Демерредж не уничтожает деньги — он **перекладывает** их из простоя в общий бюджет. Уничтожения (burn) в протоколе не существует вовсе.

### 3.3. Экономический смысл ставки

191 ppm/сутки ≈ 6.7 %/год — коридор исторических экспериментов свободных денег (Гезелль; Вёргль 1932: ~12 %/год при значительно более грубой технике). Ставка ниже — не давит на оборот; выше — превращается в конфискацию. Изменение — R2.

## 4. Взаимный кредит (trustlines)

### 4.1. Линии доверия

Пара аккаунтов `(lo, hi)` (канонический порядок — лексикографический по байтам id) открывает линию записью `TrustlineSet` с **двумя подписями**. Каждая сторона задаёт лимит кредита партнёру; лимит ≤ `trustline_max_limit` (кап каскада дефолтов). Позиция линии — одно число: `> 0` — hi должен lo, `< 0` — lo должен hi.

Понижение лимита не отрезает существующий долг задним числом: позиция может временно превышать новый лимит; новые платежи в эту сторону блокируются до возврата в коридор.

### 4.2. Платёж по цепочке

`CreditTransfer` с путём `A → B → … → Z` (максимум `credit_path_max_hops` рёбер, без повторов узлов) сдвигает позицию **каждого ребра** на сумму платежа, атомарно (двухпроходно: сначала проверка ёмкости всех рёбер, затем сдвиг). Подпись — только плательщика `A`; согласие остальных выражено их лимитами.

Свойства:

- **Нулевая сумма.** Σ чистых позиций всех участников ≡ 0. Взаимный кредит не эмитирует LIV и не может быть каналом скрытой эмиссии (инвариант движка).
- **Беспроцентность.** Долг не растёт со временем. Процент — двигатель концентрации капитала; несовместим с A2.
- **Непередаваемость доверия.** Линию нельзя продать/переуступить: она привязана к паре аккаунтов и их ключам.

### 4.3. Дефолт

Невозврат долга по линии — социальное событие между двумя людьми, а не системное: потери ограничены лимитом, который кредитор сам и установил. Протокол не вводит принудительное взыскание; репутационные последствия — вне FEP (и **не** конвертируются в параметры FGP автоматически — A1 действует в обе стороны).

## 5. Commons-казна

Казна — единственный «системный» баланс. Приход: демерредж. Расход: запись `CommonsSpend` с `policy_ref` — ссылкой на **ратифицированную категорию бюджета** FGP §10.2 (PolicyArtifact). Движок проверяет достаточность средств и неотрицательность; соответствие `policy_ref` действующему бюджету проверяет governance-слой (модуль Governance, когда появится; до тех пор запись создаёт только оператор по ратифицированному решению, и это проверяемо по журналу постфактум).

Казна финансирует общую инфраструктуру (серверы, разработка, гранты) — деньгами, образованными **временем держания денег**, а не рекламой, не данными пользователей и не процентом.

## 6. Журнал

### 6.1. Модель

Append-only последовательность записей `LedgerEntry { seq, at, prev_hash, body }`:

- `seq` — плотная нумерация с 0 (genesis);
- `at` — метка секвенсора, монотонно неубывающая;
- `prev_hash` — хеш предыдущей записи (`0³²` у genesis);
- `entry_hash = H(tag_leaf ‖ canonical(seq, at, prev_hash, body))` (§9.2).

Head журнала (аналог Signed Tree Head CT): `{size, last_entry_hash, merkle_root, at}`. Merkle-дерево — по RFC 6962 (листья — `entry_hash`), даёт inclusion-доказательства (`GET /ledger/proof/{seq}`); листовые и узловые хеши доменно разделены.

### 6.2. Виды записей (v1)

| # | Тело | Действие | Авторизация |
| --- | --- | --- | --- |
| 0 | `Genesis` | учреждение; создаёт **0 grain** | — (первая запись) |
| 1 | `ParametersUpdated` | смена параметров | решение FGP R2 (`policy_ref`) |
| 2 | `AccountOpened` | аккаунт + ключ владения | онбординг (порт Provisioner) |
| 3 | `UbiIssued` | эмиссия за диапазон эпох | аттестация V1+ (порт Attestor); суммы пересчитывает движок |
| 4 | `DemurrageCharged` | списание в казну | периодика; суммы пересчитывает движок |
| 5 | `Transfer` | перевод LIV | подпись Ed25519 отправителя |
| 6 | `TrustlineSet` | линия доверия | **две** подписи |
| 7 | `CreditTransfer` | платёж по цепочке | подпись плательщика |
| 8 | `CommonsSpend` | расход казны | бюджет FGP (`policy_ref`) |

### 6.3. Секвенсор и проверяемость

Порядок записей задаёт **секвенсор** (application-слой модуля) — единственный писатель. Честность секвенсора не предполагается — она **проверяется**:

- любой клиент реплеит журнал ядром (wasm-сборка `flora-economy-crypto`) и сверяет head;
- витнессы (независимые наблюдатели, механизм FGP §6.4) косайнят head; форк журнала = два подписанных head с одним `size` — криптографическое доказательство измены;
- расхождение реплея у любого клиента → лестница деградации FGP §7.3: экономика замирает (read-only) до расследования. Отказобезопасное направление — статус-кво, а не работа поверх скомпрометированного состояния.

Идемпотентность/анти-реплей транзакций — клиентский `nonce` (16 байт), одноразовый на весь журнал.

### 6.4. Персистентность

Reference-хранилище — JSONL (одна запись = одна строка канонического JSON, fsync на каждый append; журнал — публичный документ, человекочитаемость намеренна). Продовое хранилище — Postgres-таблица `flora_core.economy_ledger` (append-only, регистрация в `flora-migrate` — при включении модуля в прод). Состояние **не** хранится — только журнал; всё остальное производно.

## 7. Инварианты движка

Проверяются на **каждом** переходе состояния (`LedgerState::apply`):

1. Цепочка: `seq` плотный, `prev_hash` совпадает, `at` монотонен.
2. Сохранение: `Σ балансов + казна = Σ эмиссии` (точно, в grain).
3. Неотрицательность всех балансов и казны.
4. Нулевая сумма взаимного кредита (позиции сдвигаются только парно).
5. Авторизация: подписи Ed25519 с доменными метками; nonce одноразовые.
6. UBI: не выше уровня V1+ не бывает (проверка на входе секвенсора), эпоха не начисляется дважды, суммы пересчитаны.
7. Демерредж: только полные периоды, суммы пересчитаны, exempt-порог соблюдён.

Провал любого инварианта — журнал отвергается целиком с точным диагнозом (`ReplayDiverged`, `ConservationViolated`, …).

## 8. Интеграция с FGP и FPP

| Направление | Механизм | Норма |
| --- | --- | --- |
| FPP → FEP | `PersonhoodAttestor` (V1+ для UBI) | FPP §2; порт в `flora-verification-contracts` |
| FGP → FEP | параметры (R2), бюджет казны (`policy_ref`) | FGP §4.0, §10.2 |
| FEP → FGP | **запрещено** | A1: баланс не влияет ни на один параметр governance |
| FEP → FPP | **запрещено** | оплата аттестаций LIV невозможна (иначе `C_identity` выражался бы в LIV и деньги покупали бы голоса транзитивно) |

Файервол симметричен файерволу «репутация ↛ деньги»: репутационные веса FGP не дают экономических привилегий (скидок на демерредж, повышенного UBI и т.п.).

## 9. Криптографический слой

Наследует FGP-CRYPTO; отличия и уточнения фиксируются здесь.

### 9.1. Примитивы

| Назначение | Примитив | Библиотека |
| --- | --- | --- |
| Хеш журнала/Merkle | SHA-256 | `sha2` (RustCrypto) |
| Подписи | Ed25519 (RFC 8032) | `ed25519-dalek` |
| Коэффициенты | Q32.32 (`i64` raw, `i128` промежуточные, round-half-even, saturate) | `flora-economy-crypto::fixed` |

> Примечание. FGP-CRYPTO для своих структур использует BLAKE3; FEP v1 фиксирует SHA-256 — ядро обязано собираться в wasm32 с минимальным граф-зависимостей, и SHA-256 достаточен для хеш-цепочки/Merkle (второй прообраз, коллизии — вне бюджета атакующего). Смена хеша = FEP v2 (несовместимость журнала).

Ядро **не генерирует ключей** (нет CSPRNG в графе — чистая сборка wasm32): ключи создаются на устройствах (клиентские SDK) и в инфраструктуре модуля.

### 9.2. Доменные метки

Префикс `flora/economy/v1/`; полный реестр — `flora-economy-crypto::domain`:

```
flora/economy/v1/ledger/leaf        хеш записи журнала
flora/economy/v1/merkle/leaf        лист Merkle
flora/economy/v1/merkle/node        узел Merkle
flora/economy/v1/ledger/sth         подпись head витнессом
flora/economy/v1/auth/transfer      подпись перевода
flora/economy/v1/auth/trustline     подписи линии доверия
flora/economy/v1/auth/credit        подпись платежа по цепочке
```

### 9.3. Каноническая сериализация

Консенсусные байты (входы хешей и подписей) — детерминированный бинарный формат `canonical`: целые — big-endian фиксированной ширины; байтовые строки — `u32-длина ‖ байты`; списки — `u32-количество ‖ элементы`; варианты enum — ведущий `u8`-тег. JSON (camelCase, hex для байтовых полей) — только транспорт/хранение, в хеши не входит.

### 9.4. Детерминизм

Правила FGP-CRYPTO §10 обязательны: никакой плавающей точки в consensus-путях; итерация состояний — только упорядоченные структуры (`BTreeMap`); один вход → один байтовый выход на любой платформе (native/wasm32). Нормативен batch-путь демерреджа: `(1−δ)^n` одним `pow`, не последовательное начисление.

## 10. Клиентская верификация

wasm32-сборка `flora-economy-crypto` (без изменений кода) даёт клиенту:

- полный реплей журнала и сверку head («не верь серверу»);
- проверку inclusion-доказательств отдельных записей (для лёгких клиентов);
- построение и подпись транзакций локально — секретный ключ не покидает устройство.

`cargo check -p flora-economy-crypto --target wasm32-unknown-unknown` — обязательная проверка CI (как у FRC-A/FRC-I).

## 11. HTTP API (v1)

Базовый путь `/api/economy`. Суммы — grain (число), байтовые поля — hex-строки. Ошибки — `{ "error": { "code", "message" } }`.

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/parameters` | текущие параметры |
| GET | `/commons` | казна: баланс, всего эмитировано |
| GET | `/ledger/head` | head журнала |
| GET | `/ledger/entries?from=&limit=` | страница журнала (реплей у клиента) |
| GET | `/ledger/proof/{seq}` | inclusion-доказательство |
| GET | `/accounts/{uuid}` | сводка аккаунта |
| POST | `/accounts` | открыть аккаунт `{accountUuid, ownerKeyHex}` |
| POST | `/ubi/claims` | начислить UBI `{accountUuid}` |
| POST | `/transfers` | перевод `{fromUuid, toUuid, amountGrains, nonceHex, signatureHex}` |
| POST | `/trustlines` | линия доверия `{loUuid, hiUuid, limitLoToHiGrains, limitHiToLoGrains, signatureLoHex, signatureHiHex}` |
| POST | `/credit-transfers` | платёж по цепочке `{pathUuids[], amountGrains, nonceHex, signatureHex}` |

Транспортная аутентификация (JWT) — забота хоста; **авторизация денег — криптографическая** (подписи в теле), HTTP-слой решений не принимает.

Коды ошибок: `account_not_found`, `account_exists`, `insufficient_funds`, `trustline_not_found`, `trustline_capacity_exceeded`, `ubi_already_claimed`, `personhood_required`, `invalid_signature`, `sequencing_conflict`, `invalid_hex`, `rejected`, `storage_unavailable`.

## 12. Развёртывание и статус реализации

- Флаг `Economy:Enabled` (по умолчанию **false**), путь журнала `Economy:LedgerPath`. Композиция — `flora-social::economy_router`.
- Аттестор по умолчанию — консервативный (все V0): до реализации уровней FPP модулем Verification UBI не начисляется никому; переводы/взаимный кредит работают. Fail-safe направление: не раздавать права при недоступности аттестора.
- Реализовано в v1: ядро (движок, все инварианты, Merkle, подписи), модуль (секвенсор, JSONL-журнал, HTTP, порты), композиция, wasm32-сборка ядра, 90+ тестов.
- Не реализовано (дорожная карта): Postgres-журнал + `flora-migrate`; косайнинг витнессов и внешнее якорение head; фоновый демерредж-воркер в композиции (`sweep_demurrage` готов, нужен spawn); модуль Governance (онлайн-проверка `policy_ref`); golden-векторы `Documents/test-vectors/fep/` и TS-паритет; конфиденциальность сумм (Pedersen-агрегаты — исследовательский трек, FEP-THREATS §7).
