# FRC-I — Flora Relativistic Codec — Image

**Status:** Draft (текущая линия битстрима; линия FIC v1/v2 закрыта при ребренде в FRC-I)  
**Version:** 6.7 (v7.4: directional transforms + bounded trellis, §7.12/§11.3)
**Date:** 2026-07-16
**Family:** FRC — Flora Relativistic Codec (см. [`CODECS.md`](./CODECS.md))  
**Reference implementation:** `Products/FRC/crates/frc-i` (Rust, pure std)

---

## Overview

FRC-I — нативный фото-кодек экосистемы FLORA: один контейнер, два режима.

- **Lossless** — побайтно точное восстановление: обратимое цветовое преобразование
  YCoCg-R (либо identity-RGB, либо палитра до 256 цветов — выбор кодера),
  MED-предиктор, контексты по градиентам.
- **Lossy** — перцептивное сжатие: YCbCr, опциональный сабсэмплинг 4:2:0,
  направленная **intra-предикция блоков** (v3: моды DC/V/H/TM/D45/D135;
  v7.3a: +SMOOTH от реконструированных соседей; v7.3b: chroma-from-luma),
  DCT/ADST остатка (v7.4), перцептивное квантование с dead-zone и bounded
  trellis, run/level-кодирование.

Энтропийное ядро общее для обоих режимов: **rANS** (12-битные вероятности,
статические таблицы per-tile/per-context) + **hybrid-uint токены** (алфавит 32,
старшие биты больших значений уходят сырыми). Изображение делится на
**независимые тайлы 256×256** — единица параллелизма (референсная реализация
кодирует и декодирует тайлы в потоках `std::thread::scope`; результат от числа
потоков не зависит) и локализации повреждений.

Этот документ **нормативен** и описывает текущий битстрим FRC-I: v3
(бывш. FIC v3), v4 (v3 + деблокинг-фильтр §7.6), v5 (адаптивные
суперблоки 16×16 §7.7) и v6 (блок метаданных §2.5: ICC-профиль).
Исторические отличия FIC v1/v2 сведены в §7.5
и §10. Все версии заморожены golden-векторами
(`Products/FRC/crates/frc-i/tests/data/`): декодер обязан читать
любой корректный поток любой выпущенной версии всегда.

### Design rationale (кратко)

| Решение | Мотив |
| --- | --- |
| rANS вместо Huffman (JPEG/PNG) | ~дробные биты на символ: 8–15% плотнее на типовых распределениях; скорость декодирования выше арифметического кодера |
| Малый алфавит токенов + сырые биты | компактные таблицы частот, дешёвая адаптация per-tile; старшие биты шумов несжимаемы — не тратим на них моделирование |
| Статические таблицы per-tile, не адаптивные | тайлы декодируются независимо (параллелизм), кодер двухпроходный по тайлу — дёшево |
| Независимые тайлы 256×256 | параллельный encode/decode без изменения формата; локализация повреждений |
| Intra-предикция от реконструкции (модель VP8) | межблочная корреляция уходит в предсказание до DCT: −4…−16% на фотоклассах при равном/лучшем PSNR; декодеру — один предсказатель на блок |
| Диагональные моды D45/D135 (v3) | направленные текстуры: ещё −3.3% на фото при том же наборе контекстов; кодеру +2 кандидата RD, декодеру — две таблицы копий по диагонали |
| Dead-zone квантование AC (свобода кодера) | −7..12% размера за ≤0.1 dB: слабые изолированные коэффициенты не окупают своих run/level-токенов |
| Выбор инструментов на кодере (палитра/identity/raw/моды) | декодер читает всё; эвристики кодера можно улучшать без смены версии формата |
| Чистый std, без `unsafe`, без C-зависимостей | аудируемость, WASM-декодер для Apps/Web из того же исходника, детерминизм |
| Захардкоженные константы DCT/цвета (без libm) | бит-в-бит одинаковый результат на любой платформе — golden-вектора законны |
| Lossless-схема неизменна с v1 | bias-коррекция LOCO-I и run-режим были реализованы и измерены: статические rANS-таблицы уже поглощают смещение остатков и почти бесплатно кодируют нули — обе добавки ухудшали корпус, отклонены по цифрам |
| AC-контексты по nnz соседей — отклонены | реализованы и измерены при разработке v3 (3 бакета × 4 контекста, модель JXL/AV1): +5..8% на корпусе — цена дополнительных частотных таблиц тайла выше выигрыша от условности; приёмы кодеков с адаптивными вероятностями не переносятся на статические таблицы |

## Goals & Non-Goals

**Goals:**

- Заменить PNG (lossless) и JPEG (lossy) во внутренних пайплайнах Flora с
  измеримым выигрышем размера при равном качестве.
- Гарантированный худший случай: несжимаемые данные ≤ исходника + ~0.4%.
- Декодер, безопасный для недоверенного ввода (см. §9): без паник, с лимитами.
- База для FRC-V (видео): плоскостные кодеры переиспользуются в intra-кадрах.
- **Линия v7+ (§11.3): плотность класса AVIF на реальных фото** (BD-rate
  на Kodak в пределах +10% от libaom-still) при encode ≥ 10 Мп/с и кратно
  более простом декодере. Честная точка отсчёта — §11.2.

**Non-Goals (текущая линия):**

- HDR / битовая глубина >8, EXIF (для EXIF зарезервирован тип чанка
  метаданных §2.5; ICC поддержан с v6). Битность 10/12 — после v7.
- Анимация (мультикадровость — контейнер FRC-V).
- Прогрессивная развёртка (после v7).
- Победа над AVIF/JXL «любой ценой» по одной таблице BD-rate: скорость
  encode и простота декодера — часть целевой функции, их не сдаём
  (бюджеты в §11.3).

## 1. Терминология и соглашения

- Целые числа — **little-endian**.
- Битовые потоки («сырые биты», упаковка таблиц) — **MSB-first** внутри байта,
  последний байт дополняется нулями.
- «Плоскость» — прямоугольный массив отсчётов одной компоненты, row-major.
- `bitlen(v)` — позиция старшего единичного бита (`bitlen(1)=1`, `bitlen(255)=8`).
- Диапазон плоскости `[lo, hi]` и «виртуальный сосед» `mid`:

| Плоскость | lo | hi | mid |
| --- | --- | --- | --- |
| Y (lossless), R/G/B (identity), альфа, Y/Cb/Cr (lossy) | 0 | 255 | 128 |
| Co, Cg (YCoCg-R) | −255 | 255 | 0 |
| Индексы палитры из `n` записей | 0 | n−1 | n/2 (целочисленно) |

## 2. Контейнер

```text
[Header 20 B] [Metadata block?] [Palette block?] [TileTable: n_tiles x u32] [TilePayload x n_tiles]
```

Поток обязан заканчиваться ровно на последнем тайле: лишние байты — ошибка.

### 2.1. Header (20 байт)

| Смещение | Размер | Поле | Значение |
| --- | --- | --- | --- |
| 0 | 4 | magic | `8F 46 52 49` (`\x8F` + `"FRI"`) |
| 4 | 1 | version | `1..=7`; иное → `UnsupportedVersion` |
| 5 | 1 | flags | см. ниже; неизвестные биты → отказ |
| 6 | 4 | width | u32, 1..=32768 |
| 10 | 4 | height | u32, 1..=32768 |
| 14 | 1 | bit_depth | `8` |
| 15 | 1 | quality | lossy: 1..=100; lossless: 0 |
| 16 | 1 | tile_shift | `8` (тайл 256) |
| 17 | 3 | reserved | нули; иное → отказ |

Флаги (бит 0 — младший):

| Бит | Имя | Семантика |
| --- | --- | --- |
| 0 | `LOSSLESS` | режим без потерь |
| 1 | `ALPHA` | выход декодера RGBA; есть альфа-плоскость (или альфа в палитре) |
| 2 | `CHROMA420` | сабсэмплинг цветоразностей (только lossy) |
| 3 | `IDENTITY` | lossless без цветового преобразования (плоскости R, G, B) |
| 4 | `PALETTE` | палитровый lossless: блок палитры + одна плоскость индексов |
| 5 | `DEBLOCK` | деблокинг-фильтр на выходе декодера (§7.6); только v4+, только lossy |
| 6 | `METADATA` | блок метаданных после заголовка (§2.5); только v6+, любой режим |
| 7 | reserved | обязан быть 0 |

Комбинаторика (декодер обязан проверить): `IDENTITY`/`PALETTE` только при
`LOSSLESS`; `IDENTITY` и `PALETTE` взаимоисключающи; `CHROMA420` несовместим с
`LOSSLESS`; `DEBLOCK` несовместим с `LOSSLESS` и требует `version >= 4`
(в v1–v3 бит 5 — неизвестный флаг → отказ); `METADATA` требует `version >= 6`
(в v1–v5 бит 6 — неизвестный флаг → отказ); `quality` согласован с режимом.

### 2.2. Palette block (только при `PALETTE`)

```text
u8 count_minus_1;  // записей = count_minus_1 + 1 (1..=256)
entries[count]     // RGB (3 B) или RGBA (4 B при флаге ALPHA), порядок кодера
```

Референсный кодер сортирует записи по яркости BT.601 (перцептивно близкие
цвета получают соседние индексы — MED-предсказание индексов начинает работать),
но порядок — свобода кодера, декодер трактует список как данность.

### 2.3. Тайлы

Сетка тайлов 256×256 обходится **row-major**; краевые тайлы усечены до границ
изображения. `TileTable` — длины payload'ов тайлов (u32 каждая); сумма длин
обязана совпасть с остатком потока байт-в-байт.

### 2.4. Состав payload тайла

Секции строго в порядке:

| Режим | Секции |
| --- | --- |
| `PALETTE` | 1 предиктивная (плоскость индексов) |
| `LOSSLESS` планарный | 3 предиктивные (Y, Co, Cg — либо R, G, B при `IDENTITY`) [+ альфа предиктивная] |
| lossy | 3 DCT (Y, Cb, Cr) [+ альфа предиктивная] |

Альфа-плоскость кодируется **без потерь всегда**, в полном разрешении.
После последней секции в payload тайла не должно оставаться байт.

### 2.5. Metadata block (v6+, только при `METADATA`)

Расположен **сразу после заголовка**, до блока палитры. Метаданные не влияют
на декодирование пикселей.

```text
u32 total_len;             // длина остатка блока; 1..=8 МиБ, иное → отказ
chunks[..]                 // TLV-чанки до исчерпания total_len (ровно)
  u8  type;                // тип чанка
  u32 len;                 // длина данных
  data[len]
```

Типы чанков:

| type | Содержимое |
| --- | --- |
| 1 | ICC-профиль (байты профиля как есть); повторный чанк → отказ, пустой → отказ |
| прочие | зарезервированы (EXIF и др.); декодер обязан **пропустить** незнакомый чанк |

Пропуск незнакомых типов — единственное расширяемое место формата: новые
виды метаданных добавляются без смены версии, потому что не влияют на
пиксели. Обрыв чанка за границей `total_len` и `total_len` вне лимита —
порча потока. Потолок 8 МиБ — DoS-защита декодера (аллокация до проверки
тела недопустима).

## 3. Энтропийный слой

### 3.1. Hybrid-uint токены

Беззнаковое `v < 2^20` → пара (символ алфавита 32, сырые биты):

```text
v < 16:  sym = v, сырых бит нет
v >= 16: n = bitlen(v) (5..=20); sym = 16 + (n - 5); raw = v - 2^(n-1), n-1 бит
```

Знаковые значения предварительно отображаются зигзагом:
`m(v) = (v << 1) XOR (v >> 31)` (арифметический сдвиг): 0,−1,1,−2,2 → 0,1,2,3,4.

### 3.2. rANS

32-битное состояние, нижняя граница `L = 2^23`, побайтовая ренормализация,
точность вероятностей 12 бит (сумма частот таблицы = 4096).

Провод: `[u32 LE: начальное состояние для чтения][байты потока]`.

Декодирование символа по таблице (freq[s], cum[s]):

```text
slot = x & 4095
s: cum[s] <= slot < cum[s+1]
x = freq[s] * (x >> 12) + slot - cum[s]
while x < L: x = (x << 8) | next_byte   // нет байта -> Corrupt
```

Кодер (справочно): символы кодируются в обратном порядке от состояния `L`,
`x_max = ((L >> 12) << 8) * freq`; итоговый буфер разворачивается.

**Строгость:** после последнего символа секции состояние обязано равняться
ровно `L`, все байты потока — потреблены. Иное — повреждение.

### 3.3. Таблицы частот (разреженная сериализация)

Для каждого контекста секции:

```text
u8 first_sym; u8 n_syms (1..=32, first+n <= 32);
ceil(n_syms * 12 / 8) байт: n_syms значений (freq-1) по 12 бит, MSB-first
```

Сумма частот обязана равняться 4096 (все частоты диапазона >= 1). Контекст,
не встречающийся в данных, сериализуется вырожденно: `first=0, n=1, freq=4096`.

### 3.4. Поток сырых бит

Все сырые биты секции (биты токенов, знаки уровней) пишутся подряд MSB-first
в отдельный поток. Декодер обязан потребить все его байты (частичный последний
байт дочитывается нулями-паддингом).

### 3.5. Адаптивный range-кодер (v7)

Вместо статических rANS-таблиц (§3.2–3.3) lossy-секции v7 используют
**FIFO range-кодер** (32-бит, перенос через cache/pending-FF, схема LZMA)
и **адаптивные частотные модели**. Порядок декодирования = порядку
кодирования → модель обновляется после каждого символа одинаково на
обеих сторонах. Всё целочисленно (контракт §9).

Интервал: `range_init = 0xFF000000`, ренормализация при `range < 2^24`.
Первый байт потока всегда 0 (лаг-байт); финализация — 5 сдвигов. Число
байт на выходе кодера равно числу байт, потребляемых декодером той же
последовательности; обрыв — `Corrupt`.

Модель алфавита `n ∈ {2, 4, 15, 22, 32}` (SPLIT/EOB / TX / MODE / RUN /
прочие токены): счётчики `u16`,
инкремент затухает `256 → 128 → 64 → 32` по числу обновлений; при
`total ≥ 2^13` — полуделение с полом 1. Prior зависит от вида контекста
(run: высокие 0..2; level: высокие 0..1; split: уклон к WHOLE; EOB:
равновесный). В v7 EOB — отдельный бинарный флаг, а не символ RUN.

Банк моделей: 81 контекст (§7.8) с иерархическим прогревом
(родитель группы → тёплый старт детальной модели) и order-1 бакетами
(4 шт., только для алфавитов ≥ 16). Таблицы в поток **не пишутся**.

## 4. Секции

### 4.1. Предиктивная секция (lossless-плоскости)

```text
u8 mode;                        // 0 coded, 1 raw; иное -> Corrupt
mode 0: [FreqTable x 8][u32 token_len][u32 raw_len][token bytes][raw bytes]
mode 1: [w*h отсчётов по raw_bits(range) бит, row-major, MSB-first]
```

`raw_bits(range) = max(1, bitlen(hi - lo))`: 8 для 0..=255, 9 для ±255,
`bitlen(n-1)` для палитры. Значение отсчёта = прочитанное + `lo`, кламп в
`[lo, hi]`. Режим 1 — потолок худшего случая; кодер выбирает меньшую форму.

### 4.2. DCT-секция (lossy-плоскости)

v1–v6 (статический rANS):

```text
[FreqTable x n_ctx][u32 token_len][u32 raw_len][token bytes][raw bytes]
```

`n_ctx`: **5** в v1 (§7.5), **6** в v2/v3/v4, **7** в v5/v6 (§7.7, CTX_SPLIT).

v7 (адаптивная энтропия, §3.5) — таблиц нет:

```text
[u32 token_len][u32 raw_len][arith bytes][raw bytes]
```

Банк моделей общий для всех DCT-плоскостей тайла (Y→Cb→Cr): хрома
стартует тёплой. Байта режима нет.

## 5. Lossless-кодирование плоскости

Схема идентична во всех версиях формата (см. rationale: добавки JPEG-LS
отклонены по измерениям). Растровый обход. Соседи текущего отсчёта
(`W` слева, `N` сверху, `NW` по диагонали):

```text
(x=0, y=0): W = N = NW = mid
(x=0, y>0): W = N = NW = P[0, y-1]
(x>0, y=0): W = N = NW = P[x-1, 0]
иначе:      W = P[x-1,y], N = P[x,y-1], NW = P[x-1,y-1]
```

Предсказание MED (LOCO-I):

```text
если NW >= max(W,N): pred = min(W,N)
иначе если NW <= min(W,N): pred = max(W,N)
иначе: pred = W + N - NW
```

Контекст — активность градиентов `g = |N-NW| + |NW-W|`, бакеты
`{0},{1},{2},{3..4},{5..8},{9..16},{17..32},{>32}` → контексты 0..7.

Кодируется `zigzag(value - pred)` hybrid-uint токеном в контексте, сырые биты —
в raw-поток. Реконструкция: `value = clamp(pred + residual, lo, hi)` — кламп
обязателен (детерминированное поведение на повреждённых потоках).

## 6. Цвет

### 6.1. YCoCg-R (lossless, обратимое)

```text
прямое:  Co = R - B;  t = B + (Co >> 1);  Cg = G - t;  Y = t + (Cg >> 1)
обратное: t = Y - (Cg >> 1);  G = Cg + t;  B = t - (Co >> 1);  R = B + Co
```

Сдвиги арифметические. Y ∈ 0..=255, Co/Cg ∈ −255..=255. После обратного
преобразования каналы клампятся в 0..=255 (значимо только для повреждённых
потоков — валидные обратимы точно).

### 6.2. YCbCr BT.601 full-range (lossy, фиксированная точка 16.16)

`HALF = 32768`, сдвиг 16. Константы (целые, ×65536):

```text
Y  = ( 19595 R + 38470 G +  7471 B + HALF) >> 16
Cb = ((-11059 R - 21709 G + 32768 B + HALF) >> 16) + 128
Cr = (( 32768 R - 27439 G -  5329 B + HALF) >> 16) + 128
R = Y + (( 91881 (Cr-128)                 + HALF) >> 16)
G = Y + ((-22553 (Cb-128) - 46802 (Cr-128) + HALF) >> 16)
B = Y + ((116130 (Cb-128)                 + HALF) >> 16)
```

Все компоненты клампятся в 0..=255. Плавающая точка запрещена — детерминизм.

### 6.3. Сабсэмплинг 4:2:0

Плоскости Cb/Cr тайла имеют размер `ceil(tw/2) × ceil(th/2)` и вычисляются
**в границах тайла** (тайлы полностью независимы).

Даунсэмплинг: среднее 2×2 с репликацией края при нечётных размерах,
округление `(sum + 2) >> 2`.

Апсэмплинг (билинейный, co-sited с левым верхним отсчётом):

```text
fx = x/2; nx = (x нечётный) ? min(fx+1, cw-1) : fx   (аналогично fy/ny)
out[x,y] = (c[fy,fx] + c[fy,nx] + c[ny,fx] + c[ny,nx] + 2) >> 2
```

## 7. Lossy-кодирование плоскости (intra-предикция + transform остатка)

### 7.1. Блочная структура и intra-предикция

Плоскость обходится блоками 8×8 row-major; краевые блоки добираются
**репликацией края**. Каждая плоскость (Y, Cb, Cr — в 4:2:0 хрома на своём
разрешении) предсказывается **от собственной реконструкции** внутри тайла.

Граница блока `(bx, by)` из реконструированной плоскости (`px = 8bx`,
`py = 8by`; недоступные соседи замещаются 128; координаты клампятся в
валидную область плоскости `w × h`). Верхняя строка расширена вправо на
8 отсчётов (для D45; над правым краем реплицируется последний столбец):

```text
above[i]  = py > 0 ? R[py-1, min(px+i, w-1)] : 128     (i = 0..15)
left[j]   = px > 0 ? R[min(py+j, h-1), px-1] : 128     (j = 0..7)
corner    = px > 0 && py > 0 ? R[py-1, px-1] : 128
```

Моды предсказания (значения фиксированы форматом; кодируются символом
0..=5, см. §7.3):

| Сим | Мода | pred[j][i] |
| --- | --- | --- |
| 0 | DC | `(sum(above[0..8]) + sum(left) + 8) >> 4` для всех отсчётов |
| 1 | V | `above[i]` |
| 2 | H | `left[j]` |
| 3 | TM | `clamp(left[j] + above[i] - corner, 0, 255)` |
| 4 | D45 | вниз-влево: `s = i + j`; `(above[s] + 2·above[s+1] + above[min(s+2, 15)] + 2) >> 2` |
| 5 | D135 | вниз-вправо: см. опорный ряд ниже |

D135 использует опорный ряд из 17 отсчётов вдоль границы
(левый столбец снизу вверх, угол, верхняя строка):

```text
line[j] = left[7-j]      (j = 0..7)
line[8] = corner
line[8+1+i] = above[i]   (i = 0..7)
pred[j][i] = (line[d-1] + 2·line[d] + line[d+1] + 2) >> 2,  d = 8 + i - j
```

Обе диагонали сглажены 3-отводным фильтром `(1,2,1)/4` — подавляет
ступенчатость предсказания от шумной границы.

В v5 те же шесть мод применяются и к суперблокам 16×16 (§7.7) — все
формулы масштабируются заменой 8→16 (граница `above[0..32]`, `left[0..16]`,
DC-нормировка `(sum + 16) >> 5`, D135-ряд из 33 отсчётов, `d = 16 + i - j`).

Остаток `orig - pred` преобразуется ортонормированным DCT-II (базис идентичен
ITU-T T.81); центрирования (−128) начиная с v2 нет — его роль выполняет
предсказание.

Базисные константы зафиксированы литералами f32 (арифметика f32, без FMA):

```text
A0 = 0.353_553_39         C1 = 0.490_392_64      C2 = 0.461_939_77
C3 = 0.415_734_8          C5 = 0.277_785_1       C6 = 0.191_341_72
C7 = 0.097_545_16
BASIS[u][n] = c(u) * cos((2n+1) u pi / 16), c(0)=A0, c(u>0)=C(u)
```

### 7.2. Квантование и реконструкция

Базовые матрицы — ITU-T T.81 Annex K.1 (люма) / K.2 (хрома); масштаб качества —
классическое отображение IJG:

```text
scale = q < 50 ? 5000/q : 200 - 2q
Q[i] = clamp((base[i] * scale + 50) / 100, 1, 255)
```

**Деквантование (нормативно):** `coef = c * Q[i]` (f32). Квантование —
свобода кодера: формат фиксирует только смысл `c` как множителя шага `Q[i]`.
Референсный кодер (информативно) использует dead-zone: DC округляется
классически (`+0.5`, half-away-from-zero), AC — со смещением `+0.40` к нулю
(`c = sign(t) · floor(|t| + 0.40)`, `t = coef / Q[i]`): слабые изолированные
коэффициенты обнуляются, экономя run/level-токены при потере ≤ 0.1 dB.

Реконструкция отсчёта: `clamp(round(idct + pred), 0, 255)` — она же источник
границ для следующих блоков, поэтому кодер обязан вести реконструкцию тем же
путём, что декодер.

### 7.3. Кодирование блока

Контексты DCT-секции v2/v3: `0` — DC; `1`/`2` — run в низкой/высокой зоне;
`3`/`4` — level в низкой/высокой зоне; `5` — мода предсказания.
Низкая зона — позиции зигзага ≤ 15. Зигзаг — стандартный порядок JPEG.

Порядок токенов блока: **мода → DC → AC**.

- **Мода:** символ 0..=5 в контексте 5 (сырых бит нет); символ ≥ 6 → `Corrupt`.
- **DC:** `zigzag(dc)` hybrid-uint в контексте 0 — кодируется **напрямую**,
  без цепочки: межблочную корреляцию DC уже поглотило предсказание.
- **AC:** по зигзагу с позиции 1: пары «run нулей → level»:
  - run-токен в контексте зоны позиции **начала** пробега; символ `31` = EOB
    (пробеги ≤ 62 занимают символы ≤ 17 — коллизий нет);
  - level: hybrid-uint от `|c| - 1` в контексте зоны позиции коэффициента;
    знак — 1 сырой бит (1 = отрицательный);
  - если последний ненулевой коэффициент стоит на позиции 63, EOB **не пишется**.

Декодер обязан считать позицию: выход за 63 → `Corrupt`.

### 7.4. Выбор моды кодером (информативно)

Референсный кодер считает для каждой из шести мод DCT+квантование остатка и
минимизирует полную RD-стоимость `D + λ·R`: `D` — SSE ошибки квантования в
DCT-домене (базис ортонормирован — равно SSE в пикселях), `R` — оценка
битовой стоимости токенов (константа за ненулевой коэффициент + длина
мантиссы), `λ = 0.85 · qstep²` от среднего шага матрицы (модель H.264;
плато решений широкое — калибровка 0.05..10 даёт одинаковый выбор).
При равенстве — младший символ. Формат выбор не ограничивает: любой
сигнализированный набор мод валиден.

### 7.5. Отличия битстримов v2 и v1 (декодируются всегда)

**v2:**

- Моды предсказания — только 0..=3 (DC/V/H/TM); символ ≥ 4 → `Corrupt`.
  Расширение верхней строки не используется (`above[8..16]` не читается).

**v1:**

- Intra-предикции нет: блок центрируется константой 128
  (эквивалент `pred[j][i] = 128`), моды не сигналятся.
- Контекстов 5 (без контекста моды), порядок токенов блока: DC → AC.
- **DC — цепочкой:** `zigzag(dc - prev_dc)`, где `prev_dc` — DC предыдущего
  блока плоскости тайла (init 0).

### 7.6. Деблокинг-фильтр (v4, флаг `DEBLOCK`)

Пост-фильтр **вне петли предсказания**: intra-предикция (§7.1) работает с
нефильтрованной реконструкцией — байты тайлов v4 идентичны v3, меняется
только заголовок. Фильтр применяется декодером к готовой плоскости тайла
(Y, Cb, Cr; хрома — в собственном разрешении, до апсэмплинга §6.3);
тайлы остаются независимыми.

На каждой границе блоков 8×8 (вертикальной и горизонтальной) пары
`p1 p0 | q0 q1` поперёк ребра (за краем плоскости сосед реплицируется):

```text
T = clamp(Q[0] / 2, 2, 24)          // Q[0] — DC-шаг матрицы плоскости
фильтровать, если |p0-q0| < T  и  |p1-p0| <= T/2  и  |q1-q0| <= T/2
d   = clamp((3(q0-p0) + (p1-q1) + 4) >> 3, -T, T)
p0' = clamp(p0 + d, 0, 255);  q0' = clamp(q0 - d, 0, 255)
```

Порядок нормативен: сначала все вертикальные рёбра плоскости, затем все
горизонтальные (вторые читают результат первых). Целочисленная арифметика.
Условие на соседей (`T/2`) отличает ступень квантования от настоящей детали:
контрастные рёбра не размываются. Кодер выставляет флаг при `quality < 45`
(свобода кодера); декодер обязан фильтровать всегда, когда флаг стоит.
На корпусе q=30: +0.40 dB (photo) / +0.44 dB (portrait) при нулевой цене
в байтах; шум не трогается (рёбра выше порога). В v5 фильтр действует на
той же фиксированной сетке 8×8 независимо от разбиения на суперблоки.

### 7.7. Адаптивные суперблоки 16×16 (v5)

Плоскость обходится **суперблоками 16×16** row-major. На каждый суперблок
сигналится split-решение — символ в новом контексте `6` (итого контекстов
DCT-секции v5 — семь):

- **`0` (целиком):** одна мода (§7.1, масштаб 16) + DCT 16×16 остатка.
- **`1` (расщепление):** четыре блока 8×8 row-major, каждый кодируется
  ровно как в v3 (§7.1–7.3). Подблоки, полностью лежащие вне плоскости
  (правый/нижний край), **не кодируются**.
- символ ≥ 2 → `Corrupt`.

Кодирование суперблока целиком:

- **DCT 16×16** — ортонормированный DCT-II; базис из литералов
  `cos(k·π/32)` (k = 0..=16, f32) через симметрии косинуса,
  `c(0) = 1/4`, `c(u>0) = √(2/16)`.
- **Матрица квантования** (нормативно): коэффициент `(u, v)` наследует шаг
  своей пространственной частоты — `Q16[u][v] = Q[u/2][v/2]`. Базис
  ортонормирован, поэтому одинаковый шаг даёт одинаковую пиксельную ошибку
  независимо от размера блока: качество зон 16×16 и 8×8 согласовано.
  (Удвоение шага измерено: −50% размера, но −1.9 dB на фото — отклонено.)
- **Зигзаг 16×16** — то же серпантинное правило, что и 8×8
  (начало: 0, 1, 16, 32, …). Низкая зона — позиции скана ≤ 63 (та же
  четверть скана). Run-токены до 254 не коллидируют с EOB (символ 31:
  пробеги кодируются битовой длиной, максимум — символ 19).
- Порядок токенов: **split → мода → DC → AC**; правила DC/AC — §7.3
  с заменой 63 → 255 в проверке позиции.

Реконструкция и репликация краёв — как у 8×8 (масштаб 16). Выбор
целиком/расщепление — свобода кодера (референсный: RD-сравнение обоих
вариантов с общим λ плоскости; проба расщепления идёт по реконструкции
с откатом — байты детерминированы). Гладкие зоны (небо, кожа, фон)
получают одну моду и один DC вместо четырёх — главный резерв плотности v5:
на корпусе q=75 портрет −18.5% при −0.37 dB, фото −1.2% при −0.07 dB;
графика/шум не регрессируют (RD выбирает расщепление).

### 7.8. Контексты и кодирование блоков v7

Энтропия — адаптивный range-кодер (§3.5); дерево блоков — §7.9.
Число контекстов DCT-секции: **81** (не сериализуется):

| Диапазон | Назначение |
| --- | --- |
| 0 | SPLIT узла 16×16 (алфавит 2) |
| 1 | MODE (алфавит 15; §7.10–7.11) |
| 2..5 | DC (4 бакета; референс использует только базу — условность по prev_dc отклонена A/B) |
| 6..29 | RUN (алфавит 22): 6 бакетов позиции зигзага × 4 nnz-бакета предыдущего блока |
| 30..53 | LEVEL: 6 бакетов позиции × 4 бакета магнитуды предыдущего уровня |
| 54..77 | EOB (алфавит 2): 6 бакетов позиции × 4 nnz-бакета предыдущего блока |
| 78 | SPLIT корня 32×32 |
| 79 | SPLIT узла 8×8 |
| 80 | TX (алфавит 4; §7.12) |

Позиционные бакеты 8×8: `1 / 2–3 / 4–7 / 8–15 / 16–31 / 32+`.
Перед бакетизацией позиция приводится к спектральной доле 8×8:
`pos4 << 2`, `pos8`, `pos16 >> 2`, `pos32 >> 4` (минимум 1).
nnz аналогично нормируется: `nnz4 × 4`, `nnz8`, `nnz16 / 4`,
`nnz32 / 16`, затем бакеты `0 / 1–3 / 4–9 / 10+`.

AC v7: перед каждой парой `run → level` пишется EOB-флаг в контексте
позиции начала пробега (`0` = пара следует, `1` = конец блока). RUN больше
не содержит символ 31; возможные пробеги 0..1022 дают hybrid-uint символы
0..21. Если ненулевой коэффициент занял последнюю позицию скана, отдельный
завершающий EOB не пишется. Остальной порядок токенов блока — как в v5.

### 7.9. Рекурсивное дерево блоков v7.2

Плоскость сканируется корнями 32×32 row-major. Дерево фиксированной глубины
пишется pre-order; `0 = WHOLE`, `1 = QUAD`:

```text
32×32 (CTX 78) -> whole TX32 | четыре узла 16×16
16×16 (CTX  0) -> whole TX16 | четыре узла 8×8
 8×8  (CTX 79) -> whole TX8  | четыре листа 4×4
 4×4           -> лист (split-флага нет)
```

Каждый whole/лист содержит `MODE → TX → DC → AC`. Дочерние узлы обходятся
row-major; полностью лежащие вне правого/нижнего края не пишутся.
Глубина не приходит из потока, поэтому декодирование ограничено константой
и не допускает рекурсивного DoS. Референсный кодер раскрывает неполный
корень 32×32, но декодер обязан принимать whole на краю и клиповать запись.

Для `N ∈ {4,8,16,32}` в базовом TX=0 используется ортонормированный DCT-II:
`B[u,n] = sqrt(1/N)` при `u=0`, иначе
`sqrt(2/N)·cos((2n+1)uπ/(2N))`. Зигзаг — то же диагональное серпантинное
правило для матрицы N×N. Квантование наследует относительную частоту:
`Q_N[u,v] = Q_8[floor(8u/N), floor(8v/N)]`. Предикторы §7.1 масштабируются
до N без изменения формул.

Выбор split — свобода кодера. Референс сравнивает `D + λR`, реконструирует
кандидатные дочерние узлы в порядке декодера и откатывает область при победе
whole; гладкие/контрастные узлы имеют MAD-предвыбор, а частичная сумма
стоимости даёт ранний выход. Это не часть декодерного контракта.

Публичный `encode()` продолжает писать v5 до стабилизации v7; v7 доступен
через `encode_with_version(..., 7)` / CLI `--bitstream 7`.

### 7.10. SMOOTH-предиктор v7.3a

В каждом whole/листе v7 значения MODE `0..5` — DC/V/H/TM/D45/D135
(§7.1, масштаб N из §7.9); `6` — SMOOTH. Для luma это полный допустимый
диапазон `0..6`; chroma дополнительно принимает CfL `7..14` (§7.11).
v1–v6 сохраняют прежние диапазоны мод.

Для `N ∈ {4,8,16,32}`, координат `x,y ∈ [0,N)`, верхней границы `A[x]`,
левой `L[y]`, `BL = L[N−1]` и `TR = A[N−1]`:

```text
V = ((N−1−y) * A[x] + (y+1) * BL + floor(N/2)) / N
H = ((N−1−x) * L[y] + (x+1) * TR + floor(N/2)) / N
P[x,y] = (V + H + 1) >> 1
```

Деление целочисленное с округлением вниз; входы неотрицательны. Отсутствующие
границы и расширение края формируются по правилам §7.1/§7.9 до вычисления
формулы. Один и тот же предиктор обязан использоваться encoder-реконструкцией
и decoder для всех четырёх размеров.

### 7.11. Chroma-from-luma v7.3b

CfL разрешён только в Cb/Cr whole/листьях v7. Плоскость Y кодируется и
декодируется первой; источником CfL служит её **реконструкция до деблокинга**.
При `CHROMA420=1` она приводится к размеру chroma тем же усреднением 2×2,
что §6.3: `(a+b+c+d+2)>>2`, с репликацией правого/нижнего края. При
`CHROMA420=0` используется Y 1:1. Частичный блок N×N дополняется репликацией
края по §7.9.

MODE `7..14` кодирует α в Q4 без дополнительных битов:

| MODE | 7 | 8 | 9 | 10 | 11 | 12 | 13 | 14 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| α Q4 | −8 | −4 | −2 | −1 | +1 | +2 | +4 | +8 |
| α | −1/2 | −1/4 | −1/8 | −1/16 | +1/16 | +1/8 | +1/4 | +1/2 |

Для N∈{4,8,16,32}, реконструированного luma-блока `Y[i]` и обычного
DC-предиктора chroma `DC` от уже реконструированных chroma-границ:

```text
meanY = (sum(Y[i]) + N*N/2) / (N*N)
t     = alphaQ4 * (Y[i] - meanY)
delta = t >= 0 ? (t + 8) >> 4 : -((-t + 8) >> 4)
P[i]  = clamp(DC + delta, 0, 255)
```

Все деления целочисленные; половины округляются от нуля. Encoder обязан
строить residual и собственную реконструкцию от той же уже
реконструированной Y, а не от исходной luma. CfL в Y либо MODE ≥15 —
`Corrupt`. Decoder принимает CfL и для 4:4:4; reference encoder после A/B
эмитит его только для 4:2:0.

Выбор α — свобода кодера. Reference encoder оценивает
`round(16*cov(C-DC,Y-meanY)/var(Y))`, ограничивает `[-8,+8]`, округляет к
ближайшему множеству `{±1,±2,±4,±8}` (при равенстве — меньшая магнитуда)
и добавляет ровно один CfL-кандидат к SAD/RD-перебору базовых мод. Это
encoder-only оптимизация; на wire всегда допустимы все восемь значений.

### 7.12. Направленные transform и bounded trellis v7.4

После MODE каждый whole/лист v7 содержит символ TX в контексте 80:

| TX | Вертикальный базис | Горизонтальный базис |
| --- | --- | --- |
| 0 | DCT-II | DCT-II |
| 1 | ADST (DST-VII) | DCT-II |
| 2 | DCT-II | ADST (DST-VII) |
| 3 | ADST (DST-VII) | ADST (DST-VII) |

TX ≥4 — `Corrupt`. Для `N ∈ {4,8,16,32}`, пространственного residual
`R[y,x]`, вертикального базиса `V` и горизонтального `H`:

```text
DCT[k,n]  = sqrt(1/N), k=0
            sqrt(2/N) * cos((2n+1)k*pi/(2N)), k>0
ADST[k,n] = 2/sqrt(2N+1) * sin((2n+1)(k+1)*pi/(2N+1))
F[u,v]    = sum_y sum_x V[u,y] * H[v,x] * R[y,x]
R[y,x]    = sum_u sum_v V[u,y] * H[v,x] * F[u,v]
```

Оба базиса ортонормированы. Reference implementation строит ADST из
зафиксированных литералов `sin(k*pi/(2N+1))`; runtime-тригонометрия запрещена.
Координата коэффициента `(u,v)`, зигзаг и шаг `Q_N[u,v]` остаются §7.9
независимо от TX. Decoder сначала деквантует `F = c*Q_N`, затем применяет
обратный separable transform и складывает результат с predictor.

Выбор TX и trellis — свобода кодера. Reference encoder после RD-выбора MODE
сравнивает четыре TX по SSE квантования и требует от альтернативы меньшей
ошибки, не позволяя приблизительной rate-модели покупать разреженность ценой
качества. Затем encoder-only bounded trellis:

1. уточняет ненулевую магнитуду среди соседних уровней;
2. проходит AC в обратном зигзаге и может обнулить узел;
3. при удалении объединяет соседние run-рёбра, поэтому решение учитывает
   `EOB → run → level`, а не только независимый коэффициент.

Trellis использует transform-domain SSE и `λ_trellis = 0.02 * λ_plane`;
его решения не сигналятся отдельно. Identity/transform-skip остатка был
измерен, дал регрессию и **не входит** в wire-набор.

## 8. Метаданные и выбор кодера

Решения кодера (не влияют на способность декодера читать поток):

- **Палитра**: если уникальных RGBA ≤ 256 и палитровый поток меньше —
  выбирается палитра. Это верно и в lossy-запросе: малоцветная графика
  получает *точный* поток меньшего размера, чем DCT.
- **Identity vs YCoCg-R**: по субвыборке (~64k пикселей) оценивается энтропия
  MED-остатков в обоих пространствах (с потолком raw-fallback); identity
  выбирается при выигрыше > 2%.
- **Raw-fallback** на секцию: coded-форма больше сырой → пишется сырая.
- **4:2:0**: автоматически при `quality <= 85`.
- **Версия lossy-потока**: v5 (суперблоки §7.7) по умолчанию; lossless — v3.
  Экспериментально v7 (§3.5/§7.8–7.12) — через явный запрос версии. При ICC —
  v6 (§2.5).
- **Деблокинг** (§7.6): флаг ставится автоматически при `quality < 45` —
  там, где блочность заметна.
- **Split-решение** на суперблок 16×16 (v5): RD-сравнение «целиком» против
  «четыре 8×8» (§7.7) с тремя ускорителями (свобода кодера, суммарно
  encode ×1.3 при −0.7% размера корпуса q=75):
  - предвыбор по активности квадрантов (MAD 8×8): все ≤ 4 → WHOLE без
    пробы; контраст квадрантов ≥ 12 → QUAD без пробы 16×16; все ≥ 16
    (равномерный шум/текстура) → WHOLE (AC умирают, один DC дешевле
    четырёх — на шуме это ещё и −2.6% размера);
  - ранний выход из пробы расщепления: частичная сумма стоимостей 8×8
    превысила стоимость 16×16 → победитель ясен;
  - отклонено (измерено): QUAD при одном насыщенном квадранте — +2%.
- **Дерево v7.2** (§7.9): те же RD/предвыбор/ранний выход применяются
  на глубинах 32/16/8; для split 8→4 добавлена компенсация четырёх
  DC/mode-токенов в rate-оценке. Неполный корень 32×32 форсированно
  раскрывается, чтобы репликация края не смещала сравнение.
- **SAD-предотбор мод** (§7.4): полный RD только для 4 лучших из 6 мод
  в v3/v5 и из 7 базовых + одного CfL-кандидата в reference v7 chroma
  (для 16×16 — топ-3, для 32×32 — топ-2: DCT дороже, разброс мод меньше);
  нейтрален по размеру на q=75.
- **Линейность DCT** для DC/V/H: спектр остатка = F(orig)−F(pred) без
  полного DCT предсказания; аналитические F(DC), F(строки), F(столбца).
- **Мода intra-предикции** на блок: RD-перебор шести мод в v3/v5 (§7.4);
  в v7 — семи базовых (§7.10) и, для chroma, CfL (§7.11).
- **Dead-zone** при квантовании AC (§7.2), **адаптивный по активности блока**
  (adaptive quantization, перцептивное маскирование): активность — среднее
  абсолютное отклонение отсчётов блока-источника от среднего; bias линейно
  интерполируется от `0.40` (активность ≤ 4, гладкие зоны — защита градиентов)
  до `0.18` (активность ≥ 16, текстуры маскируют ошибку квантования).
  На корпусе q=75: −8.4% суммарного размера при неизменном PSNR фотоклассов
  (весь выигрыш — обнуление шумовых AC, которых не видно). Свобода кодера —
  формат фиксирует только деквантование `c * Q[i]`.

## 9. Требования к декодеру (нормативные)

1. **Никаких паник / UB** на произвольных байтах: только `Ok` или типизированная
   ошибка. Арифметика на недоверенных значениях — checked/wrapping (включая
   usize-переполнения на 32-битных платформах).
2. **Аллокации только после** валидации заголовка и проверки лимитов
   (`max_pixels`, по умолчанию 2^26; стороны ≤ 32768).
3. **Строгость структуры**: длины секций/тайлов сходятся байт-в-байт; финальное
   состояние rANS = `L`; потоки потреблены полностью; резервные поля нулевые;
   неизвестные флаги/версии — отказ (`UnsupportedFeature`/`UnsupportedVersion`).
4. **Клампы реконструкции** (предиктивная плоскость, выход IDCT, обратный цвет)
   обязательны и детерминированы.
5. Повреждённый поток не должен стоить более O(размер заявленного изображения)
   памяти и времени.

Реализация подтверждает контракт тестами: случайный мусор, обрезка валидного
потока на каждом байте, побитовые мутации, злонамеренные заголовки/таблицы.

## 10. Версионирование и заморозка

- Форматы v1–v6 **заморожены**; v7 — в разработке (decode обязателен с этой
  сборки, encode — по флагу). Любое изменение битстрима — новая версия
  (byte 4); исключение — новые **типы чанков метаданных** (§2.5).
  Кодер пишет v3 для lossless и v5 для lossy (деблокинг-флаг при
  `quality < 45`), v6 — при ICC, v7 — по явному запросу.
- Golden-вектора: `Products/FRC/crates/frc-i/tests/data/*.fri` +
  FNV-1a-хеш пиксельного выхода.
  - `golden-v1-*.fri`, `golden-v2-*.fri` — **decode-заморозка**: файлы
    закоммичены навсегда и не регенерируются; тесты проверяют только
    декодирование.
  - `golden-v3-*.fri` … `golden-v6-*.fri` — **encode-заморозка**
    (v3/v4 — через явную `encode_with_version`, v6 — `encode_with_icc`);
    регенерация — только осознанным решением:
    `FRC_I_UPDATE_GOLDEN=1 cargo test -p frc-i --test golden`.
- Кодер можно улучшать свободно (эвристики §8), пока поток корректен для
  своей версии; golden-вектора v3..v6 при этом обновляются в том же изменении.

## 11. Результаты, честный baseline и путь к AVIF

### 11.1. Синтетический корпус (исторические замеры v3–v5)

Синтетический корпус (512×512: фото с текстурами, портрет, графика, белый шум),
release-сборка; сравнение с `image` crate (PNG CompressionType::Best/Adaptive,
JPEG q=75). Измерено 2026-07-15 (кодер v5: суперблоки + AQ), x86-64:

| Изображение | PNG | FRC-I-lossless | JPEG q75 (PSNR) | FRC-I v5 q75 (PSNR) |
| --- | --- | --- | --- | --- |
| photo-512 | 221 536 | 170 705 (**−22.9%**) | 19 215 (44.42) | 12 193 (**−36.5%**, 43.97) |
| portrait-512 | 104 923 | 94 797 (**−9.7%**) | 12 100 (48.94) | 4 542 (**−62.5%**, 47.66) |
| graphics-512 | 4 192 | 1 951 (**−53.5%**, палитра) | 21 658 (41.62) | 1 951 (**точный**, в 11 раз меньше) |
| noise-512 | 787 132 | 786 480 (−0.1%, raw-потолок) | 328 987 (22.28) | 121 353 (12.16)* |

Итого lossy по корпусу: **−63.3%** против JPEG при сопоставимом PSNR
(q=30 с деблокингом: −71.3%, q=90: −24.1%).

> **Предупреждение о репрезентативности.** Этот корпус полезен для
> регрессионного контроля инструментов, но среднее по нему завышено
> классами portrait (огромные гладкие зоны) и graphics (палитра, выигрыш
> 11×). На реальных фотографиях картина другая — см. §11.2. Конкурентные
> заявления по §11.1 не делаются.

Вклад инструментов по версиям (q=75, photo/portrait):

- dead-zone AC (`+0.40`, v3-кодер): −12.7% / −7.6% размера за −0.08 / −0.01 dB;
- диагональные моды D45/D135 + RD-выбор (v3): ещё −3.2% / +1.2% при +0.05 dB;
- adaptive quantization по активности блока (§8, v3-кодер):
  −8.4% суммарного размера корпуса q=75 при неизменном PSNR фотоклассов;
- деблокинг-фильтр (§7.6, v4): +0.40 / +0.44 dB на q=30 бесплатно по байтам;
- суперблоки 16×16 (§7.7, v5): photo −1.2% (−0.07 dB),
  **portrait −18.5% (−0.37 dB)** — гладкие зоны схлопываются в один блок;
  graphics/noise без регрессии (RD выбирает расщепление);
- nnz-контексты AC (JXL/AV1): **+5..8% — отклонены** (см. rationale).

Скорость lossy (без SIMD, тайловый параллелизм, здесь 4 тайла): ~34 Мп/с
encode на q=75 (~37 на q=30, ~21 на q=90 — больше выживших AC),
~105 Мп/с decode; на изображениях с большим числом тайлов масштабируется
до числа ядер.

\* Белый шум вне перцептивной модели: FRC-I агрессивно квантует
высокочастотный шум (PSNR ниже), JPEG тратит на его сохранение в 2.4 раза
больше байт. Для реальных фото важен первый столбец пары.

Закрытые пункты старого roadmap: суперблоки 16×16 (v5, §7.7), деблокинг
(v4, §7.6), adaptive quantization (v3-кодер, §8), ICC (v6, §2.5),
скорость encode ≥ 30 Мп/с (эвристики §8). Открытые пункты слиты
в план §11.3.

### 11.2. Честный baseline: Kodak 24 против AVIF/JXL/JPEG

Первый прогон против реальных конкурентов на реальных фотографиях.
Полигон: `Tools/frc-i-compete/run_compete.py` (корпус Kodak 24 768×512,
лестницы качества всех кодеков, PSNR(RGB), BD-rate Bjøntegaard;
отчёт — JSON). Кодеки: FRC-I v5 (release), JPEG/AVIF/JXL — ffmpeg
(libaom-av1 `still-picture`, libjxl). Измерено 2026-07-15, x86-64.

**BD-rate** (меньше = лучше; медиана по 24 кадрам близка к среднему):

| Пара | BD-rate | Комментарий |
| --- | --- | --- |
| FRC-I vs JPEG | **+11.9%** | на реальных фото мы пока *хуже* JPEG |
| FRC-I vs JXL | **+37.1%** | |
| FRC-I vs AVIF | **+90.5%** | ~2× битрейт при равном PSNR; разброс +54…+144%, выигрышей нет |
| AVIF vs JPEG | −41.8% | контроль: полигон воспроизводит известное соотношение |
| JXL vs JPEG | −14.0% | контроль (PSNR занижает JXL — он оптимизируется под butteraugli) |

Сумма размеров при ~38 dB PSNR (24 кадра): AVIF 1.58 МБ, JXL 2.09 МБ,
JPEG 2.20 МБ, **FRC-I 2.76 МБ**. Скорость encode mid-quality:
**FRC-I ~23 Мп/с**, JXL ~5.2, JPEG ~9.2 (ffmpeg), AVIF ~0.6 —
**FRC-I в ~35–40 раз быстрее AVIF**. Контроль на `cpu-used=1`
(медленный/лучший aom, 6 кадров): разрыв тот же (+94.5%) — дело не в
режиме кодера AVIF.

Выводы, зафиксированные как факты для планирования:

1. Заявление «−63% vs JPEG» из §11.1 на реальные фото **не переносится**:
   на Kodak мы отстаём и от JPEG (+11.9%). Kodak-BD-rate — единственная
   метрика плотности для конкурентных решений с этого момента.
2. Разрыв с AVIF (~2×) — это класс инструментов (энтропийное
   моделирование, разбиение, предикция), а не тюнинг эвристик §8.
3. Уже достигнутое преимущество — скорость (35–40× encode) и простота
   декодера (§9, чистый std, wasm в десятки КБ). Его не сдавать: бюджет
   замедления encode на весь путь §11.3 — не более ~3× от текущего.
4. PSNR — рабочая метрика полигона, но перцептивный зазор AVIF/JXL она
   занижает; с v7 в полигон добавляется SSIM/butteraugli-класс метрика.

### 11.3. Путь к AVIF (нормативный план линии v7+)

Цель линии: **BD-rate vs AVIF (libaom, still) на Kodak в коридоре
0…+10%** при encode ≥ 10 Мп/с. Арифметика от §11.2 (+90.5% vs AVIF):
нужно **−42%** нашего битрейта. «Убить AVIF» — выиграть одновременно
по (плотность × скорость × простота).

Ядро (`frc-i`) **не переписывается**. Lossy-моделирование — битстрим
**v7**, инкрементально за флагом кодера до стабилизации.

Этапы и **фактические** цифры (полигон Kodak, PSNR BD-rate):

1. **v7.1/v7.1b — адаптивная энтропия (§3.5, §7.8).** Сделано
   (экспериментально). Range-кодер + адаптивные модели, 78 контекстов
   (nnz × позиция), бинарный EOB, RUN-алфавит 20,
   иерархический прогрев, order-1 на токенах, prior по виду контекста.
   **Факт v7.1b (Kodak 24, 2026-07-16):** **−3.6% BD-rate vs v5**;
   vs AVIF **+75.6%**. Бинарный EOB дал ещё **−0.20% среднего размера**
   поверх v7.1: лучше во всех 216 точках лестницы, диапазон −0.55…−0.01%.
   Скорость encode ~22.2 Мп/с (v5 ~23.1 Мп/с в том же прогоне).
   Order-1 для малых алфавитов SPLIT/EOB/MODE дал +0.12% и отклонён.
   **Вывод:** ожидание −15…−25% было завышено — двухпроходный
   статический rANS уже близок к оптимуму по токенам тайла; адаптив
   снимает цену таблиц и открывает богатые контексты, но сам по себе
   не даёт главного скачка. v7.1b оставлен из-за стабильного выигрыша
   при малой сложности; дальнейший основной рычаг — v7.2.
   Порог отсечения (§11.3 правила) не сработал: этап принят как
   инфраструктура при малом замедлении.
2. **v7.2 — рекурсивное разбиение 32×32 → 4×4 (§7.9).** Сделано
   (экспериментально). Фиксированное quadtree 32→16→8→4, DCT4/DCT32,
   отдельные split-контексты глубины и RD-выбор с откатом реконструкции.
   **Факт (Kodak 24, 2026-07-16):** **−2.26% BD-rate vs v7.1b**,
   накопительно **−5.73% vs v5** и **+71.8% vs AVIF**. При одинаковом
   quality размер +1.82%, PSNR +0.22 dB — BD-rate учитывает обмен честно.
   Encode ~13.7 Мп/с (v5 ~18.4 в том же прогоне), цель ≥10 сохранена.
   Первоначальное ожидание −8…−15% не подтвердилось: квадратное дерево
   улучшает локальную адаптацию, но без более сильных предикторов часто
   покупает качество дополнительными DC/mode-токенами. Этап принят:
   вклад >2%, фиксированная глубина и бюджет скорости соблюдены.
3. **v7.3 — предикция.**
   - **v7.3a — SMOOTH (§7.10): сделано (экспериментально).** Один линейный
     двумерный предиктор, wire ID 6, одинаковая целочисленная формула для
     4/8/16/32. **Факт (Kodak 24, 2026-07-16): −0.80% BD-rate vs v7.2**,
     улучшение на всех кадрах (−1.95…−0.14%); накопительно **−6.49% vs v5**
     и **+70.3% vs AVIF**. При одинаковом quality размер −0.89%, PSNR
     +0.006 dB. Encode ~14.8 Мп/с (v5 ~20.5 в том же прогоне).
   - A/B-отсечение: D63/D117/D153 по отдельности дали +0.34/+0.14/+0.32%
     на smoke-8 и удалены; SMOOTH_V/H нейтральны (+0.02/+0.00%), а
     квадратические веса дали +0.03% против линейных. В bitstream оставлен
     только стабильный победитель. Вклад меньше 2%, но этап принят как
     бесплатное по скорости улучшение всех 24 кадров.
   - **v7.3b — chroma-from-luma (§7.11): сделано (экспериментально).**
     Восемь signed Q4 slopes кодируются MODE 7..14; predictor использует
     реконструированную Y до деблокинга и работает для 4/8/16/32. Reference
     encoder эмитит CfL только в 4:2:0 и по covariance выбирает один α для
     SAD/RD. **Факт (Kodak 24, 2026-07-16): −1.57% BD-rate vs v7.3a**,
     улучшение на всех кадрах (−3.73…−0.26%); накопительно **−7.93% vs v5**
     и **+67.4% vs AVIF**. При одинаковом quality размер −0.41%, PSNR
     +0.072 dB. Encode ~13.4 Мп/с (v5 ~18.3 в том же прогоне), бюджет ≥10
     сохранён. Exhaustive-перебор восьми α был на 0.28% хуже: близкие CfL
     варианты вытесняли базовые моды из короткого RD shortlist.
   - A/B-отсечение v7.3b: CfL в 4:4:4 терял ~0.05 dB на q90/95 и отключён
     в reference encoder; исходная широкая сетка `±1/4,±1/2,±1,±2` давала
     смешанные регрессии. Степенная сетка `±1/16..±1/2` улучшила все 24
     кадра. Тонкие углы не возвращать без исправления RD/rate-модели.
4. **v7.4 — направленные transform + bounded trellis (§7.12): сделано
   (экспериментально).** Wire-набор: DCT_DCT, ADST_DCT, DCT_ADST,
   ADST_ADST для 4/8/16/32; TX — отдельная адаптивная модель. Encoder выбирает
   TX по минимальной ошибке квантования, затем уточняет уровни и обнуляет
   run-связанные AC обратным проходом. **Факт (Kodak 24, 2026-07-16):
   −8.90% BD-rate vs v7.3b**, улучшение на всех кадрах
   (−11.25…−6.46%); накопительно **−15.73% vs v5** и **+60.36% vs AVIF**
   (медиана +56.10%). При одинаковом quality размер −15.76%, PSNR −0.417 dB:
   trellis существенно перенастроил шкалу качества, а BD-rate сравнивает
   кривые при равном PSNR. Encode ~11.1 Мп/с (v5 ~23.4 в том же прогоне) —
   бюджет ≥10 сохранён с небольшим запасом.
   - A/B-отсечение v7.4: полный ADST-набор без trellis дал −3.90% на smoke-3;
     только одноосевые transform — −3.71%, только ADST_ADST — −2.70%.
     Identity/transform-skip дал **+8.41%** и удалён из encoder и wire.
     Trellis `λ` 0.01 дал −6.92%, 0.02 — −8.86% на smoke-3; слишком сильный
     0.35 разрушал качество. Повторный transform победителя устранён, чтобы
     удержать скорость.
5. **v7.5 — CDEF-класс фильтр.** Ожидание: **−2…−5%** перцептивно.

Пересчёт от факта v7.4: до AVIF остаётся +60.36%, то есть для верхней
границы цели +10% нужно ещё около **−31.4%** текущего битрейта. Ожидаемых
−2…−5% от v7.5 недостаточно; понадобится v7.6+ и отдельная оптимизация
скорости, поскольку запас до порога 10 Мп/с сократился до ~11%. План
пересчитывается после каждого этапа; этапы с вкладом < 2% BD-rate при >20%
замедления encode отклоняются.

Правила линии v7:

- **Полигон — арбитр.** `run_compete.py --frc-bitstream 7` на Kodak
  до слияния; цифры фиксируются здесь.
- **Заморозка:** v1–v6 навсегда; v7 — golden при стабилизации битстрима.
- **Контракт §9:** целочисленные детерминированные CDF, лимиты памяти,
  независимые тайлы.
- **Бюджет wasm-декодера:** ≤ ~2× текущего после всей линии v7.
- Битность 10/12 и прогрессив — после v7.

## 12. Интеграция в Flora (границы модулей)

- Кодек — **функциональный продукт** без бизнес-логики:
  `Products/FRC/crates/frc-i` (семейство FRC, см. §2.0
  `next-architecture.md`). Никаких зависимостей на модули; модули используют
  кодек через свой Infrastructure-слой.
- Владелец пайплайна фото постов — `Flora.Content`; аватарки — `Flora.Users`;
  E2E-вложения шифруются **после** кодирования на клиенте (модель доверия
  [`CODECS.md`](./CODECS.md) не меняется).
- Ввод FRC-I в прод — отдельная задача с миграционным планом (сервер продолжает
  отдавать AVIF/JPEG старым клиентам; `Accept`-переговоры). До этого FRC-I живёт
  как библиотека + CLI (`flora-codec image ...`).
- Расширение файлов `.fri`, предлагаемый MIME — `image/x-flora-frc-i`.
