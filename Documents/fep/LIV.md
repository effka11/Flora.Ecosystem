## Overview

**LIV** (Leaves) — криптовалюта экосистемы Flora: учётная единица FEP с криптографической авторизацией владения (Ed25519), публичным проверяемым журналом класса Certificate Transparency и внешним витнесс-косайнингом. Экономика LIV (сколько эмитируется, как ржавеет, как работает взаимный кредит) нормирована в [FEP.md](FEP.md); этот документ фиксирует **валютный слой**: единицы и канонический формат сумм, модель ключей и кошелька, протокол витнессов и верификацию клиентом.

LIV сознательно **не** является:

- блокчейн-активом с PoW/PoS-консенсусом — оба отвергнуты аксиоматически (FGP A2: капитал не покупает консенсус; FEP §0);
- спекулятивным инструментом/store of value — демерредж делает накопление невыгодным by design;
- анонимной наличностью — аккаунт равен подтверждённому человеку (FPP) или commons-структуре; Sybil-защита эмиссии важнее анонимности кошельков.

Целостность обеспечивается не гонкой капитала, а **проверяемостью**: любой клиент реплеит журнал тем же детерминированным ядром (wasm32-сборка `flora-economy-crypto`), сверяет head и inclusion/consistency-доказательства, а независимые витнессы косайнят head — скрытый форк истории становится криптографически доказуемым событием.

## 1. Термины

| Термин | Определение |
| --- | --- |
| **LIV / liv** | Учётная единица; тикер `LIV`. 1 liv = 10⁶ grain (FEP §1). |
| **grain** | Атом учёта, `i64`. Все консенсусные суммы — целые grain. |
| **Кошелёк** | Клиентское хранилище ключей Ed25519 + логика построения/подписи транзакций. Секретный ключ не покидает устройство. |
| **Секвенсор** | Единственный писатель журнала (application-слой `flora-economy`), FEP §6.3. |
| **Head / STH** | `{size, lastEntryHash, merkleRoot, at}` — вершина журнала; Signed Tree Head в терминах CT. |
| **Витнесс** | Независимый наблюдатель с ключом Ed25519 из публичного реестра, косайнит head (§4). |
| **Косайн** | `HeadCosign {head, witness, signature}` — подпись витнесса над каноническими байтами head. |

## 2. Единицы и канонический формат сумм

### 2.1. Единицы

Норма — FEP §1: `1 LIV = 10⁶ grain`, суммы — целые `i64` grain, дробных grain не существует, отрицательные балансы запрещены инвариантом (позиции взаимного кредита — знаковые).

Константы кода: `LIV_TICKER = "LIV"`, `LIV_DECIMALS = 6`, `LIV_IN_GRAINS = 1_000_000` (`flora-economy-crypto::amount`).

### 2.2. Канонический текстовый формат (нормативно)

Одна форма на все клиенты и документы — суммы сравнимы строкой:

```
canonical-liv = ["-"] целая-часть "." ровно-6-цифр
```

- `Grains::format_liv`: целая часть без ведущих нулей (кроме `0`), точка, **ровно 6** знаков дроби: `1.500000`, `0.000001`, `-2.250000`.
- Никаких локалей, разделителей групп, экспонент, пробелов, знака `+`.
- `Grains::parse_liv` принимает также сокращённые формы (`5`, `5.1`, `.5`), но **не более 6** знаков дроби; всё остальное отвергается (`None`), включая переполнение `i64`.
- Плавающая точка в обработке сумм запрещена на любом слое, включая UI-парсинг (JS `number` теряет точность выше 2⁵³ grain).

Golden-вектор: `fep-liv-amounts-v1.json` (формат, парсинг, отказы).

### 2.3. Отображение

Рекомендация UI (не норматив): символ `🍃`, сокращение хвостовых нулей допустимо **только** при отображении (не при передаче/хранении). Любое значение, покидающее клиент (API, QR, ссылки), — канонический формат §2.2 либо целые grain.

## 3. Идентичность, ключи, кошелёк

### 3.1. Аккаунт = человек

`AccountId` равен UUID пользователя Flora; UBI-эмиссия требует активной personhood-аттестации **V1+** (FPP §2) через порт `PersonhoodAttestor`. Commons-структуры имеют аккаунты без права UBI. Второй кошелёк = вторая личность = стоимость подделки `C_identity` (FEP §2.2) — дробление балансов не обходит ни демерредж, ни Sybil-экономику.

### 3.2. Ключи владения

- Схема — Ed25519 (RFC 8032), ключ генерируется **на устройстве**; сервер видит только публичный ключ (запись `AccountOpened`).
- Ядро не содержит CSPRNG (чистый wasm32-граф): генерация ключей — задача клиентского SDK/платформы, подпись и верификация — детерминированные функции ядра.
- Подписи всегда доменно-тегированы (FEP §9.2): подпись перевода не может быть переиспользована как подпись линии доверия и наоборот.

### 3.3. Обязанности кошелька (нормативно)

1. Хранить seed в защищённом хранилище платформы (Keychain/Keystore/защищённый бэкап FSCP-класса).
2. Строить канонические байты транзакции ядром (или бит-в-бит совместимой реализацией, проверенной по golden-векторам) и подписывать локально.
3. Генерировать `nonce` (16 байт) криптографически случайно; nonce одноразов на весь журнал — потерянный ответ сервера можно безопасно ретраить тем же nonce (идемпотентность).
4. Отображать суммы по §2.2.
5. Периодически верифицировать журнал: реплей (полные клиенты) либо inclusion/consistency-доказательства + сверка косайнов (лёгкие клиенты, §5).

### 3.4. Потеря и компрометация ключа

v1 не содержит протокольной ротации ключа владения (нет записи `OwnerKeyRotated`). Восстановление — социальная процедура через онбординг-порт (новый аккаунт + добровольный перевод остатка при доступном старом ключе). Автоматическая «замена ключа по решению оператора» отвергнута: она была бы каналом конфискации. Протокольная ротация с доказательством владения — кандидат FEP v1.x (R3, см. §7).

## 4. Витнесс-протокол

### 4.1. Модель доверия

Секвенсор один; его честность **проверяется**, а не предполагается (FEP §6.3). Витнессы — независимые наблюдатели, реплеящие журнал (или проверяющие consistency-цепочку head'ов) и подписывающие увиденное. Скрытый форк требует показать двум сторонам две истории одного `size` — два валидных косайна с разными `merkleRoot` от одного витнесса (или от двух, сверивших ленты) = криптографическое доказательство измены → лестница деградации FGP §7.3, экономика замирает в read-only.

### 4.2. Реестр витнессов

- Реестр — список публичных ключей Ed25519; параметр развёртывания (`Economy:Witnesses`, массив hex-ключей), подконтрольный governance классом **R2** (как параметры FEP).
- Пустой реестр допустим (bootstrap): протокол работает, эндпоинты возвращают пустой список косайнов — клиенты видят степень внешней заверенности head и могут повышать требования по мере зрелости сети.
- Политика кворума (сколько косайнов считать «достаточно») — клиентская/governance-политика, не консенсусное правило v1.

### 4.3. Косайн (нормативно)

```
HeadCosign {
  head:      LedgerHead,        // то, что витнесс видел
  witness:   PublicKeyBytes,    // Ed25519, 32 байта
  signature: SignatureBytes,    // 64 байта
}
signature = Ed25519.sign(witness_secret, "flora/economy/v1/ledger/sth" ‖ head.canonical_bytes())
```

`head.canonical_bytes()` — канонический бинарный формат FEP §9.3 (`size ‖ last_entry_hash ‖ merkle_root ‖ at`). JSON-представление (hex-поля, camelCase) — транспорт.

Сервер принимает косайн, только если **все** проверки прошли:

1. `witness` ∈ реестр (иначе `403 unknown_witness`);
2. подпись валидна (иначе `401 invalid_signature`);
3. head существует в **его** истории: `size ≤` текущего, `lastEntryHash`, `merkleRoot` и `at` совпадают с историей журнала на этом размере (иначе `409 cosign_mismatch` — попытка скормить серверу чужой/форкнутый head фиксируется).

Косайны идемпотентны по паре `(witness, head.size)`; сервер хранит все принятые косайны durable (sidecar `<LedgerPath>.cosigns.jsonl`) и отдаёт в STH самый свежий от каждого витнесса. Косайн более раннего head валиден (витнесс отстаёт) и не затирает более свежий.

### 4.4. Протокол витнесса

Витнесс-демон (вне ядра v1; reference-реализация — `Products/FEP/crates/flora-economy-witness`: keygen, state-файл последнего подписанного head, incident-файлы с уликами, exit-код 2 при форке). Reference-цикл:

1. `GET /api/economy/ledger/sth` → head.
2. Если видел head раньше — проверить consistency-доказательство `GET /ledger/consistency?oldSize=<прежний>&newSize=<текущий>` (append-only не нарушен); полный витнесс дополнительно реплеит новые записи `GET /ledger/entries`.
3. Подписать head (`cosign_head`) и отправить `POST /api/economy/ledger/cosigns`.
4. Расхождение (consistency не сходится, реплей падает, сервер отверг валидный косайн текущего head) — публичный инцидент: витнесс публикует свой последний подписанный head; сравнение подписанных head'ов и есть форк-детект.

## 5. Верификация клиентом

Три уровня, по возрастанию стоимости:

| Уровень | Что проверяет | Механизм |
| --- | --- | --- |
| L0 (кошелёк) | «моя операция в журнале» | inclusion-доказательство `GET /ledger/proof/{seq}` против head |
| L1 (лёгкий клиент) | «журнал только дописывается» | consistency между запомненным и текущим head + косайны витнессов |
| L2 (полный клиент) | «вся экономика честна» | полный реплей wasm-ядром: все инварианты FEP §7, сверка head бит-в-бит |

Правила L1 (нормативно): клиент **хранит** последний проверенный head; при каждом обновлении запрашивает consistency-доказательство от него к новому и проверяет `merkle::verify_consistency` (RFC 9162); сверяет косайны (`verify_head_cosign` + принадлежность реестру); понижение `size` или неверифицируемый переход — сигнал форка, клиент прекращает доверять серверу и поднимает инцидент (FGP §7.3).

Реализация клиента: L0/L1 — чистый TS (`@flora/client-core/economy`: `verifyEntryInclusion`, `advanceTrustedHead`, `replayHashChain`); L2 — `FepWasmVerifier` поверх `flora-economy-wasm` (тот же детерминированный код ядра, что и на сервере). Кошелёк (ключи, канонические байты, подписи транзакций) — там же, приватный ключ не покидает устройство.

Алгоритмы Merkle — RFC 6962/9162, домены `flora/economy/v1/merkle/{leaf,node}`; эталоны — `fep-ledger-transcript-v1.json` (позитив) и `fep-ledger-negative-v1.json` (обязательные отказы).

## 6. HTTP-поверхность валюты

Дополнение к FEP §11 (базовый путь `/api/economy`):

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/ledger/sth` | `{head, witnesses[], cosigns[]}` — head + реестр + свежайший косайн каждого витнесса |
| POST | `/ledger/cosigns` | приём косайна витнесса (тело — JSON `HeadCosign`) |
| GET | `/ledger/consistency?oldSize=&newSize=` | consistency-доказательство (`newSize` по умолчанию — текущий размер) |

Коды ошибок (дополнительно): `unknown_witness` (403), `cosign_mismatch` (409), `invalid_range` (400).

## 7. Эволюция и классы изменений

| Изменение | Класс |
| --- | --- |
| Экономические параметры (Приложение A FEP) | R2 (FGP §4.0) |
| Реестр витнессов | R2 |
| Доменные метки, канонические байты, формат сумм | R3 + новые golden-векторы (ломает исторические артефакты) |
| Хеш журнала (SHA-256 → …) | FEP v2 (несовместимость журнала) |
| Ротация ключа владения, Postgres-журнал, внешнее якорение head, конфиденциальность агрегатов | дорожная карта v1.x (FEP §12) |

Правило совместимости: узел/клиент v1 обязан отвергать журнал с неизвестными видами записей — «мягкое непонимание» запрещено (реплей либо полный, либо никакой).

## 8. Безопасность

Модель угроз — [FEP-THREATS.md](FEP-THREATS.md). Специфика валютного слоя:

- **Форк журнала** — обнаружим косайнами (§4) и consistency (§5); стоимость скрытности растёт с числом независимых витнессов.
- **Реплей транзакций** — одноразовые nonce на весь журнал (FEP §6.3).
- **Кросс-протокольный реплей подписей** — исключён доменными метками (все подписи и хеши тегированы `flora/economy/v1/...`).
- **Компрометация ключа витнесса** — витнесс может заверить форк, но не может подделать историю (head должен совпасть с журналом посервисной проверки §4.3.3); ротация реестра — R2.
- **Компрометация секвенсора** — фальшивую экономику не построить незаметно: первый же реплей/косайн расходится; направление отказа — статус-кво (read-only), не работа поверх лжи.
